# Unified Directory and Hash-v9 Catalogs

`Icod.TermInfo.Catalogs` reads **one explicitly selected** conventional
terminfo directory or supported ncurses Berkeley DB Hash-v9 file. Both return
the same immutable `TerminalCatalog` model. The package targets .NET 8, 9 and
10; it composes Runtime, Inspection and the managed BerkeleyDb library. It
requires no native Berkeley DB runtime.

This guide describes the 1.17.0 stable candidate. The current published stable
version is **1.16.0**. Install examples for that published version do not yet
include Catalogs. The coordinated 1.17.0 packages are unpublished candidate artifacts
on [draft PR #48](https://github.com/uniblab/Icod.TermInfo/pull/48).

## Read a selected source

The same loop works after either source selection:

```csharp
using Icod.TermInfo.Catalogs;

var source = new TerminalCatalogSource(
    "./terminfo", TerminalCatalogSourceKind.ConventionalDirectory);
// To read a Hash-v9 file, use its file path and BerkeleyDbHash instead.
var options = new TerminalCatalogReadOptions(
    maximumCandidateCount: 10_000, maximumParsedBytes: 16 * 1024 * 1024);
var reader = new TerminalCatalogReader(source, options);
TerminalCatalog catalog = reader.Read();
Console.WriteLine($"{catalog.Source.Kind}: {catalog.Status}");
foreach (TerminalCatalogEntry entry in catalog.Entries)
    Console.WriteLine($"{entry.PublicationName} [{entry.Kind}] -> {entry.Terminal.Name}");
foreach (TerminalCatalogIssue issue in catalog.Issues)
    Console.WriteLine($"{issue.Kind}: {issue.EntryPath ?? issue.SourcePath}");
```

The [runnable sample](../samples/Icod.TermInfo.Catalogs.Sample/README.md)
creates both formats with public writers, calls one common print routine, and
demonstrates `Partial`, cancellation, an inclusive limit and a successful
subsequent read. Its `--verify` mode runs without an installed database, native
Berkeley DB, network access or terminal interaction.

The `TerminalCatalogSource` resolves the path to an absolute path on creation.
Selection does no I/O. `Read()` acquires fresh data each time and never searches
ambient provider paths or falls back to another format. An absent source,
explicit kind mismatch and inaccessible source have different results.

## Publication versus declaration

`PublicationName` is the name actually observed as a directory file or hashed
key. `entry.Terminal.Name` is the canonical identity declared *inside* the
compiled description. `entry.Terminal.Aliases` are declared identities; an
alias becomes an `Alias` row only when the corresponding file or key exists.
The sample's directory terminal declares `uc06-unpublished` but has no such
file, so it produces no row. A canonical publication produces a `Canonical`
row. A separately published alias produces a distinct `Alias` row pointing
to the same terminal identity.

Directory files have absolute `EntryPath` values; their `SourcePath` is the
absolute directory root. Hashed entries have a null `EntryPath`; their
`SourcePath` is the database file and `PublicationName` is the actual key. Do
not synthesize a per-entry hashed file path or infer a published key from a
declaration. When multiple physical directory files publish the same name,
all occurrences remain; `DuplicatePublicationNames` and one issue per group
report the ambiguity. No winner, cross-source priority or deduplication is
chosen. A duplicate hashed key instead invalidates the store.

Entries are sorted by publication name, then storage locator and kind, using
ordinal comparisons. Issues are sorted by locator, kind and message. Use the
typed `TerminalCatalogIssueKind` for decisions: the explanatory `Message` text
is not a stable programmatic code and may differ by operating system.

## Status and failure handling

| Status | Meaning | Rows |
| --- | --- | --- |
| `Complete` | Readable source with no issues, including a valid empty source | Observed publications |
| `Partial` | Directory candidates failed, links were skipped or duplicate names occurred | Valid siblings remain, possibly none |
| `Missing` | Source absent at the start of acquisition | None |
| `UnsupportedSource` | Explicitly selected kind does not match the source | None |
| `Unavailable` | Whole source cannot be accessed or read | None |
| `InvalidStore` | Malformed or unsupported hashed content/index/identity | None |

A linked directory **root** may be readable. Linked child files or
subdirectories are skipped with `LinkSkipped` issues rather than followed or
invented as alias rows. Bad compiled directory files may leave valid siblings
in a `Partial` result. Invalid Hash-v9 content fails closed with no partial
hashed entries. Source/permission/I/O issues have typed categories; do not
parse their text to distinguish causes.

## Limits, cancellation and source lifetime

`TerminalCatalogReadOptions` exposes inclusive candidate, retained entry,
issue, parsed-byte, hashed database-size, physical-record, index-hop and
decoded-byte bounds, plus a snapshot of Runtime's per-entry parser options.
Ignored filesystem candidates and malformed inputs still consume the
applicable work budgets; normalization never refunds acquired work. A value
exactly at its bound is allowed. The next item or byte raises
`TerminalCatalogLimitException` with the common `LimitName`, configured
`Limit`, source and, where applicable, a typed lower-layer inner cause. It
returns **no** truncated catalog.

Use `reader.Read(cancellationToken)` when callers need cancellation. A token
cancelled before a read raises `OperationCanceledException`; checks also occur
between acquisition, decoding, normalization and sorting steps. Cancellation
does not return a partial result and cannot interrupt a blocked synchronous
filesystem call. Returned catalogs retain no open source handles. Each new
read observes the source again and starts with fresh budgets; concurrent
replacement is **not** an atomic snapshot guarantee. Treat results from a
source being modified by another process as observations of that read, not a
cross-process transaction.

## Package and compatibility boundary

The 1.17 family contains **eight nupkg**, including the Tools package, and
**seven library snupkg**. Catalogs directly depends on matching-version
Runtime, Inspection and BerkeleyDb. Compiler is used in the sample to create
fixtures, not by production catalog reads. The isolated package consumer
restores only Catalogs directly from the locally built package feed and checks
transitive dependency closure on all three frameworks. The five Tools commands
and six existing platform archives do not acquire a Catalogs dependency.

Unified catalogs do not feed existing directory-only database sets, planning
or comparison APIs. Mixed-source precedence, directory/hashed conversion,
migration, synchronization, new JSON and `toe`/`infocmp`/`tic` catalog switches
are outside this release. Historical JSON v1–v6 and existing command output
remain unchanged.
