# Icod.TermInfo 1.3.0 — I03 Normalized Unresolved-Source Renderer

**Tranche:** I03 — Normalized unresolved-source renderer
**Development version:** `1.3.0-Alpha-3`
**Working branch:** `1.3.0`
**I03 preimage:** `ad690c394ab009fd7c1e31860bddc13eba7a5b31`
**Inspection assembly identity:** `Icod.TermInfo.Inspection, Version=1.0.0.0`

## Purpose

I03 adds deterministic rendering for the unresolved public Source 1.1 model.
Unlike the I02 effective renderer, I03 does not materialize a
`TerminalDescription` and therefore does not flatten `use=` inheritance.

The public surface is `TermInfoSourceRenderer`, with string and caller-owned
`TextWriter` entry points for both:

- `TermInfoSourceEntry`;
- `TermInfoSourceDocument`.

No command-line policy, native ncurses dependency, Compiler dependency, or
filesystem installation behavior is introduced.

## Source-model boundary

I03 renders the structured unresolved model rather than the lexical token stream.
For an entry it preserves:

- canonical terminal name;
- aliases;
- description;
- field sequence;
- field kind;
- capability identity;
- decoded numeric/string value;
- `use=` reference placement;
- cancellation placement;
- disabled-field placement;
- duplicate-field ordering.

For a document it additionally preserves entry order.

`TermInfoSourceDocument.Tokens` is deliberately not used to reconstruct the
original text. Comments, blank-line choices, indentation, original source spans,
and original lexical spellings are therefore outside the I03 preservation
contract.

## Canonical field forms

I03 emits enabled fields in normalized semantic form:

```text
am,
cols#80,
clear=\E[H,
```

Boolean fields retain their Source-model capability spelling. Numeric values are
emitted as invariant-culture decimal values, so equivalent hexadecimal and octal
input spellings normalize to decimal. String values are regenerated from the
decoded Source value with deterministic escaping.

Cancellation is rendered as:

```text
capability@,
```

Inheritance is rendered as:

```text
use=parent,
```

Both remain in their original field positions.

## Disabled fields

Source 1.1 intentionally models a disabled declaration as a disabled field plus
its capability identity. Any disabled operand spelling such as the right-hand
side of:

```text
.clear=\E[H,
```

is retained only in the field's raw lexical `Text`; it is not decoded into the
structured disabled-field model and is not consulted by inheritance resolution.

I03 therefore emits the canonical structured form:

```text
.clear,
```

This preserves the field kind, capability identity, sequence position, and
resolution behavior without pretending that an opaque disabled operand is part
of the structured semantic contract.

## Identity-header normalization

Source 1.1 has one historical header rule that requires special handling: a
final names-field component without whitespace is interpreted as both an alias
and the description.

For a parser-produced entry such as:

```text
example|short,
```

`Aliases` contains `short` and `Description` is also `short`. I03 recognizes
that dual role and emits the component once rather than incorrectly producing:

```text
example|short|short,
```

Structured header states that cannot be represented by the frozen Source 1.1
header rules fail deterministically with `InvalidOperationException`.

## String normalization

String rendering uses the same source-safe canonical spellings established by
I02 for source-significant characters:

- `\E` for ESC;
- `\a`, `\n`, `\r`, `\t`, `\b`, and `\f` for common controls;
- `\s` for space;
- escaped backslash, comma, caret, colon, and vertical bar;
- three-digit octal for remaining byte-range controls and high Latin-1 bytes.

The unresolved Source model may retain literal characters above Latin-1. I03
preserves those characters directly because this renderer is round-tripping the
Source model itself rather than projecting into I02's effective compiled-byte
representation.

An embedded NUL or a numeric/string field whose decoded value is absent cannot
be normalized from structured state and produces `InvalidOperationException`.
Raw malformed field text is not silently substituted for a missing semantic
value.

## Layout

Normalized output uses:

- LF line endings on every platform;
- four spaces before every capability field;
- eight spaces for wrapped string continuations;
- an 80-character wrapping target;
- one blank line between document entries.

Wrapping occurs only between complete encoded string units, so an escape such as
`\200` is never divided across physical source lines.

## Determinism

I03 does not sort source fields or entries. Their existing order is itself part
of the unresolved source semantics and is reproduced exactly.

Determinism therefore means that the same structured Source model always
produces the same normalized spelling and layout, independent of:

- process culture;
- operating system line endings;
- dictionary implementation details;
- repeated execution.

## Relationship to I02

The renderers answer different questions:

```text
TerminalDescriptionSourceRenderer
    effective state
    inheritance flattened
    cancellations/disabled/use= unavailable
    capability ordering canonicalized

TermInfoSourceRenderer
    unresolved Source state
    inheritance declarations retained
    cancellations/disabled/use= retained
    field and entry ordering retained
```

Neither renderer depends on `Icod.TermInfo.Compiler`.

## Validation

I03 tests exercise:

- multi-entry documents;
- multiple `use=` references;
- local values before and after inheritance references;
- cancellation in an inheritance-heavy entry;
- disabled fields with opaque operands;
- duplicate local declarations;
- mixed standard and extended capabilities;
- hexadecimal/octal numeric normalization;
- control, comma, space, high Latin-1, and Unicode string values;
- the Source 1.1 dual alias/description header rule;
- deterministic LF layout and wrapping;
- culture independence;
- string and `TextWriter` entry points;
- empty documents;
- explicit failure for undecoded malformed fields.

The principal gate performs:

```text
parse unresolved source
    -> render normalized unresolved source
    -> parse normalized source
```

and compares the ordered structured entry/field models. It then resolves every
entry from both documents and compares the resulting effective canonical I02
representations.

This demonstrates both unresolved-model equivalence and equivalent
re-resolution against the same document semantics.
