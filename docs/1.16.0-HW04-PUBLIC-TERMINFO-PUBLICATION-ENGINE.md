## Publication flow

The public writer performs these operations in order:

1. resolves the destination to a full path;
2. snapshots the writer options and enumerates the caller's entries exactly
   once;
3. applies the complete HW01 validation and Runtime parsing preflight;
4. creates the canonical ncurses key/data records;
5. constructs the complete deterministic Hash-v9 image in memory;
6. observes cancellation once more before opening the destination; and
7. writes the complete image through `CreateNew` by default or `Create` when
   `OverwriteExisting` is explicitly enabled.

All publication records are therefore validated and all pages are constructed
before destination mutation begins. Canonical names and aliases recover the
exact caller-supplied compiled bytes through the shipped reader, and the public
provider reconstructs the expected `TerminalDescription`.

## Determinism and interoperability evidence

The accepted tests prove that:

- equivalent publications produce identical bytes regardless of input order;
- the public output for a two-bucket overflow entry exactly matches the
  independent HW00 byte oracle;
- canonical and alias lookups return the exact compiled payload;
- the 1.15 managed reader and provider consume the public writer output;
- the input sequence is enumerated once;
- default publication refuses an existing destination and preserves its bytes;
- explicit overwrite replaces an existing destination;
- pre-open validation or image-construction failure preserves an existing
  destination; and
- pre-cancellation prevents destination creation.

## Frozen compatibility boundaries

HW04 adds no public type or member. The exact three-type writer surface frozen
in HW01 remains unchanged, reusable assembly identity remains `1.0.0.0`, and
the coordinated package version advances to `1.16.0-Alpha-4` on all three
target frameworks. `Icod.TermInfo.BerkeleyDb` retains its Runtime-only
production dependency and remains IL-only with no native assets.

Hash-v9 physical primary bucket counts remain powers of two. Berkeley DB's
mask-addressed lookup contract uses `high_mask` and `low_mask`; the earlier
prime-length sizing preference does not apply to this physical on-disk count.
This preserves native Hash-v9 compatibility and the accepted HW03 layout.

## Deliberate HW04 filesystem boundary

HW04 writes the already-complete in-memory image directly to the caller path.
This establishes the public publication engine, but it is not yet the safe
filesystem commit promised for the finished 1.16 release.

In particular, HW04 does not yet create a unique sibling temporary file,
flush and close it, reopen it through the production reader, or atomically
rename/replace it. An I/O or process failure after the destination is opened can
therefore expose a partial new file or, with explicit overwrite, damage the old
destination. Concurrent-writer, symlink/reparse, injected-I/O-failure, cleanup,
and commit-boundary guarantees are likewise not claimed here.

## Next gate

The next implementation gate is **HW05 / Alpha-5 — safe filesystem commit**.
HW05 owns sibling temporary-file construction, reader verification, durable
close/flush behavior, atomic same-filesystem commit, cleanup, overwrite race

failure tests. Migration and catalog automation remain deferred to 1.17.
