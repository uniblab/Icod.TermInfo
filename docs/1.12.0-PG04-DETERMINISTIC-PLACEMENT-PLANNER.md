# Icod.TermInfo 1.12.0 — PG04 Deterministic Placement Planner

**Tranche:** PG04 — deterministic lifecycle-aware placement planner  
**Development version:** `1.12.0-Alpha-4`  
**Baseline:** accepted PG03 placement classification  
**Primary package:** `Icod.TermInfo.Inspection`

## Purpose

PG04 adds the protocol-neutral planning layer that combines an already-produced frozen 1.11 persistent-raster lifecycle plan with the PG03 advanced-placement profile.

The planner does not repeat lifecycle capability analysis. The 1.11 planner remains authoritative for upload, placement creation, update, deletion, and resource lifecycle readiness. PG04 evaluates only the two 1.12 advanced-placement semantics:

```text
SourceRectangle
SignedZOrder
```

No concrete rectangle coordinates or signed z-order integers are carried by the TermInfo planning model.

## Public surface

PG04 adds six public types:

```text
PersistentRasterPlacementRequest
PersistentRasterPlacementPlanStatus
PersistentRasterPlacementPlanRequirement
PersistentRasterPlacementPlanIssue
PersistentRasterPlacementPlan
PersistentRasterPlacementPlanner
```

Together with PG01–PG03, the cumulative approved 1.12 Inspection API ledger now contains twelve `PersistentRasterPlacement*` public types.

## Request contract

`PersistentRasterPlacementRequest` contains two Boolean semantic requirements:

```text
RequireSourceRectangle
RequireSignedZOrder
```

At least one requirement must be selected. An empty placement request is invalid because it adds no 1.12 semantic constraint.

Requirements are emitted canonically in subject order:

```text
SourceRectangle
SignedZOrder
```

## Lifecycle composition

The planner signature is responsibility-equivalent to:

```csharp
PersistentRasterPlacementPlanner.Plan(
    PersistentRasterLifecyclePlan lifecyclePlan,
    PersistentRasterPlacementProfile placementProfile,
    PersistentRasterPlacementRequest request
)
```

This keeps the 1.11 and 1.12 contracts orthogonal:

- `PersistentRasterLifecyclePlanner` decides lifecycle admissibility once;
- `PersistentRasterPlacementPlanner` consumes that result without reinterpreting lifecycle evidence;
- the placement profile independently answers advanced semantic support.

A successful lifecycle plan does not imply advanced placement support. Advanced placement support does not imply lifecycle readiness.

## Deterministic outcome truth table

PG04 exposes four placement-plan outcomes:

```text
Satisfied                   = 0
RequiresRuntimeVerification = 1
Indeterminate               = 2
Impossible                  = 3
```

Outcome precedence is deterministic:

1. lifecycle `Impossible` or any requested placement subject classified `Unsupported` or `Contradicted` => placement `Impossible`;
2. otherwise lifecycle `Indeterminate` => placement `Indeterminate`;
3. otherwise any requested placement subject classified `Unknown` => `RequiresRuntimeVerification`;
4. otherwise all requested placement subjects are `Supported` and the result is `Satisfied`.

Placement impossibility therefore dominates an indeterminate lifecycle result.

## Requirements and issues

Every requested placement subject is retained in `PersistentRasterPlacementPlan.Requirements` with:

- the subject;
- its classified support status; and
- whether runtime verification is required.

Every non-supported placement requirement also produces one structured `PersistentRasterPlacementPlanIssue`.

For PG04:

- `Unknown` requires runtime verification;
- `Unsupported` is impossible;
- `Contradicted` is impossible;
- `Supported` produces no issue.

This treatment of `Contradicted` is intentionally stricter than the frozen 1.11 lifecycle planner. Conflicting advanced-placement evidence does not manufacture an executable semantic guarantee and is therefore not deferred as an admissible placement requirement.

Lifecycle uncertainty or impossibility is retained separately through `PersistentRasterPlacementPlan.LifecycleStatus`; PG04 does not duplicate the 1.11 lifecycle issue model.

## Immutability and bounds

Plans snapshot their canonical requirement and issue collections into read-only arrays.

The request vocabulary has exactly two subjects, so a placement plan contains one or two requirements and no more issues than requirements. This gives the planner a fixed cardinality independent of caller input size.

Undefined enum values and invalid public arguments use ordinary argument exceptions consistent with the rest of Inspection.

## Frozen compatibility boundaries

PG04 does not change:

- any `PersistentRasterLifecycle*` enum, request, profile, planner, plan, or issue type;
- JSON schema versions 1, 2, or 3;
- the 1.11 public API fingerprint;
- the production package dependency graph.

The cumulative 1.12 API ledger is used to reconstruct the exact frozen 1.11 Inspection surface during compatibility verification.
