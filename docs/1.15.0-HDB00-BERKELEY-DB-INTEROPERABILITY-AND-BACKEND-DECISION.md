# Icod.TermInfo 1.15.0 — HDB00 Berkeley DB Interoperability and Backend Decision

## Status

**Tranche:** HDB00 — Interoperability Research and Backend Decision  
**Decision:** select a bounded, dependency-free, managed Berkeley DB Hash-v9 reader for production 1.15 acquisition  
**Native Berkeley DB role:** fixture producer and interoperability oracle in development/CI only  
**Production writing:** deferred  
**Public provider API:** not frozen by HDB00

HDB00 establishes that ncurses hashed terminfo acquisition can preserve the
approved 1.15 architecture without introducing a second terminfo parser or a
mandatory native Berkeley DB dependency:

```text
Berkeley DB / hashed store
          |
          v
managed Hash-v9 container reader
          |
          v
ncurses hashed-record envelope
          |
          v
compiled entry bytes
          |
          v
CompiledTermInfoParser
          |
          v
TerminalDescription
```

The selected production direction is therefore **Approach B from the 1.15
roadmap, narrowed to the exact Berkeley DB Hash-v9 structures required by ncurses
read-only acquisition**.

---

## 1. Research questions

HDB00 was required to answer these questions before production API work:

1. Can a current ncurses hashed database be produced reproducibly against a
   supported Berkeley DB library?
2. What key/value envelope does ncurses store around compiled terminfo bytes?
3. How do canonical names and aliases resolve?
4. Are the bytes obtained from the hashed database identical to conventional
   `tic` compiled-entry bytes?
5. Does the existing `CompiledTermInfoParser` accept those bytes unchanged?
6. Can clean misses be distinguished from malformed/wrong database containers?
7. Are overflow pages required for legal terminfo entries, and can they be read
   safely?
8. Can a managed reader interpret the same database on Windows without Berkeley
   DB installed?
9. Should production 1.15 dynamically link Berkeley DB, bundle it, or read the
   required on-disk format directly?

The experiments answer all nine questions sufficiently for HDB01 to begin.

## 3. Native Berkeley DB oracle

### 3.1 Tested Berkeley DB

The Linux oracle used:

```text
Berkeley DB 5.3.28
Ubuntu 24.04
libdb5.3-dev / db5.3-util
```

The macOS oracle used Homebrew:

```text
berkeley-db@5
```

The ncurses source selects the modern Berkeley DB API when
`DB_VERSION_MAJOR` is available. HDB00 therefore does not assume that the legacy
`dbopen()` compatibility-1.85 API is the only relevant interface.

### 3.2 Exact ncurses hashed-record envelope

The ncurses writer stores two record kinds relevant to acquisition:

```text
marker 0 -> compiled terminfo data
marker 2 -> name/alias index target
```

The marker byte belongs to the ncurses hashed-storage envelope, not the compiled
terminfo entry.

A successful data lookup therefore yields:

```text
[ 0 ][ compiled terminfo bytes ... ]
```

and the bytes passed to `CompiledTermInfoParser` begin immediately after the
marker.

An index lookup yields:

```text
[ 2 ][ target database key ... ]
```

and acquisition performs a bounded exact-key lookup using that target.

## 4. Canonical-name and alias evidence

The ordinary HDB00 fixture declares:

```text
hdb00-primary|hdb00-alias|Icod HDB00 hashed terminfo fixture
```

Native Berkeley DB lookup demonstrated:

```text
canonical request: hdb00-primary
lookup hops:       2
compiled bytes:    871

data records:      1
index records:     2
```

and:

```text
alias request:     hdb00-alias
lookup hops:       2
compiled bytes:    871

data records:      1
index records:     2
```

Both names resolve to the same marker-0 compiled-data record.

The canonical extraction, alias extraction, and conventional directory entry are
byte-identical. Their observed payload SHA-256 is:

```text
1b71f0eb0b552389b41d9e7d99f1bd8237e30aaee6d27cc973194766584cdd70
```

The existing managed acquisition sample then parses those bytes unchanged and
observes:

```text
Name: hdb00-primary
Aliases: hdb00-alias
Columns: 80
Lines: 24
Colors: 8
```

This satisfies the fundamental HDB00 acceptance condition: the hashed-storage
layer can stop at opaque compiled bytes and reuse the existing Runtime parser.

## 5. Managed Berkeley DB Hash-v9 experiment

HDB00 implemented a deliberately narrow managed reader to determine whether
production acquisition actually requires native Berkeley DB.

The experiment recognizes only the structures needed for bounded read-only
ncurses acquisition:

- Berkeley DB Hash magic;
- on-disk Hash format version 9;
- byte-order detection;
- bounded power-of-two page sizes;
- Hash metadata pages;
- Hash data pages;
- inline key/data items;
- off-page item references;
- overflow-page chains;
- exact byte keys;
- ncurses marker-2 index indirection;
- ncurses marker-0 data extraction.

It deliberately does **not** implement:

- Berkeley DB hashing or bucket selection;
- writes;
- transactions;
- recovery;
- environments;
- locking policy;
- Btree, Queue, Recno, or Heap access methods;
- encrypted databases;
- checksummed-page variants;
- arbitrary Berkeley DB application semantics.

For read-only terminfo acquisition, scanning validated Hash pages and comparing
exact keys is sufficient. A production implementation may build a bounded
in-memory key index after validation, but does not need to reproduce Berkeley
DB's hash algorithm.

## 6. Managed/native equivalence

The managed reader was tested against the same database used by the native
Berkeley DB oracle.

On both Linux and macOS it independently produced the same results for:

- canonical-name lookup;
- alias lookup;
- marker-2 indirection;
- marker-0 extraction;
- clean miss;
- wrong database access method rejection; and
- arbitrary/truncated input rejection.

For the ordinary fixture the managed reader reported:

```text
Berkeley DB Hash version: 9
Byte order: little-endian
Page size: 4096
Lookup: hdb00-primary
Hops: 2
Compiled bytes: 871
Data records: 1
Index records: 2
```

The managed and native extracted payloads compare byte-for-byte.

## 7. Overflow-page evidence

A second fixture deliberately increases the compiled terminfo payload enough to
force Berkeley DB off-page storage.

Observed native result:

```text
Lookup: hdb00-overflow
Hops: 2
Compiled bytes: 2967
Data records: 1
Index records: 1
Overflow pages: 1
```

The conventional compiled entry and native hashed extraction have payload
SHA-256:

```text
0d8055f77cbc130d8da0bada82534d7adff9eb4bb96e7f236c57e7f39a537f09
```

The managed reader reconstructs the overflow chain and produces exactly the same
2,967 bytes. The existing `CompiledTermInfoParser` accepts those bytes unchanged.

The managed overflow reader validates at least:

- page number bounds;
- page type;
- declared total length;
- per-page payload length;
- cumulative length;
- next-page references; and
- cycle detection.

This establishes that production 1.15 cannot assume all legal ncurses terminfo
records are inline within a Hash page.

## 8. Windows cross-host portability

The Linux HDB00 job publishes only the generated Hash-v9 databases and oracle
payloads as a short-lived CI artifact.

A Windows job then:

1. installs only .NET;
2. downloads the Linux-generated database;
3. does **not** install Berkeley DB;
4. runs the managed reader against `hdb00-alias`;
5. compares the result with the Linux native-oracle payload;
6. runs the managed reader against the overflow fixture; and
7. compares that result with the Linux native-oracle overflow payload.

Both comparisons pass.

Therefore Berkeley DB Hash-v9 terminfo acquisition can be portable across the
Icod Windows/Linux/macOS support matrix without shipping or requiring a Berkeley
DB native library.

## 9. Failure classification evidence

HDB00 distinguishes these container-level outcomes before Runtime parsing.

### Clean miss

A valid Hash-v9 database with no exact key yields a clean miss.

The research probe uses a dedicated status for this case and does not classify it
as corruption.

### Wrong access method

A Berkeley DB Btree database is rejected as not being the supported Hash
container.

### Arbitrary/truncated bytes

Input too small to contain a valid metadata page or without the expected Hash
magic is rejected as malformed/unsupported database input.

### Unsupported Hash format

The HDB00 managed reader accepts on-disk Hash format **version 9 only**. Other
versions are explicit unsupported-format failures until authoritative fixtures
are added.

### Malformed compiled value

Once marker-0 bytes are extracted, `CompiledTermInfoParser` remains authoritative
for compiled terminfo validation.

### Identity mismatch

The future provider must still validate the resulting `TerminalDescription`
canonical name and aliases against the originally requested name. A database key
alone is not proof of terminal identity.

## 11. Licensing and distribution decision

Native Berkeley DB was rejected as a production dependency for 1.15 for both
portability and distribution reasons.

Oracle documents that Berkeley DB 6.0 and later moved to AGPLv3, while previous
releases continue under the Sleepycat license:

- <https://docs.oracle.com/database/bdb181/html/installation/license_change60.html>

Oracle's Berkeley DB licensing information also states that redistribution under
the open-source licensing model can require the complete source code of an
application using Berkeley DB to be available and freely redistributable:

- <https://www.oracle.com/database/technologies/related/berkeleydb/berkeleydb-licensing.html>

Those obligations are inappropriate to impose indirectly on arbitrary downstream
consumers of a reusable Icod NuGet package.

The managed reader avoids that coupling:

- `Icod.TermInfo.BerkeleyDb` does not link Berkeley DB;
- it does not redistribute Berkeley DB binaries;
- it does not require Berkeley DB to be installed;
- Berkeley DB packages installed by CI are development/test oracle dependencies,
  not package dependencies; and
- production artifacts contain only Icod-managed code.

This document records an engineering scope decision, not legal advice. Any future
proposal to redistribute or dynamically link Berkeley DB must receive a new
licensing review.

## 12. Backend decision

### Approach A — dynamically bind native Berkeley DB

**Result:** interoperable, but rejected as the production default for 1.15.

Reasons:

- native availability differs by OS/distribution;
- ABI/library-name probing becomes product behavior;
- Windows has no comparable system-default Berkeley DB dependency;
- native lifetime and loader failures enlarge the error model;
- downstream licensing consequences are undesirable; and
- the managed experiment proves the native dependency is unnecessary for the
  approved read-only scope.

Native Berkeley DB remains valuable as the independent compatibility oracle in
CI.

### Approach B — bounded managed Hash-v9 reader

**Result:** **selected for production 1.15.**

Reasons:

- byte-identical results against native Berkeley DB on Linux and macOS;
- cross-host success on Windows with no Berkeley DB installation;
- overflow records are supported;
- no native ABI dependency;
- no bundled third-party binary;
- deterministic hostile-input validation is under Icod control;
- the supported subset can remain much smaller than a general Berkeley DB
  implementation; and
- the existing Runtime parser remains the sole terminfo semantic parser.

### Approach C — bundle Berkeley DB native binaries

**Result:** rejected.

The portability, security-maintenance, artifact-size, native servicing, and
licensing costs are unnecessary given the successful managed experiment.

## 13. Consequences for the remaining 1.15 roadmap

HDB01 and later tranches should now treat `Icod.TermInfo.BerkeleyDb` as an
**optional package with no native or third-party production dependency**.

### HDB01

Create the optional package and tests, but do not expose concepts such as a native
backend loader merely because they appeared in the provisional roadmap.

### HDB02

HDB02 becomes the productionization of the **managed read-only Berkeley DB Hash-v9
container reader**.

Its production requirements include:

- stream/file-length bounds before allocation;
- bounded page size;
- bounded page count;
- exact Hash-v9 metadata validation;
- byte-order handling;
- validated Hash-page index tables;
- bounded inline records;
- bounded off-page records;
- overflow cycle detection;
- overflow cumulative-length validation;
- explicit unsupported handling for encryption/checksum variants;
- explicit rejection of non-Hash containers; and
- no general Berkeley DB public API.

### HDB03

The public hashed terminal provider composes the managed container reader with
`CompiledTermInfoParser` and requested-name identity validation.

There is no production "Berkeley DB backend unavailable" state because no native
backend is required.

### HDB04 and later

System discovery, enumeration, tools, hardening, packaging, and release gates all
remain applicable, but their cross-platform qualification becomes purely managed.
Native Berkeley DB is needed only in fixture-generation/differential-oracle CI.

---

## 14. Compatibility claim

HDB00 freezes a deliberately narrow initial storage claim:

> Icod.TermInfo 1.15 targets ncurses-compatible, read-only Berkeley DB **Hash
> on-disk format version 9** stores whose required page/item forms are covered by
> authoritative fixtures and the 1.15 hardening corpus.

HDB00 does **not** claim compatibility with every historical Berkeley DB release
or every possible Hash-v9 database feature.

Additional database format versions or page features require explicit fixtures,
adversarial tests, and a reviewed compatibility expansion.
