## Input validation

`Plan(...)` snapshots the candidate sequence exactly once and requires:

- one or two candidates;
- no null candidate element;
- unique backend identity;
- a non-null semantic request; and
- when a preference order is present, a complete set-equal ordering of exactly the supplied candidate backends.

Empty input, more than two candidates, duplicate candidates, partial preference, absent-candidate preference, and cardinality mismatch are rejected.

`options = null` is equivalent to `new RasterBackendSelectionOptions()` and therefore means that the caller supplied no ranking.

## Candidate evaluation and canonical output

Every candidate is evaluated only through the existing RB03 `RasterBackendPlanner.Evaluate(...)` method. RB04 does not duplicate lifecycle or placement semantics.

Stored `CandidateEvaluations` are ordered by backend numeric identity for deterministic output. This canonicalization happens independently of winner selection and is never used as a ranking rule.

## Selection semantics

### Explicit complete preference

The planner walks the caller's preference order exactly as supplied:

1. `Impossible` candidates are skipped;
2. the first `RequiresRuntimeVerification` candidate stops fallback and yields overall `RequiresRuntimeVerification` with no selected backend;
3. the first `Satisfied` candidate is selected; and
4. if every candidate is impossible, the plan is `Impossible`.

An unverified preferred backend therefore blocks fallback to a lower-ranked satisfied backend.

### No preference

The planner counts non-impossible candidates independently of input and canonical order:

- zero => `Impossible`;
- exactly one `Satisfied` => `Selected` with that backend;
- exactly one `RequiresRuntimeVerification` => `RequiresRuntimeVerification` with no selected backend; and
- more than one non-impossible candidate => `RequiresPreference` with no selected backend.

`SelectedBackend` is populated exactly when the overall status is `Selected`.
