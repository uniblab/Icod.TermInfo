# Icod.TermInfo 1.3.0 — I02 Canonical Effective Source Renderer

**Tranche:** I02 — Canonical effective source renderer
**Development version:** `1.3.0-Alpha-2`
**Working branch:** `1.3.0`
**I02 preimage:** `c4fb78a269b4ab96405413deff3dedbc4265db4f`
**Inspection assembly identity:** `Icod.TermInfo.Inspection, Version=1.0.0.0`

## Purpose

I02 introduces the first public `Icod.TermInfo.Inspection` behavior: deterministic
rendering of an effective `TerminalDescription` into normalized `.ti`-style
source.

The renderer is deliberately an Inspection responsibility. Runtime remains the
effective semantic model; Source remains the parser/resolver; Compiler remains
the compiled-entry writer. I02 does not enlarge the frozen Runtime, Source, or
Compiler public APIs.

## Public API

I02 introduces:

```text
TerminalDescriptionSourceRenderer
```

with a string-returning entry point and a caller-owned `TextWriter` entry point.

The public Inspection API baseline advances from the intentionally empty I01
baseline to this reviewed renderer surface.

## Canonical output

The renderer emits:

1. canonical terminal name;
2. aliases;
3. verbose description when present;
4. standard Boolean capabilities;
5. standard numeric capabilities;
6. standard string capabilities;
7. extended capabilities.

Standard capabilities are obtained from `StandardCapabilityCatalog` and emitted
in canonical compiled-table order within each value kind.

Extended capabilities are emitted in this order:

```text
Boolean
numeric
string
```

and then by ordinal, case-sensitive capability name within each kind.

Effective absence is omitted.

## String representation

Output uses the Source 1.1 byte semantics.

Canonical escapes include conventional forms for ESC, bell, newline, carriage
return, tab, backspace, form feed, space, backslash, comma, caret, colon, and
vertical bar. Other control bytes, DEL, and high Latin-1 bytes are emitted as
three-digit octal escapes.

String wrapping:

- uses LF regardless of host operating system;
- begins capability fields with four spaces;
- continues wrapped string values with eight spaces;
- targets a deterministic maximum physical line length of 80 characters;
- never splits one source escape sequence across physical lines.

The frozen Source value parser removes the physical continuation newline and
indentation, so wrapping does not alter the decoded capability value.

## Effective versus source-aware state

I02 renders only effective `TerminalDescription` state.

It does not and cannot reconstruct:

- `use=` inheritance;
- cancellation tombstones;
- disabled source fields;
- duplicate source fields;
- comments;
- source spans;
- source formatting or provenance.

Those are Source-layer facts and remain work for I03 and I05.

## Lossless-representation boundary

`TerminalDescription` can express a few states which the frozen Source 1.1
grammar cannot round-trip exactly.

I02 rejects those states with `InvalidOperationException`; it never rewrites
them into a semantically different source entry.

Rejected cases include:

- aliases when no verbose description exists, because Source would interpret
  the final names-field component as a description;
- a verbose description containing no whitespace, because Source deliberately
  treats such a final component as both alias and description;
- header components containing source field separators or otherwise ambiguous
  trailing escapes;
- negative numeric values, which the frozen Source numeric grammar does not
  accept;
- embedded NUL in a string value;
- string characters outside the Latin-1 byte range;
- source-significant extended-capability names which cannot be represented as
  an enabled field without changing the capability name.

This is a representation failure, not a parser or resolver diagnostic.

## Validation

I02 tests cover:

- every built-in terminal profile;
- all five checked-in T29 compiled fixtures;
- source-sensitive punctuation and control bytes;
- high Latin-1 bytes;
- canonical standard and extended ordering;
- a description containing every standard capability;
- deterministic 80-character wrapping;
- LF-only output;
- repeated rendering;
- culture independence;
- parity between string and `TextWriter` entry points;
- deterministic rejection of unrepresentable effective state;
- public argument validation.

The round-trip gate is:

```text
TerminalDescription
    |
    v
TerminalDescriptionSourceRenderer
    |
    v
TermInfoSourceParser
    |
    v
TermInfoSourceResolver
    |
    v
TerminalDescription
```

The first and final descriptions must be semantically equivalent.

The T29 gate begins from compiled fixture bytes:

```text
compiled fixture
    |
    v
CompiledTermInfoParser
    |
    v
TerminalDescription
    |
    v
render -> parse -> resolve
    |
    v
equivalent TerminalDescription
```

No host `tic`, `infocmp`, ncurses library, or external terminal database is
required.

## Package and compatibility contract

All four coordinated package versions advance to `1.3.0-Alpha-2`.

All four assemblies retain version `1.0.0.0`.

The dependency graph remains:

```text
Inspection -> Source -> Runtime
Inspection ----------> Runtime

Compiler   -> Source -> Runtime
Compiler   ------------> Runtime
```

Inspection gains no production dependency on Compiler.

The Runtime 1.0, Source 1.1, and Compiler 1.2 public API baselines remain
unchanged.
