# Icod.TermInfo 1.9.0 MI04 - Database Catalog Manifests and JSON Schema

**Development version:** `1.9.0-Alpha-4`
**Roadmap tranche:** MI04
**Status:** complete
**Public API change:** none

## Purpose

MI04 activates the existing `TermInfoJsonRenderer.Render` overloads for
`TermInfoDatabaseCatalog` and publishes the complete version-1 JSON Schema. The
renderer is a deterministic, bounded projection of an already inspected catalog.
It does not inspect a directory, load terminal capabilities again, sort evidence,
resolve duplicate names, or rerun planning.

The envelope remains:

```json
{
  "schema": "urn:icod:terminfo:inspection:json:1",
  "schemaVersion": 1,
  "documentKind": "databaseCatalog",
  "data": {}
}
```

The existing MI01 public surface remains unchanged at 31 exported Inspection
types. MI05 owns command-level JSON composition.

## Catalog payload

The `data` object has this exact property order:

1. `root`
2. `kind`
3. `isComplete`
4. `entries`
5. `issues`
6. `duplicateCanonicalNames`

`root` is the normalized root recorded by `TermInfoDatabaseCatalog`. `kind` is
one of `missing`, `conventionalDirectory`, `unsupportedStore`, or `unavailable`.
The renderer maps the managed enum explicitly and rejects unknown enum values.

`isComplete` is true only when the supplied catalog kind is
`ConventionalDirectory` and `HasIssues` is false. Missing, unsupported,
unavailable, malformed, permission-failed, I/O-failed, link-skipped, and other
partial catalog states therefore do not claim completeness.

Duplicate canonical names are separate ambiguity evidence. They remain in
`duplicateCanonicalNames` in the catalog's existing order. They do not by
themselves change `isComplete`; downstream planning retains responsibility for
rejecting conflicting duplicate meanings. The renderer neither hides nor
resolves that ambiguity.

## Entries and issues

Every entry is projected in the supplied catalog order with:

- normalized `path`;
- canonical `name`;
- aliases in immutable terminal-identity order; and
- nullable `description`.

The manifest deliberately does not recursively embed terminal capabilities.
Callers that require an effective description can render that description as a
separate `terminalDescription` document.

Every issue is projected in the supplied catalog order with `kind`, `path`, and
`message`. The stable issue strings are `malformedEntry`, `invalidPlacement`,
`permissionFailure`, `ioFailure`, and `linkSkipped`. Valid entries remain visible
when issues make a conventional-directory catalog incomplete.

## Determinism, bounds, and cancellation

Compact JSON is canonical. Indented JSON uses LF and two spaces and has no
trailing line terminator. Strings retain the MI01 safe escaping and invalid
UTF-16 rejection policy. `MaximumOutputByteCount` applies to the exact final
UTF-8 representation.

Cancellation is checked before rendering, at entry, alias, issue, and duplicate
name boundaries, and before returning the finished document. Cancellation never
causes a partial string to be returned.

## Complete version-1 schema

`docs/Icod.TermInfo.Inspection.schema.json` is a JSON Schema draft 2020-12
document with identifier `urn:icod:terminfo:inspection:json:1`. It covers all
four published document kinds:

- `terminalDescription`;
- `comparison`;
- `sourcePlan`; and
- `databaseCatalog`.

Payload objects reject unknown properties. The envelope permits additional
properties so version-1 consumers can tolerate future envelope metadata without
changing the meaning or value kind of an existing field. A breaking payload
change requires a new schema identifier and version.

The schema is included in the `Icod.TermInfo.Inspection` NuGet package at
`docs/Icod.TermInfo.Inspection.schema.json`. Package verification requires that
entry and verifies the schema dialect, identifier, and four document variants.

## Fixtures and evidence

The checked-in fixtures include compact and indented forms for every published
document kind. MI04 adds both complete and incomplete catalog states:

```text
tests/Icod.TermInfo.Inspection.Tests/fixtures/mi04/
    database-catalog.complete.compact.json
    database-catalog.complete.indented.json
    database-catalog.incomplete.compact.json
    database-catalog.incomplete.indented.json
```

The complete fixture retains duplicate canonical-name evidence without claiming
an inspection issue. The incomplete fixture retains a valid entry and its
malformed-entry issue while setting `isComplete` to false. Tests validate all
MI02, MI03, and MI04 fixtures against the published schema and also prove that
missing required fields, unknown catalog kinds, and false completeness claims
are rejected.

Additional gates cover exact text fixtures, property and item order, every
catalog and issue mapping, culture and repeated-run determinism, exact UTF-8
bounds, cancellation, invalid text, packaged schema presence, package-consumer
rendering, and the unchanged 31-type public surface.

## Forward boundary

MI04 completes reusable JSON rendering and the version-1 schema. It does not add
command options or change stdout, stderr, or exit-status behavior. MI05 owns
`infocmp` and `toe` JSON automation and explicit-directory all-candidates
planning.
