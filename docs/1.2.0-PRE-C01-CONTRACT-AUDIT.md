## Purpose

This document freezes the architectural decisions made before implementation of
the 1.2 terminfo compiler line.

The 1.1 source-language work proved that package topology, public-API
snapshotting, package smoke tests, release verification, and publication policy
must be established at the beginning of a new package rather than deferred to
release closure.

Accordingly, C01 owns both the Compiler package foundation and the minimal
binary-writer contract.

## Existing foundation

The 1.2 writer is built on already-frozen contracts:

- `TerminalDescription` is the single immutable resolved semantic model;
- `StandardCapabilityCatalog` is authoritative for standard capability names,
  kinds, and binary indices;
- `CompiledTermInfoParser` accepts the selected conventional compiled family;
- the runtime parser understands legacy `0432`, `01036` wide numerics, and the
  selected ncurses extended section;
- compiled capability bytes use the reversible Latin-1 bridge;
- `Icod.TermInfo.Source` parses and resolves `.ti` source and materializes
  effective `TerminalDescription` values;
- source cancellation tombstones do not survive materialization;
- the checked-in T29 compiled corpus provides offline reference evidence with
  pinned ncurses/`tic` provenance.

No 1.2 implementation may create a parallel standard capability table or a
second source parser/resolver.

## Package topology

The package graph is:

```text
Icod.TermInfo.Compiler
        |        \
        |         +------------> Icod.TermInfo
        |
        +----> Icod.TermInfo.Source
                        |
                        +--------> Icod.TermInfo
```

C01 initially requires only:

```text
Icod.TermInfo.Compiler
    -> Icod.TermInfo
```

The Compiler dependency on Source is introduced no earlier than C05, when
source compilation becomes part of the Compiler package.

The following dependencies are forbidden:

```text
Icod.TermInfo -> Icod.TermInfo.Source
Icod.TermInfo -> Icod.TermInfo.Compiler
Icod.TermInfo.Source -> Icod.TermInfo.Compiler
```

The runtime package remains dependency-free.

## Low-level writer ownership

The low-level writer is the inverse of the existing reader:

```text
CompiledTermInfoParser
    compiled bytes -> TerminalDescription

CompiledTermInfoWriter
    TerminalDescription -> compiled bytes
```

`CompiledTermInfoWriter` is the preferred public type name. Exact method and
options signatures remain subject to the C01 API-regret review.

The writer is pure. It does not:

- inspect `TERMINFO`, `TERMINFO_DIRS`, HOME, or platform database roots;
- read or write filesystem entries;
- install entries globally;
- invoke native `tic`, `infocmp`, `libtinfo`, or ncurses;
- own caches or process-global state.

C06 owns database-layout filesystem output.

## Binary family and tranche ownership

The complete 1.2 writer ultimately supports exactly the conventional binary
family already accepted by the runtime parser:

```text
0432
01036
ncurses extended section
```

Tranche ownership is:

```text
C01  minimal deterministic 0432 writer
C02  complete standard capability emission
C03  ncurses extended capability emission
C04  explicit/automatic format selection and representation limits
C05  source compiler composition
C06  safe database-layout output
C07  corpus, robustness, determinism, and differential validation
```

C01 does not need to implement C03/C04 behavior merely because its public writer
will eventually support those formats.

## Binary representation rules

All integer fields are emitted little-endian according to the frozen reader
contract.

Standard capability positions come only from
`StandardCapabilityCatalog.BinaryIndex`. Enum ordinal values and a duplicated
compiler capability table are forbidden.

Identity strings, extended capability names, and capability strings use a
strict Latin-1 encoding contract:

- code points representable as one byte are emitted exactly;
- unrepresentable managed characters fail;
- replacement characters are never substituted silently;
- embedded NUL fails wherever NUL terminates a binary field;
- identity data containing the compiled names separator fails when it would
  make canonical name/alias/description boundaries ambiguous.

The writer performs checked arithmetic before narrowing values to 16-bit fields
or allocating output buffers.

## Representation versus runtime semantics

`TerminalDescription` is intentionally broader than any one binary
representation. A valid runtime description is not automatically encodable in
every compiled format.

The writer therefore distinguishes:

```text
invalid caller argument
valid semantic value not representable in selected compiled format
successful deterministic encoding
```

No successful path silently truncates, wraps, replaces, or invents data.

The existing parser contract treats the compiled names field as containing a
canonical name and verbose description. Therefore a `TerminalDescription` with
no description is not currently losslessly representable. The writer fails
rather than synthesizing a description unless later authoritative evidence
establishes an equivalent conventional representation.

Present numeric values which collide with compiled absent/canceled sentinels or
fall outside the selected numeric representation are not silently coerced.
String/name offsets and extended table sizes must fit their frozen field widths.

## Cancellation boundary

Compiled formats have absent/canceled sentinels, but the immutable resolved
`TerminalDescription` intentionally exposes only effective capability presence.

Source cancellation tombstones disappear during:

```text
TermInfoSourceResolvedEntry
    -> TerminalDescription
```

Consequently:

- a writer receiving only `TerminalDescription` cannot distinguish absent from
  canceled source state;
- it emits absence for absent effective values;
- it does not invent cancellation sentinels;
- C05 preserves effective terminal semantics, not source-only tombstone history.

If a future use case requires source cancellation preservation in emitted
compiled data, that requires an explicit richer input contract and a separate
API review.

## Determinism

For the same semantic input and writer options, output bytes are identical
across:

- repeated executions;
- Windows, Linux, and macOS;
- `net8.0` and `net10.0`;
- process culture;
- dictionary insertion/enumeration order.

Standard capabilities use canonical binary order. Extended capabilities are
grouped by Boolean, numeric, and string kind and ordered by ordinal,
case-sensitive name within each kind.

Alias order is preserved because aliases are already an ordered part of
`TerminalDescription` identity.

## Validation strategy

The principal semantic invariant is:

```text
TerminalDescription A
    -> write
    -> compiled bytes
    -> CompiledTermInfoParser
    -> TerminalDescription B

A == B semantically
```

That invariant is necessary but not sufficient. The writer also requires direct
binary-layout assertions so a matching bug in writer and reader cannot validate
itself.

The checked-in T29 corpus and pinned `tic` provenance provide independent
compatibility evidence. Normal CI remains offline with respect to native
ncurses; optional differential regeneration remains a maintainer operation.

## C01 readiness gate

C01 may begin when this contract is accepted.

C01 is complete only when:

- all three package projects are `1.2.0-Alpha-1`;
- all three assembly versions remain `1.0.0.0`;
- Compiler is independently consumable as a NuGet package;
- Compiler API manifests match across `net8.0` and `net10.0`;
- the initial Compiler API baseline is checked in;
- the minimal writer emits deterministic legacy `0432`;
- the existing parser reads those bytes back with semantic equivalence;
- strict Latin-1 and representation failures are deterministic;
- Runtime remains dependency-free;
- Source remains independent of Compiler;
- package verification and fresh Compiler consumers pass on both target
  frameworks;
- the Windows/Linux/macOS CI matrix remains green.

No C02 standard-table breadth, C03 extended writing, C04 full format policy, C05
source compilation, or C06 filesystem output is required to close C01.
