## Evaluator contract

RB03 adds exactly one behavior owner:

```csharp
RasterBackendPlanner.Evaluate(
    RasterBackendCandidate candidate,
    RasterBackendSelectionRequest request
)
```

The evaluator always delegates lifecycle semantics to `PersistentRasterLifecyclePlanner`. When a placement request is present, it always delegates placement semantics to `PersistentRasterPlacementPlanner`. The resulting plans are retained in `RasterBackendCandidateEvaluation` even when backend availability itself determines the final candidate status.

Backend availability has final-status precedence exactly as approved:

- `Unsupported` => `Impossible`;
- `Unknown` or `Contradicted` => `RequiresRuntimeVerification`;
- `Supported` => status derives from the frozen lifecycle/placement plans.

For a supported backend, lifecycle `Impossible` => candidate `Impossible`; lifecycle `Indeterminate` => runtime verification; lifecycle `Success` with no placement request => `Satisfied`; otherwise placement `Impossible` => candidate `Impossible`, placement `RequiresRuntimeVerification`/`Indeterminate` => runtime verification, and placement `Satisfied` => candidate `Satisfied`.

No Sixel/Kitty-specific lifecycle or placement rule exists in the evaluator. Backend identity is carried only as candidate identity.
