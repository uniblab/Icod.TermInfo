## 2. Frozen output-profile facts

The following facts are accepted inputs to HW01 and later construction work:

| Property | Accepted HW00 value |
| --- | --- |
| Access method | Berkeley DB Hash |
| On-disk version | 9 |
| Byte order | little-endian |
| Page size | 4096 bytes |
| Initial buckets | two, mapped to pages 1 and 2 |
| Metadata page type | 8 |
| Hash page type | 13 |
| Overflow page type | 7 |
| Inline item type | 1 |
| Off-page item type | 3 |
| Ncurses data marker | 0 |
| Ncurses publication marker | 2 |

The qualified hash function begins with zero and, for each input byte, performs
an unchecked 32-bit multiply by `16777619` followed by XOR with that byte.
Bucket selection uses the Hash-v9 high/low-mask rules.

The metadata character-key hash is not the hash of the visible characters alone.
Berkeley DB hashes `sizeof("%$sniglet^&")`, including the terminating NUL. The
canonical stored value is therefore:

```text
0x5E688DD1
```

Omitting that NUL produces a structurally readable database that native
`db_verify` correctly rejects as using a custom hash function.

## 3. Native sorted-page invariant

Hash-v9 pages use native binary search. Keys within a bucket must therefore use
Berkeley DB's exact byte comparator, not the platform's generic byte-sequence
comparer.

The accepted order is:

1. compare corresponding bytes in ascending unsigned-byte order; then
2. when one key is an exact prefix of the other, place the **longer** key first.

For example:

```text
hdb00-alias
hdb00-primary|hdb00-alias|description
hdb00-primary
```

A generic lexicographic comparer places the shorter exact prefix first. Such a
page remains visible to sequential dump/verification, but native binary lookup
can report a clean miss for a present key. The accepted test corpus pins this
ordering explicitly.

## 4. Inline, collision, and overflow evidence

The managed candidate contains five ncurses records:

- two marker-2 publications for `hdb00-primary` and `hdb00-alias`;
- one marker-0 compiled-data record for their shared storage key;
- one marker-2 publication for `hdb00-overflow`; and
- one marker-0 compiled-data record for the overflow fixture.

The probe also generates controlled multi-record inputs proving that both initial
buckets receive records and that multiple key/value pairs coexist on a bucket
page.

Items larger than one quarter of the 4096-byte page use a 12-byte off-page item
reference. Overflow pages carry at most 4070 payload bytes after the 26-byte page
header and form an explicitly numbered, bounded chain. The 2,967-byte native
overflow fixture is recovered byte-for-byte by native and managed readers.

## 5. Determinism evidence

The research writer:

- snapshots the compiled-entry inputs;
- derives exact ncurses storage and publication keys from the compiled names
  section;
- rejects duplicate database keys;
- sorts records with the native Hash-v9 comparator;
- derives page numbers and offsets through checked arithmetic;
- uses canonical not-logged LSN values;
- derives the 20-byte file identifier from the sorted logical records; and
- clears and rewrites a caller-provided output stream as one complete image.

Reversing the input sequence produces byte-identical output. No output byte
depends on current culture, temporary path, destination path, process ID, time,
or operating system.

## 7. Licensing and dependency consequence

HW00 does not change the LGPL-3.0 licensing of Icod.TermInfo and does not add a
Berkeley DB production dependency.

- no Berkeley DB source, header, library, or binary is incorporated into an Icod
  assembly, NuGet package, or tool archive;
- no production code dynamically loads or invokes Berkeley DB;
- native packages installed by CI are independent interoperability oracles;
- the managed writer is an original implementation of the qualified on-disk
  format facts; and
- `Icod.TermInfo.BerkeleyDb` continues to depend only on `Icod.TermInfo` Runtime.

This is an engineering/distribution decision, not legal advice. Any future plan
to link, bundle, or redistribute Berkeley DB requires a new licensing review.

## 8. Backend decision

### Native Berkeley DB writer

**Rejected for production.** It would add platform-specific discovery, loading,
lifetime, packaging, servicing, and downstream licensing concerns that the
managed proof demonstrates are unnecessary.

### Bounded managed Hash-v9 whole-file writer

**Selected for 1.16.** It satisfies native and managed readers on all supported
hosts, keeps the implementation terminfo-specific, preserves deterministic output,
and avoids a native production dependency.

### General-purpose Berkeley DB writer

**Rejected.** Transactions, recovery, environments, multiple access methods,
in-place mutation, and arbitrary key/value APIs are outside the approved release
and would create a substantially larger compatibility and security surface.

- complete deterministic images, not in-place mutation;

- Runtime-only package dependency;
- no public bucket, page, offset, hash, or overflow controls;
- caller-visible resource and overwrite policy only where required; and
- validation and safe destination commit remain outside the low-level image
  builder.

HW00 introduces no production API and does not itself advance the coordinated
version. HW01 owns the Alpha-1 contract and version gate.
