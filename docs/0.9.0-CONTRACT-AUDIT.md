# Icod.TermInfo 0.9.0 Contract Audit

This document records the final T41 repository-side contract audit for the
`Icod.TermInfo` 0.9.0 release.

T40 froze the intended public API, documentation, samples, package shape, and
fresh-package acquisition smoke contract at `0.9.0-rc.1`. T41 sets the
project/package version to final `0.9.0`, adds the final end-to-end and workflow
boundary guards, corrects the release documentation to the main-only publication
contract, and records the evidence map below.

This document does **not** claim that the final T41 commit has already passed the
`main` Release/package/publication workflow. The final source candidate is ready
for that validation. Tag `v0.9.0` only after the exact final `main` commit passes
the complete Windows/Linux/macOS Release matrix and package-validation job. No
source/package content may change between that successful validation and tagging.

## Completion verdict

The two T41 completion questions are answered **yes** by the repository contract.

> Can a caller hand `Icod.TermInfo` any valid compiled entry in the supported
> frozen System V/ncurses family and obtain the same complete immutable semantic
> shape that 0.8 could construct manually?

**Yes.**

The supported binary family is represented by one shared pure parser and is
covered by the checked-in T29 fixtures plus T33-T35 parser suites:

- legacy `0432`;
- ncurses extended Boolean/numeric/string sections;
- `01036` signed-32-bit numerics;
- canonical names, aliases, and descriptions;
- standard capability mapping by frozen binary index;
- exact case-sensitive extended names;
- absent/canceled states;
- exact Latin-1 high-byte string data;
- bounded malformed/truncated/overflow handling.

> Can a caller explicitly ask `Icod.TermInfo` to find such an entry through a
> configured directory/system search without introducing hidden global state or
> terminal-specific C# code?

**Yes.**

T36-T39 establish caller-owned acquisition:

```text
caller-supplied bytes
    -> CompiledTermInfoParser

caller-owned directory
    -> DirectoryTerminalDescriptionProvider
    -> CompiledTermInfoParser

caller-owned system provider
    -> snapshotted TERMINFO / user / TERMINFO_DIRS / platform roots
    -> DirectoryTerminalDescriptionProvider / encoded bytes
    -> CompiledTermInfoParser
```

Successful arbitrary external descriptions are cached only by caller-owned
provider instances. Clean misses and failures remain retryable. Constructing a
new provider is the deterministic refresh mechanism. `TerminalDatabase.BuiltIn`
remains immutable and can be composed explicitly after the system provider.

`T41CompletionGateTests.SupportedCompiledEntryFlowsThroughParserProvidersAndBuiltInFallback`
replays that complete chain from compiled bytes through the parser, explicit
directory provider, system provider, and built-in fallback while verifying that
the external description never leaks into `TerminalDatabase.BuiltIn`.

## Final public contract

The T40 public API freeze remains unchanged in T41.

0.9 adds these acquisition-facing exported types:

```text
CompiledTermInfoFormatException
CompiledTermInfoParserOptions
CompiledTermInfoParser
DirectoryTerminalDescriptionProvider
SystemTerminalDescriptionProviderOptions
SystemTerminalDescriptionProvider
```

T39 additionally made the existing `TerminalDatabase` implement
`ITerminalDescriptionProvider` so databases can participate directly in explicit
first-provider-wins composition.

No public filesystem watcher, cache-clear API, mutable global provider registry,
process-global current terminal, native ncurses handle, or source-level terminfo
model is added.

`PublicApiSurfaceTests` and `T40ApiPackageFreezeTests` remain the exact API
surface and nullability/ownership freeze.

## Final workflow boundary

Publication is intentionally asymmetric.

### Pull requests

`.github/workflows/pr-build-and-test.yaml`:

```text
pull_request
    -> Staging clean/restore/build/test
    -> Windows / Ubuntu / macOS
    -> no pack
    -> no publication credentials
    -> no deployment
    -> no package publication
```

A pull request is validation work only.

### Main

`.github/workflows/push-main.yaml`:

```text
push to main
    -> Release clean/restore/build/test
    -> Windows / Ubuntu / macOS
    -> package validation
    -> exact package artifact upload
    -> Release deployment
    -> NuGet.org + GitHub Packages
```

No development or release branch is an additional publication trigger.

`T41CompletionGateTests.ReleaseWorkflowBoundaryIsFrozen` exists specifically to
make a future accidental broadening of this boundary fail the test suite.

## Package and artifact boundary

The final 0.9 package remains managed and dependency-free.

The package verifier rejects:

- unexpected runtime DLLs;
- native library payloads;
- `runtimes/` payloads;
- runtime NuGet dependencies;
- repository-only test/tool content;
- compiled fixture `.bin` files;
- fixture/source `.ti` files;
- missing portable symbols/Source Link repository metadata.

The fresh package consumer creates a valid legacy compiled entry at runtime. It
does not copy the repository fixture corpus into the consumer. It proves that
the packed package itself can parse bytes, load an explicit conventional tree,
construct restricted and normal system providers, and compose system lookup with
built-in fallback.

## Final T41 strengthening

T41 intentionally makes no production acquisition redesign.

It adds three final completion assertions:

1. the assembly identifies final `0.9.0`, not an RC/prerelease;
2. one supported compiled entry completes the parser -> explicit directory ->
   system provider -> built-in fallback chain without mutating the built-ins;
3. the publication workflow boundary is frozen so only `main` can publish and
   pull-request validation can never publish.

The stale T40 RC-version assertion is removed rather than rewritten; historical
tranche tests continue to assert behavior/API contracts rather than pretending
the assembly remains at an old prerelease version.

## Final release sign-off

After the T41 patch is committed, the repository is a **final 0.9.0 source
candidate**.

The intended release sequence is:

1. apply T41 on a working branch and run local build/test/package verification;
2. open the pull request to `main`; require `pr-build-and-test.yaml` to pass on
   Windows, Ubuntu, and macOS; this PR validation must not publish anything;
3. merge the exact reviewed T41 candidate to `main`;
4. require the `push-main.yaml` Release matrix and package-validation job for
   that exact `main` commit to pass;
5. allow the downstream Release deployment to publish the validated package
   artifacts from that exact `main` commit;
6. tag that exact successful `main` commit `v0.9.0`;
7. confirm `Icod.TermInfo` 0.9.0 and symbols are visible at the intended package
   feeds and a genuinely fresh consumer can restore the public version.

If any source or package content changes after successful validation, the T41
completion gate must be rerun before the replacement commit is considered the
final 0.9.0 release commit.

## Post-0.9

With T41 complete, the core low-level 0.9 acquisition promise is closed.

The next work is an explicit 1.0 readiness review rather than automatic
expansion of `Icod.TermInfo` into session ownership, PTYs, curses, source
compilers, graphics protocols, or terminal emulation. Those families remain in
`docs/FUTURE-WORK-INVENTORY.md`.
