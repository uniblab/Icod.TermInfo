## Composition API

RB05 adds exactly one reviewed public constructor to the RB01-added `RasterBackendCandidate` type:

```csharp
public RasterBackendCandidate(
    RasterBackendProfile backendProfile,
    PersistentRasterRuntimeIntegrationResult integration

```

The constructor requires both arguments, retains the supplied backend profile unchanged, and takes the exact `LifecycleProfile` and `PlacementProfile` references already retained by the frozen 1.13 integration result.

## Trust and orchestration boundary

The composition constructor deliberately performs no semantic work beyond packaging existing profiles. It does not:

- re-integrate runtime observations;
- manufacture or reclassify evidence;
- assign source ordinals;
- inspect inconclusive observations;
- infer backend availability from lifecycle or placement observations;
- require `PersistentRasterRuntimeIntegrationResult.Succeeded` to be true; or
- merge runtime contexts belonging to different backends.

A failed or partially successful integration result can therefore still be packaged. The candidate receives exactly the profiles represented by that integration result, including any unchanged family preserved by 1.13 after an integration limitation. Backend availability remains the separately supplied `RasterBackendProfile`.

Consumers verifying multiple backends continue to maintain separate 1.13 integration contexts. The new constructor only removes the final manual extraction of each context's lifecycle and placement profiles.

## Behavioral equivalence

Tests prove that constructing a candidate from `(backendProfile, integration)` is behaviorally equivalent to constructing it manually from `(backendProfile, integration.LifecycleProfile, integration.PlacementProfile)`. Existing `RasterBackendPlanner.Evaluate(...)` and `Plan(...)` outputs therefore remain authoritative and unchanged.
