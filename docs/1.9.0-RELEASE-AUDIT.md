## Rendering and evidence contract

Rendering is an explicit projection of existing immutable values. It does not
create a second semantic model. Fixed property and item order, ordinal strings,
typed capability values, comparison source evidence, exact generated source,
selected parents, score components, plan completeness, catalog issues,
duplicate names, and catalog completeness are stable version-1 meanings.

Compact and indented forms are deterministic across supported frameworks,
processes, cultures, and hosts. Maximum size is measured in UTF-8 bytes.
Requests over the bound fail without a successful truncated document.
Cancellation is observed at deterministic boundaries and returns no partial
success.

## Command contract

The stable machine-readable command forms are:

```text
infocmp --json target
infocmp --json -d left right
infocmp --json --plan-use target candidate [candidate ...]
infocmp --json --plan-use --all-candidates -B directory target
toe --json directory
```

Successful stdout is exactly one JSON document and one LF. Diagnostics remain
on stderr. All-candidates planning requires one explicit database root and does
not perform implicit host-wide discovery. Existing human-readable commands and
all frozen 1.7 synthesis and 1.8 planning semantics remain unchanged.

## Package-consumer and sample evidence

Isolated consumers restore produced packages from an isolated NuGet source and
execute on every supported reusable TFM. The Inspection consumer requires the
exact 31-type inventory and renders, parses, and checks all four version-1
documents. It also covers cultures, pathological text, large text, and exact
UTF-8 bounds.

The deterministic Toolchain sample plans, synthesizes, resolves, compiles,
publishes, reacquires, compares, and renders source-plan JSON using controlled
fixtures. The release verifier runs it twice in separate processes and requires
byte-identical output equal to the checked-in fixture. ToolSuite documents direct
and routed automation without depending on a host terminfo database.

## Release gate

Before stable tagging, the exact intended release commit must pass:

1. clean restore, build, and test on Windows, Linux, and macOS;
2. every frozen public API baseline and cross-framework API comparison;
3. exact version-1 schema and package inclusion checks;
4. package and symbol structural verification for all six packages;
5. isolated consumer execution on every supported reusable TFM;
6. deterministic Toolchain fixture and separate-process byte equality;
7. direct, routed, installed-tool, and matching-archive JSON smoke;
8. structural checks for all six archives and the checksum manifest; and
9. coordinated `1.9.0-Alpha-7` version and unchanged `1.0.0.0` assembly identity.

After those gates pass, the repository owner may perform the version-only
transition to `1.9.0`, merge the exact release commit to `main`, tag that exact
commit `v1.9.0`, and publish. The stable commit and tag fields above must then be
updated with exact owner publication evidence.
