# Icod.TermInfo 1.11.0 Persistent Raster Lifecycle Guide

## Purpose

`Icod.TermInfo.Inspection` 1.11 adds a protocol-neutral way to describe, classify, and plan persistent-raster lifecycle behavior without turning TermInfo into a live terminal-session library.

The central question is:

> What persistent-raster lifecycle semantics does this terminal description claim or imply, what evidence supports that conclusion, and what semantic operations can a consumer safely plan?

The answer remains advisory. A sibling runtime such as `Icod.Terminal` still owns live verification, protocol transmission, resource and placement identities, lifecycle invalidation, acknowledgements, and cleanup execution.

## Ownership boundary

```text
Icod.TermInfo
    evidence
    provenance
    classification
    uncertainty / contradiction
    semantic planning
    machine-readable inspection

Icod.Terminal
    live verification
    protocol execution
    resource identity
    placement identity
    lifecycle-generation invalidation
    terminal-side cleanup

Icod.DCurses
    layout
    virtual-screen policy
    scene/application state
```

TermInfo therefore exposes no Kitty image number, image ID, placement ID, raw APC/Sixel payload, coordinate system, resource registry, acknowledgement reader, or disposal handle.

## Evidence subjects

Persistent lifecycle evidence is classified against eight semantic subjects:

```text
RasterDisplay
PersistentUpload
AcknowledgedUpload
PlacementCreation
MultiplePlacements
PlacementUpdate
PlacementDeletion
ResourceDeletion
```

These are deliberately separate from the six semantic plan operations. In particular, acknowledgement and multiple-placement support are capabilities which influence planning but are not themselves terminal operations.

## Evidence values and provenance

`PersistentRasterLifecycleEvidence` is immutable and records:

- the semantic subject;
- positive or negative polarity;
- evidence kind;
- source label; and
- deterministic source ordinal.

Evidence kinds have an explicit precedence:

```text
Verified
    >
Declared
    >
CapabilityDerived
```

`Verified` is intended for facts a caller has established through its own trusted mechanism, including live terminal verification performed outside TermInfo. `Declared` represents explicit caller-supplied semantic declarations. `CapabilityDerived` represents recognized description-derived evidence.

Lower-precedence evidence is never discarded from the canonical evidence snapshot merely because a higher-precedence fact determines the classified state.

## Four support states

Each lifecycle subject classifies to exactly one of:

```text
Unknown
Supported
Unsupported
Contradicted
```

`Unknown` means the available evidence does not establish either support or non-support. Static absence is not automatically `Unsupported`.

`Supported` means the highest-precedence present evidence is conclusively positive.

`Unsupported` means the highest-precedence present evidence is conclusively negative.

`Contradicted` means positive and negative evidence coexist at the highest present precedence tier. Contradiction remains visible rather than being silently resolved by ordering.

## Inspecting a terminal description

`PersistentRasterLifecycleInspector.Inspect(...)` derives recognized semantic evidence from an immutable `TerminalDescription` and returns a classified profile.

The recognized static declarations are explicit Icod extended Boolean capabilities. Ordinary raster evidence such as Sixel support does **not** imply persistent upload or placement semantics.

For example, a description which only identifies ordinary Sixel capability remains `Unknown` for persistent upload and placement creation. A persistent request made from that profile is therefore indeterminate and requires caller-owned verification.

## Database-set inspection

The database-set overload consumes the already-frozen 1.10 `TermInfoDatabaseSet` lookup model. It does not implement a second precedence algorithm.

The inspection result retains:

- the original ordered database set;
- the exact canonical-name lookup result;
- a lifecycle profile for every observed occurrence in occurrence order; and
- an effective profile only when 1.10 lookup semantics identify a conclusive winner.

An earlier incomplete root which makes the lookup indeterminate prevents a later occurrence from being promoted to effective truth. Shadowed descriptions remain inspectable as evidence.

## Requests and semantic plans

`PersistentRasterLifecycleRequest` expresses bounded consumer intent without protocol identifiers. Requests can ask for:

- one-shot ephemeral display;
- persistent resource upload;
- acknowledged upload;
- one or more placements;
- placement update;
- placement deletion; and
- resource deletion.

The planner emits ordered semantic operations from this vocabulary:

```text
DisplayEphemeral
UploadResource
CreatePlacement
UpdatePlacement
DeletePlacement
DeleteResource
```

A `PersistentRasterLifecyclePlan` has one of three statuses:

```text
Success
Indeterminate
Impossible
```

A successful plan has enough semantic support evidence for its requested operations.

An indeterminate plan contains operations whose requirements are unknown or contradicted and therefore identifies runtime-verification requirements explicitly.

An impossible plan identifies requirements classified as unsupported.

The plan never allocates resource IDs or placement IDs and never performs terminal I/O.

## Strengthening static knowledge with live verification

A typical runtime integration is:

```text
TerminalDescription
    -> Inspect
    -> static profile
    -> Plan
    -> Indeterminate
    -> consumer performs live verification
    -> append Verified evidence
    -> Classify
    -> Plan again
    -> Success or Impossible
    -> consumer executes through its own terminal runtime
```

The checked-in `samples/Icod.TermInfo.PersistentRasterLifecycle.Sample` demonstrates this exact transition without performing terminal I/O itself.

## Machine-readable automation

Lifecycle profiles and plans use the additive version-3 JSON contract:

```text
schema:        urn:icod:terminfo:inspection:json:3
schemaVersion: 3
```

Document kinds are:

```text
persistentRasterLifecycleProfile
persistentRasterLifecyclePlan
```

Profile documents contain all eight states and the complete canonical evidence snapshot. Plan documents contain plan status, ordered steps, structured issues, and runtime-verification requirements.

The schema is `docs/Icod.TermInfo.Inspection.schema.v3.json`. Version-1 and version-2 JSON contracts remain unchanged.

## Determinism and bounds

Evidence snapshotting, request placement counts, planner results, and JSON output are bounded. Ordering is ordinal and culture-independent. Repeating classification, planning, or rendering with equivalent inputs produces equivalent results.

The renderer reuses `TermInfoJsonRendererOptions` and its existing UTF-8 output bound and cancellation behavior.

## Package boundary

A consumer needs only the `Icod.TermInfo.Inspection` package directly. RL07 permanently validates a fresh NuGet-only consumer on `net8.0`, `net9.0`, and `net10.0`.

There is no `Icod.TermInfo` production dependency on `Icod.Terminal`. The package graph remains:

```text
Icod.TermInfo.Inspection
    -> Icod.TermInfo.Source
    -> Icod.TermInfo
```

with Inspection also directly depending on matching Runtime as before.

## Mapping to Icod.Terminal

A Terminal consumer can map semantic requirements onto its own persistent-raster resource and placement APIs. The intended direction is:

```text
Icod.TermInfo lifecycle profile / plan
        |
        v
consumer-owned verification
        |
        v
Icod.Terminal resource creation
        |
        v
Icod.Terminal placement creation/update/disposal
        |
        v
Icod.Terminal resource disposal
```

TermInfo does not require those runtime APIs to exist and does not import their identities. This loose coupling is the central 1.11 architectural guarantee.
