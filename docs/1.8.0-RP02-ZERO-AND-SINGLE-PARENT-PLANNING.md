# Icod.TermInfo 1.8.0 RP02 - Zero- and Single-Parent Planning

**Development version:** `1.8.0-Alpha-2`

**Input baseline:** `1.8.0` branch commit
`3c7d2c8ff42084222cf66f87ee657bed6c022dff` (`RP01`)

## Scope

RP02 implements the first complete operational search behind
`TerminalDescriptionSourcePlanner`. It evaluates:

1. the zero-parent effective-source baseline; and
2. every legal single candidate position in caller order.

Candidate acquisition, snapshot limits, ordinal self-reference exclusion,
immutable result types, and the lexicographic score remain the RP01 contract.
The public API surface is unchanged.

## Search semantics

The planner snapshots the candidate sequence once before search. When
`MaximumSelectedParentCount` is zero, only the zero-parent baseline is legal.
Otherwise RP02's legal domain contains the baseline and one plan for each
snapshotted candidate position. Equivalent candidate descriptions and repeated
reference identities remain distinct positions and are each evaluated once.

The default selected-parent limit remains two because it is the cumulative 1.8
policy frozen by RP01. RP02 implements search depth zero and one; RP03 adds the
ordered multi-parent portion of that policy. When an accepted snapshot contains
two or more positions and the selected-parent limit exceeds one, the request
already admits ordered multi-parent plans. RP02 rejects that request with
`InvalidOperationException` and directs the caller to configure a limit of one.
It does not misreport a partial domain as exhaustive. Zero- and one-candidate
snapshots remain exhaustive under the default policy because no distinct ordered
pair is legal.

`IsExhaustive` retains its RP01 meaning: every legal plan within the accepted
candidate snapshot and selected-parent limit was evaluated.

Before evaluation, the planner computes the number of plans needed for exhaustive
RP02 search. If that count exceeds `MaximumEvaluatedPlanCount` and
`AllowNonExhaustiveResult` is false, planning fails with
`InvalidOperationException`. With explicit non-exhaustive opt-in, evaluation
stops at the budget and returns the best valid plan found with
`IsExhaustive == false`.

Each attempted baseline or candidate increments `EvaluatedPlanCount`, including
plans rejected as unrepresentable or too long. If no evaluated plan is valid,
planning fails with `InvalidOperationException`; it never returns an approximate
description.

## Frozen score evidence

RP02 preserves the RP01 lexicographic score order:

1. local directive count;
2. cancellation count;
3. selected parent count;
4. rendered UTF-8 byte count without a byte-order mark; and
5. selected candidate-index sequence.

Source generation is still delegated to the frozen 1.7 synthesizer. An internal
synthesis result now carries the source plus local-directive and cancellation
counts collected at the renderer's semantic emission points. The public
`TerminalDescriptionSourceSynthesizer.Synthesize` and `Write` contracts are
unchanged. Production planning does not reparse generated source or command
output to compute a score.

The zero-parent local count is the number of effective standard and extended
capabilities rendered for the target, with zero cancellations. Relative counts
increment exactly when standard or extended local value/cancellation fields are
emitted. Identity header components and `use=` references are not local
directives.

## Selection and validity

Every plan uses `TerminalDescriptionSourceSynthesizer` with the exact active
synthesis options. `InvalidOperationException` from a semantically
unrepresentable synthesis candidate rejects only that candidate. A generated
source longer than `MaximumGeneratedSourceLength` is likewise rejected.

The smallest valid score wins. Candidate indices provide deterministic tie
resolution after all semantic and size components. The winning
`TerminalDescriptionSourceSynthesisParent` instance and its exact `UseName`
spelling are retained in `SelectedParents` and the emitted source.

Cancellation is observed before snapshot, during snapshot, before each plan,
and after the bounded evaluation loop.

## Independent validation

Focused RP02 tests enumerate the same zero/single domain independently through
the public 1.7 synthesizer. The oracle parses each generated source with
`Icod.TermInfo.Source`, counts local fields and cancellations from the unresolved
source model, computes UTF-8 length, applies the frozen public score, and compares
its winner with the planner.

The matrix covers standard capabilities, extended capabilities, inherited
cancellations, candidates which do not improve the baseline, invalid synthesis
plans, generated-source limits, exhaustive and opt-in partial budgets, ordinal
candidate ties, exact alias spelling, culture changes, candidate reordering,
repeated calls, and semantic resolution round trips. The multi-target Inspection
test project applies the same contract to `net8.0`, `net9.0`, and `net10.0`.

## Compatibility and package boundaries

- Runtime, Source, Compiler, and Termcap public APIs remain frozen.
- Inspection adds no public type or member beyond the RP01 surface.
- Inspection production dependencies remain Runtime and Source only.
- All reusable assembly versions remain `1.0.0.0`.
- Router dispatch, command behavior, package topology, and archive topology are
  unchanged.
- The coordinated package and command version is `1.8.0-Alpha-2`.

## RP02 gate

RP02 is complete when repository validation proves that every zero- and
single-parent result matches the independent oracle, valid winners round-trip
semantically, exact references and evidence are retained, deterministic behavior
holds across supported target frameworks, and the coordinated Alpha-2 package
and command gates pass.
