# Icod.TermInfo 1.14.0 Raster Backend Selection Guide

## Scope

Icod.TermInfo 1.14 adds an advisory, protocol-neutral raster-backend selection layer to `Icod.TermInfo.Inspection`. The first concrete backend identities are **Sixel** and **Kitty Graphics**. Inspection classifies evidence and plans; it does not transmit graphics, probe a live terminal, allocate terminal-side resource identities, or execute either protocol.

Backend availability is deliberately separate from the frozen persistent-raster lifecycle and placement contracts. A backend can be available while a requested lifecycle or placement operation remains unsupported or unverified.

## Evidence and static inspection

`RasterBackendEvidence` carries a backend identity, polarity, provenance kind, source label, and source-local ordinal. Classification uses `Verified > Declared > CapabilityDerived` precedence. At the highest precedence present, positive-only evidence means supported, negative-only means unsupported, both polarities mean contradicted, and no evidence means unknown.

Static inspection is conservative. An exact Boolean `Sixel` extended capability is positive capability-derived evidence for Sixel. Absence does not prove Sixel unsupported. Kitty Graphics is never inferred from terminal names, emulator brands, xterm identity, Windows Terminal identity, Sixel metadata, or unrelated capabilities.

## Candidate evaluation

A `RasterBackendCandidate` composes three independent snapshots: backend availability, the existing lifecycle profile, and the existing placement profile. `RasterBackendPlanner.Evaluate` delegates lifecycle and placement semantics to the frozen 1.11 and 1.12 planners.

- backend unsupported => candidate impossible;
- backend unknown or contradicted => `RequiresRuntimeVerification`;
- supported backend plus impossible semantic plan => impossible;
- supported backend plus indeterminate or verification-required semantic plan => `RequiresRuntimeVerification`;
- supported backend plus satisfied requested semantics => satisfied.

The actual lifecycle and placement plans are retained for auditability.

## Selection policy

Preference is caller policy, never hidden library ranking.

With no explicit preference order, all impossible candidates yield impossible; exactly one non-impossible candidate can be reflected directly; and more than one viable candidate yields `RequiresPreference`. Candidate input order and backend enum numeric order never choose a winner.

With a complete explicit preference order, impossible candidates are skipped. The first satisfied preferred candidate is selected. A preferred candidate that still needs runtime verification stops fallback and yields `RequiresRuntimeVerification`; the planner does not silently pass it to select a lower-ranked backend. This makes the preference order an explicit fallback policy rather than a hint.

## Runtime verification composition

The 1.13 runtime observation and integration model remains backend-neutral and unchanged. A caller that verifies multiple backends maintains a separate integration context for each backend, converts its observations through `PersistentRasterRuntimeEvidenceIntegrator`, and composes the strengthened lifecycle and placement profiles into that backend's candidate before replanning.

RB07 qualifies this boundary against published **Icod.Terminal 1.13.0** on `net8.0`, `net9.0`, and `net10.0`. Mapping `Icod.Terminal` capability results to backend evidence remains caller-owned; production Inspection still has no Terminal dependency.

## Machine-readable audit output

**JSON v6** adds two deterministic bounded documents:

```text
rasterBackendProfile
rasterBackendSelectionPlan
```

Earlier JSON versions remain frozen. Selection-plan output retains the semantic request, explicit preference order, canonical candidate evaluations, overall status, selected backend only when selected, and the remaining blocker for non-selected outcomes.

## Recommended flow

1. Build or inspect backend availability evidence.
2. Keep lifecycle and placement evidence independent of backend identity.
3. Compose one candidate per backend.
4. Call `RasterBackendPlanner.Plan` with no preference to discover whether a choice is required, or provide a complete explicit preference order when policy is already known.
5. If the result is `RequiresRuntimeVerification`, perform live verification outside TermInfo, integrate the observations into the corresponding backend context, compose a strengthened candidate, and plan again.
6. Execute the selected graphics protocol outside TermInfo.

## Deliberate exclusions

1.14 does not add graphics transport, image codecs, terminal-brand heuristics, alpha/pixel-format planning, performance scoring, latency ranking, scene/layout policy, terminal-side image/resource identity management, animation, or generic JSON deserialization.
