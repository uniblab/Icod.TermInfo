# 1.16.0 HW07 — Writer hardening

**Status:** Implemented; exact-head normal and native qualification pending.
**Coordinated version:** `1.16.0-Alpha-7`.

## Resource audit and correction

The writer previously materialized its entire source sequence before checking
`MaximumRecordCount`. That contradicted the bounded enumeration promised by
HW01. It also allocated and validated alias identities before checking their
physical record cost.

The writer now consumes the record budget during its single source enumeration,
before retaining each entry, and before preparing that entry's identities.
Each entry costs one storage record, one canonical redirect, and one redirect
per alias. The first over-budget entry causes failure; the enumerator is disposed
and filesystem publication has not started. Exact-budget input still succeeds.
Enumeration failure and cancellation preserve an existing destination. A
redundant payload clone was removed because `Entry.Data` already returns a copy.

The four initial regression cases failed against the previous implementation
and passed with the correction. Additional cases cover exact limits, aliases,
enumerator disposal, cancellation, and preservation of existing bytes.

`MaximumDatabaseSize` bounds the output image, not total managed heap usage.
Caller-owned entry construction, a blocked caller enumerator, and allocations
inside caller code remain outside the writer's control. Parser limits and the
physical record limit retain their distinct purposes; this change introduces no
new public API or stronger total-memory guarantee.

## Expanded interoperability matrix

- Four fixed seeds produce 96 records each: exact full-hash collisions,
  chained buckets, long keys, empty values, and values around inline/overflow
  boundaries through 9,000 bytes. Native Berkeley DB verifies, dumps, reloads,
  and dumps each database again. Every key/value pair is compared with the
  generated source records, independent of physical record order.
- Pinned native ncurses compiles `vt100`, `linux`, `xterm`, `xterm-256color`,
  `screen`, `screen-256color`, `tmux`, and `tmux-256color`. The managed public
  writer republishes those compiled payloads. Native Berkeley DB and hashed
  ncurses retrieve every canonical and alias key with unchanged payloads.
- Non-ASCII publications exercise exact UTF-8 keys, distinct case, and absence
  of manufactured Latin-1 or normalized aliases. Compiled names retain the
  existing compiled-format encoding; lookup keys are UTF-8.
- Windows, Linux, and macOS reconstruct the generated databases byte-for-byte,
  read all original and native-reloaded raw records, and reconstruct the
  representative and non-ASCII public catalogs from their payload manifests.

The normal PR workflow also builds the complete solution in Release with
warnings as errors on all three hosts, alongside its existing Staging gates.
The shared matrix source participates in native workflow change classification.

## Security and failure-boundary audit

| Boundary | Evidence retained or added |
| --- | --- |
| Names, ownership, input mutation | HW01 rejects unsafe portable identities and duplicate ownership, requires parsed identity agreement, and snapshots mutable inputs. HW07 tests exact UTF-8 identities and bounded enumeration. |
| Record/page/output limits | Existing HW02–HW04 checked layout and overflow tests remain active; HW07 adds mixed boundary sizes, insufficient output budgets, and exact-image-budget reconstruction. |
| Cooperative writers and readers | HW05 thread/process contention, killed-holder recovery, independent destinations, and concurrent-reader tests remain active on every host. |
| Filesystem mutation | HW05 rejects unsafe immediate paths and links, protects create-new collisions, and verifies staged bytes and catalog before commit. |
| Cancellation | HW05 tests pre-commit stages and post-commit success semantics; HW07 adds cancellation during source enumeration. |
| Disk and permission failures | HW05 fault injection covers write/flush/close/reopen/read/verify/rename/cleanup failures and permission denial. The Windows read-only destination case exercises a real OS restriction. Disk-full coverage is injected, not a claim of physically filling a CI disk. |
| Package isolation | Existing package/API/IL-only/dependency checks and isolated consumers remain required; native Berkeley DB and ncurses are qualification tools, never shipped dependencies. |

The accepted HW05 filesystem scope remains unchanged: cooperative writers,
supported local filesystems, no hostile ancestor replacement guarantee, no
coordination with arbitrary native writers, and no power-loss durability claim.
No migration, merge, catalog automation, or new native runtime dependency is
introduced. Migration and catalog automation remain deferred to 1.17.
