# 0.8.0 T23 — Parameter Program Completion, Analysis, and Hardening

T23 advances the development package to `0.8.0-alpha.3`.

This tranche completes the generic terminfo parameter runtime needed before
0.9 can admit arbitrary compiled terminal descriptions. It does not add
per-description parsed-program caching; that remains T24.

## Conformance result

The pre-T23 engine already implemented the modern stack language needed by the
selected ncurses/System V-compatible baseline:

- `%p1` through `%p9`;
- `%i`;
- `%P` and `%g` dynamic/static variables;
- integer and character constants;
- `%l`;
- arithmetic, bitwise, logical, and comparison operators;
- `%?`, `%t`, `%e`, and `%;` conditionals;
- `%c`, `%s`, `%d`, `%o`, `%x`, and `%X`;
- printf-style flags, width, and precision.

T23 therefore hardens and analyzes that implementation rather than replacing
it.

The compatibility runtime also accepts the common historical tparm formatting form in which
a parameter string with no explicit `%pN` pushes can consume supplied
parameters successively when a formatting conversion needs a value and the
explicit stack is empty. This keeps forms such as `ESC[%d;%dH` usable without
introducing a termcap database parser.

## Immutable internal analysis

Every successfully parsed `TermInfoParameterProgram` now owns immutable
analysis describing:

- parameter indices referenced;
- highest parameter index referenced;
- potential integer/string use for each parameter;
- dynamic variable names used;
- persistent/static variable names used;
- parsed instruction count;
- maximum conditional nesting;
- maximum analyzed stack depth;
- whether implicit formatting compatibility is active;
- whether any analyzed control-flow path can underflow.

The analysis remains internal in T23. T30 can decide whether a durable public
inspection API is justified without freezing parser internals prematurely.

Type information is intentionally conservative across conditional paths. A
parameter may be classified as both integer and string when different runtime
branches use it differently. Expansion remains path-sensitive: only the
actually executed branch validates the supplied value.

## Resource-safety limits

T23 freezes the following implementation limits:

| Resource | Limit |
| --- | ---: |
| Parameter-program source | 65,536 characters |
| Parsed instructions | 8,192 |
| Conditional nesting | 64 levels |
| Evaluation stack | 1,024 values |
| printf-style field width | 10,000 |
| printf-style precision | 10,000 |
| Expanded output | 1,048,576 characters |

These ceilings are deliberately far above the requirements of conventional
terminal descriptions while bounding work and allocation for future
externally loaded entries.

Parser limits fail with `TermInfoFormatException`. Runtime incompatibility,
stack underflow for the values actually supplied, arithmetic overflow, and
output-limit failure use `TermInfoEvaluationException`.

## Arithmetic behavior

T23 changes integer addition, subtraction, multiplication, `%i`, and the
signed division overflow case from unchecked/wrapping behavior to deterministic
evaluation failure. Division/modulo by zero remain deterministic evaluation
errors. Bitwise operations retain ordinary signed 64-bit behavior.

`TermInfoParameter` remains a signed 64-bit parameter value. This is distinct
from T22's signed 32-bit numeric-capability storage contract.

## Compatibility and boundaries

T23 does not:

- add terminal-name-specific parameter behavior;
- add a native ncurses dependency;
- add a termcap parser;
- add compiled terminfo loading;
- add a global parsed-program cache;
- cache parameter programs on `TerminalDescription`.

T24 owns bounded per-description parsed-program reuse and explicit extended
string expansion.

## Upstream reference

The conformance/hardening audit follows the current ncurses documentation for
`tparm`, `tiparm_s`, and `tiscan_s`, together with the parameterized-string
language documented by `terminfo(5)`. The project keeps deterministic
checked-in tests and has no runtime dependency on host ncurses.
