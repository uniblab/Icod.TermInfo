# Icod.TermInfo 1.8.0 RP04 - Bounded Search, Cancellation, and Evidence

**Development version:** `1.8.0-Alpha-4`
**Roadmap tranche:** RP04
**Implementation base:** `29571e04854062931b4a563836553edb6f4eebf2`

## Purpose

RP04 freezes the operational safety contract for relative-source planning. It
does not add public API. The immutable limits and result evidence introduced by
RP01, the operational planner introduced by RP02, and the ordered search added
by RP03 now have hostile-input, cancellation, allocation, and runtime proof.

## Frozen bounds

One request is constrained by four coordinated limits:

- accepted candidate positions;
- selected ordered parents;
- evaluated plans;
- generated source length in UTF-16 code units.

The options constructor validates every scalar before candidate enumeration. A
candidate sequence is enumerated once, self-references are excluded ordinally,
and the first non-self position beyond the candidate limit terminates the
snapshot with `ArgumentException`.

The parent limit cannot exceed either the candidate limit or the frozen 1.7
synthesis parent limit. The evaluation limit is always positive. Generated
source which exceeds its active limit is rejected as one plan without changing
target semantics.

## Checked plan-space arithmetic

For candidate count `n` and selected-parent depth `d`, the legal plan count is:

```text
1 + P(n, 1) + P(n, 2) + ... + P(n, min(n, d))
```

The planner never constructs or represents that factorial space. It accumulates
permutation counts only while the total remains within the configured evaluation
limit. Division-based preflight proves whether the next multiplication would
cross that limit; the permitted operations then use checked arithmetic. Thus a
request at the supported 256-candidate, 256-parent maxima is
rejected or admitted for bounded evaluation without integer wraparound.

When exhaustive search is required and the plan space exceeds the budget, the
planner throws before source evaluation. When non-exhaustive results are
explicitly permitted, evaluation stops exactly at the budget.

## Deterministic bounded order

RP04 retains the RP03 order without pruning:

1. zero-parent baseline;
2. all single-parent plans in candidate order;
3. all two-parent plans in lexicographic candidate-index order;
4. later depths in the same lexicographic order.

The bounded result is therefore the best plan from one deterministic
lexicographic prefix. It is reproducible across process, framework, culture, and
operating system. No wall-clock deadline, hash iteration, task scheduling, or
heuristic frontier affects selection.

`IsExhaustive` is `true` only when the exact legal plan count fits within the
budget and every one of those plans was evaluated. A bounded prefix always
reports `false` and never claims global optimality.

## Stable cancellation boundaries

The cancellation-token overload observes cancellation at stable cancellation
boundaries:

- before candidate snapshot;
- before each candidate is consumed;
- after snapshot completion;
- before ordered evaluation;
- at each bounded enumeration step;
- before one plan is prepared;
- after its parent sequence is prepared;
- immediately after synthesis returns;
- after enumeration and before result construction.

Synthesis remains the frozen synchronous 1.7 operation. A cancellation request
which arrives during synthesis is observed before the synthesized source can
replace the current best plan.

The planner stores search state only in method-local variables. A result is
constructed only after the final cancellation check and after a valid best plan
exists. Consequently cancellation, bounds rejection, and representation failure
cannot publish a partial plan or mutable internal state.

## Allocation and retained evidence

Enumeration uses one selected-index buffer and one selected-position bitmap
bounded by the validated candidate and parent limits. It does not materialize a
plan list or frontier. During evaluation it retains only the current synthesized
result and the best source and selected parent sequence found so far. Rejected
source is eligible for collection after that evaluation.

The returned immutable evidence remains:

- `SelectedParents` in exact synthesis order;
- `Source`;
- the frozen lexicographic `Score`;
- `EvaluatedPlanCount`, including valid and rejected plans;
- `IsExhaustive`;
- `CandidateCount` after self-reference exclusion.

No additional public evidence type is needed for RP04.

## Verification

RP04 tests prove:

- supported-maximum combinatorial overflow is rejected before synthesis and
  within a conservative allocation ceiling;
- candidate enumeration stops at the first overflowing accepted position;
- a large legal space returns the exact 66-plan lexicographic prefix when
  explicitly budgeted;
- an oversized baseline source can be rejected while a later bounded parented
  representation wins;
- duplicate-reference combinations count as rejected evaluated plans without
  preventing exhaustive completion;
- cancellation scheduled only after candidate snapshot returns no partial plan;
- the complete default 4,097-plan space remains under a generous 30-second CI
  regression guard.

Existing RP02 and RP03 oracle tests continue to prove that exhaustive results
are exact and semantically round-trip to their targets.

## Compatibility result

The public Inspection surface is unchanged from RP01. The frozen 1.7 synthesis
API and semantics are unchanged. Inspection retains only Runtime and Source
production dependencies, and every reusable assembly retains version
`1.0.0.0`.

All coordinated packages and commands advance to `1.8.0-Alpha-4`.
