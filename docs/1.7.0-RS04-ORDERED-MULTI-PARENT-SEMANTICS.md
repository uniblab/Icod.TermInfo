# Icod.TermInfo 1.7.0 RS04 — Ordered Multi-Parent Semantics and Reference Fidelity

**Development version:** `1.7.0-Alpha-4`
**Tranche:** RS04
**Status:** implementation contract
**Previous tranche:** RS03 — Extended Capability Synthesis
**Next tranche:** RS05 — Relative Source Rendering and Semantic Verifier

## Objective

RS04 stress-tests and freezes ordered `use=` composition as an explicit
relative-synthesis contract.

RS01 established ordered parent descriptors. RS02 implemented the standard
capability aggregate. RS03 extended that aggregate to the complete effective
`TerminalDescription` capability universe. RS04 does not introduce another
semantic layer. It proves that the existing engine preserves caller-supplied
parent order and source-reference identity across one or many parents.

The implementation remains owned by `Icod.TermInfo.Inspection`. Runtime, Source,
Compiler, and Termcap public APIs remain unchanged.

## Parent order is semantic input

The exact caller-supplied sequence is preserved.

For:

```text
P1
P2
P3
```

the synthesized source emits:

```text
use=P1,
use=P2,
use=P3,
```

in that order.

The synthesizer does not:

- sort parent names;
- sort parent descriptions;
- reorder parents to reduce local directives;
- remove a parent because it appears redundant;
- canonicalize a caller-supplied reference spelling.

The parent sequence is materialized once by the synthesis plan and is then used
both for aggregate construction and for `use=` emission.

## Ordered aggregate precedence

The aggregate continues to follow the Source precedence contract frozen before
1.7:

```text
parents = empty

for each parent from rightmost to leftmost:
    parents.OverlayHigherPriority(parent)
```

Therefore a present capability contributed by a leftward parent has higher
priority than the same capability contributed by a parent to its right.

For effective parent descriptions this means:

- standard Boolean presence is inherited if any effective parent contributes it;
- for numeric capabilities, the leftmost parent that contains the capability
  supplies the inherited value;
- for string capabilities, the leftmost parent that contains the capability
  supplies the inherited value;
- for an extended ordinal name, the leftmost parent that contains the name
  supplies the complete `TermInfoCapabilityValue`, including value kind.

RS04 fixtures exercise collisions across all four groups and compare the
synthesizer's assumptions with the real Source resolver.

## Effective-state boundary and cancellation provenance

A synthesis parent is an effective `TerminalDescription`.

That distinction matters for absence.

Source resolution can internally retain a cancellation tombstone while merging
unresolved source entries, but `TerminalDescription` intentionally exposes only
effective state. Once a parent has been reduced to a `TerminalDescription`, an
absent capability does not reveal whether its original source:

- never mentioned the capability;
- inherited and later cancelled it;
- reached the same effective absence by another source arrangement.

RS04 therefore freezes the only semantics the reusable input can truthfully
represent:

> absence in a higher-priority effective parent is no contribution; it is not a
> reconstructed cancellation against a lower-priority parent.

The synthesizer does not invent lost parent provenance. When the target itself
must remove capability state inherited from the aggregate, the target-local
delta still emits the required `cap@` cancellation.

## `UseName` is source-reference identity

`TerminalDescriptionSourceSynthesisParent` deliberately carries two identities:

```text
UseName
Description
```

`Description` supplies effective capability semantics.

`UseName` supplies the exact source token emitted after `use=`.

The synthesizer preserves `UseName` verbatim after the validation frozen in
RS01. It does not replace the value with `Description.Name`.

This permits a caller to acquire an effective terminal by canonical identity but
emit an alias intentionally:

```text
Description.Name = xterm-256color
UseName          = xterm-direct-alias
```

The caller remains responsible for supplying a source environment in which the
chosen `UseName` actually resolves to the effective semantics represented by
`Description`. The reusable synthesizer does not perform database lookup or
source discovery.

## Repeated and equivalent parents

The RS01 duplicate-reference policy remains authoritative.

Within one request:

- two identical `UseName` values are rejected under ordinal, case-sensitive
  comparison;
- names differing only by case are distinct;
- the same effective `TerminalDescription` may appear more than once when each
  occurrence has a distinct valid `UseName`;
- semantically equivalent but independently constructed descriptions may also
  appear under distinct references;
- no repeated/equivalent parent is silently removed.

A canonical name and an alias may therefore intentionally reference the same
effective parent twice:

```text
use=base,
use=base-alias,
```

if those are the exact references supplied by the caller.

This policy favors deterministic fidelity to caller intent over parent-set
optimization. Parent reduction or optimization remains outside the 1.7 scope.

## Reference spelling versus canonical identity

RS04 verifies that alias spelling survives synthesis unchanged.

For a parent acquired as:

```text
Description.Name = rs04-parent
Description.Aliases contains rs04-parent-alias
```

a synthesis parent created with:

```text
UseName = rs04-parent-alias
```

must emit:

```text
use=rs04-parent-alias,
```

and must not silently rewrite the field as:

```text
use=rs04-parent,
```

The distinction is presentation-visible and may also matter to callers whose
source trees intentionally use stable aliases.

## Cross-check against Source

RS04 adds an independent resolver cross-check.

The primary multi-parent fixture constructs an ordinary child source entry
containing only:

```text
use=P1,
use=P2,
use=P3,
```

plus full rendered source entries for the effective parents.

That ordinary source is parsed and resolved through:

```text
TermInfoSourceParser
    -> TermInfoSourceResolver
    -> TerminalDescription
```

and compared with the expected target through
`TerminalDescriptionComparer`.

The same target and ordered parent descriptors are then passed through
`TerminalDescriptionSourceSynthesizer`.

When the target exactly equals the inherited parent aggregate, the synthesized
entry must contain no local capability directives and must be byte-identical to
the independently written use-only child entry.

This makes the Source resolver, rather than a duplicate test merge routine, the
oracle for parent precedence.

## Determinism

RS04 extends deterministic evidence across multiple parents.

Equal semantic targets, equal ordered reference lists, and equal effective
parent semantics must produce equal source regardless of:

- capability dictionary insertion order;
- extended dictionary insertion order;
- hash randomization;
- current culture;
- operating system;
- target framework.

The ordered parent list itself is intentionally not normalized. Changing parent
order changes semantic input and may change the inherited aggregate.

## Production implementation

RS04 adds no new public API.

The existing relative renderer remains the implementation point. The code now
documents two ordering invariants directly beside the operations that implement
them:

1. aggregate construction traverses effective parents from right to left;
2. `use=` fields are emitted from the materialized parent list from left to
   right without reordering or pruning.

The public parent descriptor documentation also records that `UseName` may be an
alias and may differ from `Description.Name`.

## Package smoke

The Inspection package smoke extends its synthesis coverage by supplying the
same effective parent twice under its canonical name and an alias.

The smoke requires both `use=` fields to survive in exact caller order. This
guards the packaged public surface against an implementation that later starts
canonicalizing or deduplicating parent references.

## RS04 gate

RS04 is complete when:

- the coordinated development version is `1.7.0-Alpha-4`;
- one-parent behavior remains correct;
- three-parent Source-backed precedence agrees with synthesis across standard
  Boolean, numeric, string, and extended capabilities;
- exact caller `use=` order is preserved;
- alias-spelled `UseName` values are not canonicalized;
- the same effective parent may be repeated under distinct valid references;
- ordinal case-distinct reference names remain distinct;
- capability insertion order does not affect multi-parent output;
- duplicate `UseName` rejection from RS01 remains intact;
- no parent is reordered or removed as an optimization;
- package smoke exercises repeated canonical/alias references;
- Runtime, Source, Compiler, and Termcap frozen contracts remain intact;
- Inspection retains its existing production dependency boundary.

RS05 may then finalize relative rendering and make the semantic verifier a
permanent release-quality regression gate without revisiting the ordered-parent
contract.
