# Icod.TermInfo 1.15.0 — Berkeley DB Ecosystem and Dependency Audit

## Status

This document records the dependency/ecosystem review performed before
productionizing the HDB02 managed Berkeley DB Hash-v9 reader.

It complements:

- `Icod.TermInfo-1.15.0-Berkeley-DB-Hashed-Terminfo-Acquisition-Roadmap.md`; and
- `docs/1.15.0-HDB00-BERKELEY-DB-INTEROPERABILITY-AND-BACKEND-DECISION.md`.

The conclusion is an engineering/dependency decision, not legal advice.

## Executive conclusion

No reviewed NuGet package or existing modern .NET implementation is a better
production dependency for Icod.TermInfo 1.15 than the narrowly scoped managed
read-only reader selected by HDB00.

The available .NET/NuGet options fall into two categories:

1. old .NET Framework wrappers around native Berkeley DB; or
2. old native Berkeley DB binary/header packages with no modern managed API.

Neither provides the maintained, pure-managed, cross-platform
`net8.0`/`net9.0`/`net10.0` contract required by this repository.

Accordingly, production 1.15 remains:

```text
Icod.TermInfo.BerkeleyDb
        |
        +-- pure managed
        +-- read only
        +-- Berkeley DB Hash on-disk format v9 subset only
        +-- no native Berkeley DB runtime
        +-- no third-party database package dependency
        |
        v
compiled terminfo bytes
        |
        v
existing Icod.TermInfo parser
```

Native Berkeley DB remains an interoperability oracle/fixture producer in the
HDB workflow only.

## 1. Requirements used to judge alternatives

A production dependency would need to satisfy substantially all of these
requirements:

- active or credibly maintained implementation;
- modern .NET support suitable for `net8.0`, `net9.0`, and `net10.0`;
- Windows, Linux, and macOS support;
- no assumption that a system Berkeley DB shared library is installed;
- no fragile unmanaged ABI discovery;
- no need to bundle RID-specific Berkeley DB binaries;
- read-only support for the Berkeley DB Hash on-disk representation used by
  ncurses hashed terminfo;
- support for off-page/overflow values used by legal compiled terminfo entries;
- deterministic failure behavior on malformed or unsupported containers;
- acceptable licensing/distribution characteristics for a reusable NuGet
  library;
- a scope no broader than necessary for terminfo acquisition; and
- enough testability to keep the existing 12-job package/tool qualification
  matrix authoritative.

A dependency which merely exposes Berkeley DB through P/Invoke does not satisfy
these requirements by itself.

The existence of old packages therefore does not justify making one of them a
runtime dependency.

## 3. Upstream Berkeley DB format authority

Berkeley DB's own source remains the strongest technical authority for the
on-disk page structures used by the HDB00 managed probe and planned HDB02 reader.

The upstream page definitions document, among other things:

- metadata magic/version/page-size placement;
- `P_OVERFLOW == 7`;
- `P_HASHMETA == 8`;
- `P_HASH == 13`;
- the 26-byte ordinary page header;
- paired key/data indices on Hash pages;
- `H_KEYDATA == 1`;
- `H_OFFPAGE == 3`;
- overflow page chaining through `next_pgno`; and
- overflow data length through the page header's high-free-offset field.

These definitions correspond to the structures independently exercised by HDB00.

Useful upstream/archive references:

- <https://github.com/berkeleydb/libdb>
- `src/dbinc/db_page.h` in Berkeley DB source trees.

The production implementation must rely on reviewed format constants/structures,
not copied Berkeley DB implementation code.

## 4. ncurses requirements

The ncurses build documentation explicitly supports hashed terminfo databases via
`--with-hashed-db` and describes Berkeley DB as the storage engine used for that
configuration.

The HDB00 experiment is stronger than documentation alone because it built
ncurses in both conventional-directory and hashed modes from the same pinned
source, then compared the resulting logical entry bytes.

For Icod.TermInfo, the required contract is not "implement Berkeley DB". It is:

```text
ncurses Hash store
       |
       v
exact key/value recovery
       |
       v
ncurses record envelope
       |
       v
compiled terminfo bytes
```

The observed ncurses record envelope relevant to acquisition is:

```text
marker 2 -> index/alias target key
marker 0 -> compiled terminfo payload
```

The package does not need Berkeley DB transactions, recovery, writing, hash-table
expansion, environments, or general application database features to satisfy
this contract.

Reference:

- <https://github.com/mirror/ncurses/blob/master/INSTALL>

## 5. Other-language precedent

A useful architectural precedent is the Rust `db185` project, which implements a
narrow Berkeley DB 1.85 reader/writer for a specific package-database use case
rather than binding the full native database engine.

It is not directly reusable for 1.15 because:

- it targets the Berkeley DB 1.85 Btree format;
- its README explicitly lists Hash and Recno as out of scope; and
- introducing Rust/native FFI would defeat our pure-managed deployment goal.

It nevertheless supports the architectural principle that a constrained consumer
can reasonably implement only the on-disk subset it needs.

Reference:

- <https://github.com/jperkin/db185>

No reviewed C#/.NET project surfaced that offers the needed modern managed
Hash-v9 reader with stronger maintenance, compatibility, or test evidence than
the HDB00 direction.

## 6. Licensing and distribution considerations

Licensing is not the sole reason for the managed-reader decision, but it
strengthens the choice to avoid runtime linkage or redistribution when linkage is
unnecessary.

Oracle documents that:

- Berkeley DB releases beginning with 6.0 moved to AGPLv3 for the open-source
  distribution;
- earlier releases continue under the Sleepycat license; and
- Oracle offers commercial licensing as an alternative distribution model.

References:

- <https://docs.oracle.com/database/bdb181/html/installation/license_change60.html>
- <https://www.oracle.com/database/technologies/related/berkeleydb/berkeleydb-licensing.html>

`Icod.TermInfo.BerkeleyDb` does **not** embed or link Berkeley DB in production.
It independently reads the documented/observed on-disk representation needed for
terminfo acquisition.

The package must therefore avoid copying Berkeley DB implementation source into
our production code. Format constants and structures should be re-expressed as
necessary interoperability facts and backed by our own tests and documentation.

Any future proposal to redistribute, link, or derive implementation code from a
third-party Berkeley DB distribution requires a fresh licensing review.

## 7. Why native linking is less reliable for this project

A native Berkeley DB wrapper would require us to qualify at least:

- Windows DLL availability and architecture;
- Linux sonames and distro variations;
- macOS/Homebrew/system-library availability;
- Berkeley DB major-version ABI differences;
- dynamic loader behavior;
- native lifetime/error translation;
- package RID assets if we bundle binaries;
- security updates for bundled native code; and
- licensing consequences of the chosen Berkeley DB release/distribution.

HDB00 demonstrated that none of this is necessary for read-only terminfo
acquisition. A Linux-generated Hash-v9 fixture was consumed on Windows without a
Berkeley DB library and produced byte-identical compiled terminfo data.

Removing an unnecessary runtime subsystem is therefore a reliability improvement,
not merely a dependency-avoidance preference.

## 8. Managed-reader risk and containment

Owning a file-format reader carries real risks:

- malformed-file attack surface;
- format-version assumptions;
- integer overflow/page-boundary bugs;
- unsupported Berkeley DB features;
- overflow-chain corruption;
- accidental scope expansion into a database engine.

The 1.15 roadmap contains these risks by requiring:

- Hash format v9 only unless later evidence expands the contract;
- read-only operation;
- no hash-table mutation;
- strict metadata/access-method recognition;
- validated page geometry;
- checked arithmetic;
- bounded allocations;
- overflow cycle detection;
- exact-key matching;
- existing `CompiledTermInfoParserOptions.MaximumEntrySize` enforcement;
- real ncurses/Berkeley DB differential fixtures;
- Windows/Linux/macOS qualification; and
- rejection of unsupported features rather than heuristic interpretation.

HDB02 remains internal implementation work. Public provider API freeze waits for
HDB03.

## 10. HDB02 entry criteria

HDB02 may proceed when:

1. HDB01 package/test/pack verification is accepted on an exact head;
2. the HDB00 oracle workflow remains green;
3. this ecosystem audit remains part of the release record;
4. production code is started test-first rather than copied from the research
   probe; and
5. the scope remains an internal read-only Hash-v9 reader, not a public general
   database API.

The first HDB02 tests should define the smallest externally observable internal
reader behaviors needed by the eventual provider:

- valid exact-key retrieval;
- clean missing-key result;
- valid inline key/data recovery;
- off-page/overflow value recovery;
- unsupported access-method/revision rejection;
- malformed page/index rejection;
- truncated/cyclic overflow rejection; and
- resource-bound enforcement.

---

## 11. Decision

The HDB00/HDB01 engineering decision remains:

> `Icod.TermInfo.BerkeleyDb` will implement a narrowly scoped, pure-managed,
> read-only Berkeley DB Hash-v9 reader for ncurses terminfo acquisition. It will
> not take a production dependency on the reviewed legacy NuGet wrappers or
> native Berkeley DB packages. Native Berkeley DB is retained only as an
> interoperability oracle for authoritative CI fixtures and differential tests.

This decision should be reconsidered only if a materially better modern managed
implementation appears or if authoritative interoperability evidence shows that
the selected bounded Hash-v9 subset cannot satisfy real ncurses stores.
