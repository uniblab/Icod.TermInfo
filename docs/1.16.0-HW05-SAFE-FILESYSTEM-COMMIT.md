## Publication behavior

The existing public writer still completes input snapshots, validation, ncurses
record planning, and deterministic image construction before filesystem work.
It delegates publication to an internal implementation with a private filesystem
seam for deterministic fault and concurrency tests.

The publisher holds a persistent per-destination sibling lock through staging,
verification, commit, and failure cleanup. The production lock uses exclusive
sharing and verifies enforcement with a second open. Only recognized
host-specific sharing/lock contention is retried, with cancellation-aware 50 ms
polling and no timeout. Other errors propagate. A filesystem that permits both
exclusive opens is rejected before staging.

Staging exclusively creates a unique sibling file, writes in bounded chunks,
requests write-through, flushes to disk, and closes. The existing stable reader
reopens and observes it twice through a borrowed cancellation-aware adapter.
The publisher verifies complete bytes, exact physical key/value records, and
canonical/alias catalog names, kinds, resolved identities, and ordered aliases.
Only then does it revalidate paths, check cancellation, and invoke one
same-directory move with the selected overwrite policy.

Cancellation is never observed after move begins. Every tested pre-commit
failure preserves previous destination bytes or destination absence. Cleanup
targets only a successfully created temporary file. Failed exclusive creation
never transfers ownership. Write failures survive subsequent close and cleanup
errors; a successful move never deletes a recreated temporary pathname.

## Filesystem boundaries

For `terminfo.db`, the lock is `.terminfo.db.icod-terminfo.lock`; staging uses
`.terminfo.db.icod-terminfo-<unique identifier>.tmp`. The lock persists and is
never deleted, truncated, or populated with ownership data. Existing contents
remain untouched. Process death releases its handle, not its pathname.

The immediate parent must be an existing ordinary directory. Destination and
lock directories, live or dangling symbolic links, and reparse points are
rejected. Preliminary checks do not replace validation under the lock or the
final authoritative move. Portable managed checks are not a hostile
path-substitution defense.

Replacement uses fresh staged-file metadata under normal directory inheritance,
not the old destination's ACLs, attributes, or mode. Cooperative Icod writers
serialize; native writers and unrelated tools do not participate. Atomic
visibility depends on filesystem same-directory move semantics. There is no
universal directory power-loss durability guarantee or application-level
copy/delete fallback. Windows may refuse replacement while a reader has the destination open, even
when that reader permits delete sharing; refusal preserves the previous file.

The 62 new cases cover lock contention and enforcement, cancellation in both
stable-read passes, independent equality levels, staged-operation fault
injection, primary exception preservation, temporary ownership, concurrent
writers/readers, separate destinations, fresh metadata, long sidecar names,
and independent-process release, crash recovery, and persistent-lock reuse.

The case-equivalent path fixture first probes the actual directory's case
behavior and reports unavailable coverage on case-sensitive filesystems.
The Windows read-only-attribute fixture reports inapplicability elsewhere.
These conditional fixtures do not claim coverage on filesystems or hosts where
the required capability is absent; the local Linux directory was case-sensitive.

The process helper is test-only, non-packable, and copied only into the test
output. It references the production BerkeleyDb library, adds no production
dependency, and is not a shipped tool or archive executable.


The first CI candidate exposed two repository formatting gates (multiline
ternaries and multiline call closing parentheses). Both failures reproduced
locally; the corrected candidate passed all six convention tests and all 648
Runtime Staging tests on .NET 10, as well as 587 BerkeleyDb Release tests.
Full local solution restore was blocked because the reachable mirror lacks
`Icod.CommandFramework`; full-solution qualification uses the normal CI feed.

Windows qualification exposed an incorrect test assumption: allowing delete
sharing does not guarantee that overwriting an open destination succeeds.
[Microsoft's File.Move contract](https://learn.microsoft.com/en-us/dotnet/api/system.io.file.move?view=net-10.0)
documents refusal when exclusive destination access is unavailable;
[dotnet/runtime #114230](https://github.com/dotnet/runtime/issues/114230)
records the matching delete-sharing case. The observation test now accepts
only the Windows access-denied exception captured at the actual move boundary,
verifies exact prior bytes, temporary cleanup and lock release, and requires a
successful publication after the observer closes. Every successful observation
must still be one complete old/new image. No production retry, fallback, or
contract change was introduced.

The normal workflow passed all 12 jobs at the code head above. Its host logs
confirm 587/587 BerkeleyDb tests for each of net8.0, net9.0, and net10.0 on
Windows, Linux, and macOS. Exact package verification confirmed Runtime-only
dependencies, IL-only assembly identity, portable symbols, Source Link, and no
native assets. Isolated consumers and all six matching-host tool archive smoke
jobs passed.

The test-only final correction was outside HDB00's sensitive change classifier,
so the automatic HDB00 run skipped native work. It is not used as native
acceptance evidence. Full HDB00 run 36273400765 was explicitly dispatched on
`341162b405978f0ff28bf0996e497e3a41f46460`; the classifier and workflow were not
changed to trigger it.

Full HDB00 qualification passed all three jobs at the same code head.
Interoperability tests passed 77/77 on each of net8.0, net9.0, and net10.0
on Linux, macOS, and Windows. Linux/macOS used native Berkeley DB 5.3;

installed.
