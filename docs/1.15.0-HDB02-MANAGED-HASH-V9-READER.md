Test-only RED head: `219555c023b53018fa79a80b3b41c4a63a36c1f0`.

[PR workflow #1036 / 35010444473](https://github.com/uniblab/Icod.TermInfo/actions/runs/35010444473)
proved the RED on Linux across net8.0/net9.0/net10.0: 5 failed, 34 passed,
39 total per target framework. All five failures were the expected
`Assert.Throws` failure because no exception was thrown.

The five regression cases cover:

- incorrect base metadata page identity, in both byte orders;
- incorrect scanned Hash-page identity, in both byte orders;
- incorrect followed overflow-page identity.

The fixture builders now set the correct page identities. The independent
layout reference is Berkeley DB's
[DBMETA/PAGE definition](https://github.com/berkeleydb/libdb/blob/5b7b02ae052442626af54c176335b67ecc613a30/src/dbinc/db_page.h).
The production fix reads the stored page number in the detected byte order and
rejects a mismatch before consuming that page's records or overflow payload.

Validation is deliberately attached to metadata, scanned Hash pages, and
followed overflow pages. It is not attached to generic page slicing:
unused/sparse pages are not required to carry an initialized page identity.

The same test-only commit adds passing characterization coverage for:

- invalid magic, revision, page sizes, encryption/checksum flags, metadata type,
  and last-page bounds;
- odd/oversized item counts, free-offset bounds, and item-offset bounds;
- empty/truncated metadata and partial data pages;
- overflow cycles, out-of-range references, wrong page type, declared-length
  underflow/overflow, and oversized declared values;
- case-, prefix-, and suffix-different requested keys returning a clean miss.

The tests use real temporary files and the production reader. They do not use
mocked storage or assert private diagnostic wording.

## Resource limits and file ownership checkpoint

Compile RED head: `87e69b5e195fbed4b8a58696564ff3803755b6f6`.

[PR workflow #1038 / 35012764739](https://github.com/uniblab/Icod.TermInfo/actions/runs/35012764739)
reported CS1739 for the missing limit parameters on net8.0/net9.0/net10.0
on Windows, Linux, and macOS.

Signature-only behavioral RED head: `b3416a1bd1d0aceb2a54b2de51539b7e0b3043ec`.
[PR workflow #1039 / 35013180048](https://github.com/uniblab/Icod.TermInfo/actions/runs/35013180048)
proved behavioral RED on Linux and macOS across net8.0/net9.0/net10.0:
9 failed, 50 passed, 59 total per target framework. File/item limit rejections
did not throw, invalid limits reached file opening, and the parallel-call case
reported the same missing rejection. No production enforcement was added until
the Linux behavioral RED had been observed.

The internal reader now accepts positive, inclusive limits for database bytes
and stored item bytes. Defaults are 64 MiB per database and 1 MiB per item.
These are internal defaults, not frozen public provider options.
`CompiledTermInfoParserOptions.MaximumEntrySize` remains independently
authoritative when HDB03 introduces compiled-entry parsing.

The implementation:

- validates limit arguments before opening the file;
- opens one read-only file handle, checks its length against the database limit
  and `Array.MaxLength`, and rejects a too-short metadata file before allocating
  the file buffer;
- reads exactly the checked length, rejects an extra byte indicating growth,
  and lets short-read and other I/O exceptions propagate;
- disposes the file handle before container parsing;
- bounds both stored keys and returned values before inline copies or
  overflow-result allocation; and
- carries limits as per-call arguments, without mutable shared configuration.

The 20 new cases cover inclusive database/inline/overflow boundaries, stored-key
limits, invalid arguments before file opening, empty values, exclusive file
reopening after success/miss/malformed input/limit rejection, and independent
parallel calls with different limits. The complete suite contains 59 cases.

The tests use small explicit caps. Default values and preallocation check
placement are reviewed in source; the tests do not directly exercise the large
default boundaries or force file-growth/short-read races. Parallel calls
exercise independent limits without promising scheduling overlap. A single
handle avoids a separate size-check/reopen race, but does not guarantee an
atomic snapshot against same-length external writes.

## Valid layouts and empty 64 KiB pages checkpoint

Test-only RED head: `792162df22cc3ff4760e74aa28122378e9486e26`.

[PR workflow #1041 / 35015617182](https://github.com/uniblab/Icod.TermInfo/actions/runs/35015617182)
proved RED on Linux and macOS across net8.0/net9.0/net10.0:
4 failed, 93 passed, 97 total per target framework. All four failures were
`InvalidDataException` for free offset zero on otherwise valid empty 64 KiB
Hash pages, in both byte orders, with either a later record or a clean miss.

The independent layout reference is Berkeley DB's
[`PAGE` / `P_INIT` definition](https://github.com/berkeleydb/libdb/blob/5b7b02ae052442626af54c176335b67ecc613a30/src/dbinc/db_page.h).
`P_INIT` initializes the free offset by casting page size to the 16-bit
`db_indx_t`; an empty 65536-byte page therefore stores zero.

Production normalizes that offset to 65536 only when the page size is 65536,
the item count is zero, and the stored free offset is zero. Other zero offsets
retain the existing corruption failure. No production change was made before
the expected behavioral RED was observed.

The 38 new cases in `Hdb02HashLayoutTests` cover:

- all eight supported power-of-two page sizes, 512 through 65536, in both
  byte orders, with opaque binary keys and values;
- empty minimum/maximum-size Hash pages followed by either another empty page
  or a populated page;
- multiple records on one page, records on later pages, and unused sparse pages;
- off-page keys, off-page values, or both, in both byte orders;
- a two-page key chain (486 + 214 bytes) and a three-page value chain
  (486 + 486 + 28 bytes), each linked in noncontiguous physical order;
- off-page stored-key size rejection while searching for a shorter key; and
- negative controls rejecting zero free offsets on empty 512-byte pages and
  populated 65536-byte pages.

The other 34 new cases passed before the production change and are
characterization coverage. These are synthetic container-layout fixtures;
they do not replace native-generated interoperability qualification.

## Unsupported layouts and filesystem failures checkpoint

Test-only RED head: `1d46d6eb71568e50bfd1dab0bae35ca960f8af5d`.

[PR workflow #1043 / 35018087138](https://github.com/uniblab/Icod.TermInfo/actions/runs/35018087138)
proved RED on Linux and macOS across net8.0/net9.0/net10.0:
28 failed, 118 passed, 146 total per target framework. Only the 18 metadata
feature cases and 10 unsupported scanned-page cases failed; each expected
`InvalidDataException`, but the reader returned normally.

The pinned upstream
[`DBMETA`, `HMETA`, page and item definitions](https://github.com/berkeleydb/libdb/blob/5b7b02ae052442626af54c176335b67ecc613a30/src/dbinc/db_page.h)
identify metadata feature flags at byte 26, partition count at bytes 36–39,
and access-method flags at bytes 48–51. Hash flags include duplicate,
subdatabase, and sorted-duplicate support, all outside this reader's subset.

The production checks now:

- retain the existing checksum/encryption rejection, and reject other nonzero
  metadata feature flags, nonzero partition counts, and nonzero Hash flags;
- skip unused/free pages (type 0) and unfollowed overflow pages (type 7) while
  scanning, and read supported sorted Hash pages (type 13);
- reject other encountered page types explicitly, including legacy unsorted
  Hash pages (type 2), additional metadata, and duplicate layouts; and
- preserve ordinary I/O failures and clean misses as distinct outcomes.

Legacy page type 2 is a valid Berkeley DB layout that this implementation
does not support; it is not inherently corrupt. Page validation occurs as
lookup encounters pages. A successful match still ends the scan, so this is
not an exhaustive validator of unvisited pages or unrelated values.

The 49 new cases include 28 RED regressions plus 21 passing characterization
cases: skipped nonrecord pages, unsupported key/value item types, truncated
off-page headers, missing files and retry, exclusive-open failure and retry,
directory-open failure, and replacement after successful or malformed reads.
The existing 97 cases remain unchanged.

Filesystem tests use real files and handles. Replacement is deterministic
**between** reads; these tests do not force truncation, growth, or replacement
during an active read and do not establish atomic snapshot semantics.

## Direct native-oracle qualification checkpoint

Initial test/workflow head: `081f460ee814fd40b80991a23f85dea79f63875e`.

[HDB00 workflow #74 / 35020360943](https://github.com/uniblab/Icod.TermInfo/actions/runs/35020360943)
verified the initial access RED on Linux across net8.0/net9.0/net10.0:
CS0122 for `BerkeleyDbHashReader` after successful native fixture generation
and dump export. This is an internal-access failure, not evidence of a
production storage bug. The next change grants only `InternalsVisibleTo`
access to the dedicated interoperability test assembly; reader code is
unchanged.

`Icod.TermInfo.BerkeleyDb.Interop.Tests` calls the production reader directly.
Native Berkeley DB `db_dump -k` supplies the expected opaque key/value bytes
from the existing pinned-ncurses primary/alias and forced-overflow stores.
The test helper decodes only Berkeley DB's documented byte-value dump framing
and hexadecimal records, based on upstream
[`__db_prdbt`, `__db_prheader`, and `__db_prfooter`](https://github.com/berkeleydb/libdb/blob/5b7b02ae052442626af54c176335b67ecc613a30/src/db/db_pr.c).
It contains no Hash-page reader or ncurses record-resolution implementation.

Six cases run per TFM:

- compare every native record in the primary/alias store (three records);
- compare every native record in the forced-overflow store (two records);
- establish clean misses in each store, with absence checked against the native
  record set; and
- reject the native-generated Btree file and the existing invalid-file fixture.

Exact record counts, nonempty dump data, paired lines, required headers/footer,
and byte-for-byte assertions prevent missing or empty fixtures from producing
vacuous success. `ICOD_HDB02_FIXTURE_ROOT` is mandatory; there is no skip path.

Linux and macOS create and test their own native fixtures. Windows downloads
the Linux databases and their matching native dumps and runs the same tests
without Berkeley DB installed. All hosts install net8/net9/net10 SDKs.
Linux and macOS database/dump artifacts are retained for seven days by CI.

The existing research probe remains in the workflow. New path filters ensure
production BerkeleyDb, unit/interoperability tests, and shared build-property
changes trigger qualification. The fixture-dependent project is intentionally
outside normal solution tests. To reproduce after generating the workflow's
fixtures and dumps, set `ICOD_HDB02_FIXTURE_ROOT` and run:

```sh
dotnet test tests/Icod.TermInfo.BerkeleyDb.Interop.Tests/Icod.TermInfo.BerkeleyDb.Interop.Tests.csproj -c Release
```

Native big-endian stores and Windows-native Berkeley DB generation are not
covered here; existing big-endian layout tests remain synthetic.

## Deterministic acquisition-failure checkpoint

Test-only head: `51f5eb5c5caec99275ed114f9e60e732df65e4c6`.

[PR workflow #1048 / 35023681267](https://github.com/uniblab/Icod.TermInfo/actions/runs/35023681267)
verified CS0117 on Linux and macOS across net8.0/net9.0/net10.0 because the
internal stream overload did not exist. This is compile/access RED, not a
demonstrated defect in the existing file-read safeguards.

The production path wrapper still opens and owns one read-only FileStream.
It now delegates byte acquisition to an internal overload borrowing a readable,
length-reporting stream positioned at byte zero. The overload validates null
and positive-limit arguments and leaves stream disposal to its caller.
Existing length checks, allocation, `ReadExactly`, and trailing-byte probe are
extracted without behavioral changes. The file handle is still disposed before
container parsing.

Nineteen new cases use a controlled Stream backed by a real MemoryStream:

- assemble the complete payload from reads limited to 1, 7, 511, or 512 bytes;
- propagate truncation with 0, 1, or 511 bytes available after observing length 512;
- reject an extra byte after the checked payload, including growth beyond the cap;
- preserve the original IOException at the first read, mid-payload, and EOF probe;
- reject undersized, over-limit, and above-Array.MaxLength reported lengths
  before any payload read; and
- validate null/limit arguments and leave borrowed streams open on all outcomes.

These deterministic stream cases characterize the same acquisition helper used
by the file path. They do not claim to reproduce an operating-system race.
Existing real-file ownership, replacement-between-reads, sharing, and retry
tests remain unchanged. Independent test review found no blocking findings.
The expected complete unit suite contains 165 cases per TFM; GREEN qualification
is pending for the extraction commit.

## Final scope review

The complete internal reader was reviewed against HDB02's roadmap requirements.
No blocking finding was identified in the declared subset. Acceptance retains
these limits:

- Validation follows encountered pages and items; a match ends lookup without
  exhaustively validating unrelated values or unvisited pages.
- File/item limits bound individual allocations, not aggregate lookup work.
  Repeated references to large off-page keys can cause repeated reconstruction.
- A single open handle and exact-length checks do not guarantee atomic snapshots
  against same-length concurrent external writes.
- Native-oracle coverage uses the qualified Unix producers. Big-endian fixtures
  are synthetic; Windows consumes Linux-generated fixtures.

These limits are not promises of general-purpose Berkeley DB support or
concurrent-writer coordination.
