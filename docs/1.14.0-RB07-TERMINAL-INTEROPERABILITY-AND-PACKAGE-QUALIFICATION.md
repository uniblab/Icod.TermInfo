## Explicit adapter policy

The qualification flow keeps backend identity separate from lifecycle semantics.

The Sixel candidate is derived from explicit static `TerminalDescription` Sixel metadata through `RasterBackendInspector`. No terminal-name or emulator-brand heuristic is used.

The Kitty path demonstrates a caller-owned Terminal adapter:

```text
published Terminal semantic result
    -> caller-owned Terminal support mapping
    -> backend-scoped 1.13 runtime lifecycle observations
    -> PersistentRasterRuntimeEvidenceIntegrator
    -> strengthened lifecycle/placement profiles
    -> caller-owned explicit Kitty availability evidence
    -> RasterBackendCandidate
```

The downstream consumer explicitly touches the published Terminal 1.13 public symbols `TerminalCapabilityStatus` and `TerminalCapability.PersistentRasterGraphics`. It does not inspect Terminal internal backend resolver types.

A `TerminalCapabilitySupport.Verified` result is mapped to a supported 1.13 runtime observation outcome; `Unsupported` maps to unsupported; `Unknown` and `Advertised` remain inconclusive. The sample additionally requires a real live `TerminalCapabilityEvidenceKind.LiveObservation` before treating a live status as conclusive.

The expansion from Terminal's coarse `PersistentRasterGraphics` semantic result into TermInfo's seven lifecycle subjects remains visible caller policy. TermInfo does not perform that expansion itself.

Likewise, the decision that a conclusive persistent-raster result represents Kitty Graphics availability is explicit caller policy in the qualification consumer/sample. It is not a new TermInfo inference rule.
