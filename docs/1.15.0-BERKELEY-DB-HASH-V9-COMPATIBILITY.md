# Icod.TermInfo 1.15.0 Berkeley DB Hash-v9 Compatibility

## Qualified contract

Icod.TermInfo 1.15 supports the narrow on-disk subset used by qualified ncurses
hashed terminfo stores. “Hash-v9” means Berkeley DB Hash access-method format
version 9; it does not mean all Berkeley DB products, versions, access methods,
or application schemas.

The accepted data path is:

```text
P_HASHMETA metadata -> P_HASH records -> ncurses marker envelope
    -> exact compiled terminfo bytes -> Runtime parser
```

## Accepted container structures

The managed reader recognizes:

- Berkeley DB Hash magic `0x00061561` and format version 9;
- power-of-two page sizes from 512 through 65536 bytes;
- little-endian and big-endian metadata/page fields;
- `P_HASHMETA` metadata pages (type 8);
- sorted `P_HASH` pages (type 13);
- paired key/value offset tables;
- inline `H_KEYDATA` items (type 1);
- `H_OFFPAGE` descriptors (type 3); and
- bounded `P_OVERFLOW` page chains (type 7).

Page numbers, page types, offsets, lengths, item pairing, unsigned byte-key
ordering, overflow topology, declared length, and record uniqueness are checked.
Unexpected pages or unsupported item forms are rejected rather than guessed.

## ncurses record envelope

The qualified ncurses schema uses:

- marker 2 for a canonical-name or alias index value whose payload is a target
  storage key; and
- marker 0 for a compiled terminfo data value.

Index chains are followed with an explicit hop bound. Empty records, unsupported
markers, dangling targets, cycles, and hop-limit exhaustion are format errors.
Only an absent initial lookup key is a clean miss.

Compiled bytes remain opaque until they reach Runtime's existing bounded parser.
The provider then requires the requested name to be the compiled canonical name
or an exact declared alias.

## Names and encodings

Lookup is exact and ordinal. UTF-8 is attempted first. A representable Latin-1
key is attempted only after a clean UTF-8 miss. Catalog decoding likewise uses
valid UTF-8 first and Latin-1 only for raw keys that are not valid UTF-8.

Compiled identity fields retain Runtime's established byte-preserving Latin-1
interpretation. General encoding detection, Unicode normalization,
transliteration, best-fit mapping, and locale-dependent comparison are not
supported or claimed.

## Interoperability evidence

Linux and macOS independently build Berkeley DB 5.3 and ncurses hashed mode,
extract exact native records, and compare them byte-for-byte with managed
lookup. Qualification covers inline and forced overflow values, 64-entry
multi-page stores, native big-endian containers, canonical and alias lookup,
exact Latin-1 names, logical catalog enumeration, and direct/routed commands.
Windows consumes transported Linux fixtures without Berkeley DB installed.

## Explicit exclusions

Version 1.15 rejects or does not claim:

- Btree, Recno, Queue, Heap, or other access methods;
- Hash revisions other than version 9;
- legacy type-2 Hash pages;
- subdatabases, duplicate-value semantics, transactions, logs, recovery, or
  environments;
- encryption or checksum features;
- mutation, publication, migration, or repair;
- atomic snapshots while another process writes; or
- arbitrary non-ncurses application data.

Future support requires new authoritative fixtures, adversarial tests, API and
dependency review, and a separate compatibility decision.
