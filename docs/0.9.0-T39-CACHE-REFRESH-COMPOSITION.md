# Icod.TermInfo 0.9.0 — T39 Provider Cache, Refresh, and Composition

**Tranche:** T39 — Provider Cache, Refresh, and Composition
**Development version:** `0.9.0-beta.3`
**Previous tranche:** T38 — system discovery and precedence
**Next tranche:** T40 — API, documentation, samples, and package freeze

---

## Purpose

T39 completes the provider lifetime/concurrency contract frozen in T32.

The tranche does not change terminfo parsing or discovery precedence. It
hardens how the existing directory and system providers behave after callers
begin resolving names repeatedly or concurrently.

T39 freezes these rules:

- successful external descriptions are cached per provider instance;
- concurrent first load of one requested name is single-flight;
- clean misses are not permanently cached;
- parser/I/O failures are not converted into or retained as misses;
- a successfully cached immutable description remains stable for that provider
  lifetime;
- a new provider instance is the ordinary refresh mechanism;
- separate providers never share arbitrary external-description cache state;
- `TerminalDatabase` may itself participate as a provider, enabling explicit
  nested composition such as system lookup followed by built-in fallback;
- `TerminalDatabase.BuiltIn` remains unchanged and isolated.

## Single-flight cache primitive

Both `DirectoryTerminalDescriptionProvider` and
`SystemTerminalDescriptionProvider` use the same ownership pattern:

```text
ConcurrentDictionary<
    exact requested name,
    Lazy<TerminalDescription?>
>
```

The dictionary is an instance field.

`LazyThreadSafetyMode.ExecutionAndPublication` means that although
`ConcurrentDictionary.GetOrAdd` may construct more than one candidate `Lazy`
object during a race, only the one candidate actually published in the
dictionary is evaluated by callers using that dictionary value.

Consequently a successful concurrent first load performs one effective
provider load for the published name and all callers observe the same immutable
`TerminalDescription` instance.

## Successful entries

A non-null successful result remains in the provider-local dictionary.

Subsequent lookups for that exact requested name therefore:

- do not reread the filesystem;
- do not reparse the compiled entry;
- do not rescan earlier system-discovery sources;
- do not re-decode an encoded `TERMINFO` entry;
- return the same immutable description instance.

This is intentionally a provider-lifetime snapshot of successful acquisition.

If the underlying file is replaced after success, the existing provider keeps
the cached result.

## Clean misses

A lazy load which completes with `null` represents an ordinary clean miss.

That exact lazy is removed conditionally from the dictionary before
`TryLoad` returns `false`.

No persistent negative-cache entry remains.

Therefore:

```text
lookup missing name
    -> false

install/create entry

lookup same name through same provider
    -> provider searches again
    -> entry may now succeed
```

This applies to both explicit directory and system providers.

## Failures

If evaluation throws, the provider conditionally removes the exact lazy which
threw and rethrows the original exception.

The conditional key/value removal is important under concurrency: a waiter on
an old failed lazy cannot remove a newer retry lazy which has since been
published for the same name.

Parser, I/O, permission, unsupported-source, and other T38 error categories
therefore remain errors rather than becoming cached misses.

After the underlying cause is corrected, a later call may retry normally.

## System-provider cache

T38 already constructed stable directory-source providers for the lifetime of
one `SystemTerminalDescriptionProvider`.

T39 adds a provider-wide successful cache above the discovery chain.

This is necessary for two reasons:

1. successful encoded `TERMINFO` descriptions previously had no provider cache;
2. repeated lookups should not repeatedly traverse higher-precedence sources
   after a lower source has already produced the immutable result.

The T38 precedence is unchanged. The first uncached lookup still evaluates:

```text
encoded TERMINFO
TERMINFO directory
user .terminfo
TERMINFO_DIRS
platform defaults
```

The successful result is then retained by the system provider.

The directory providers underneath retain their own provider-local caches as
well. This layering does not introduce process-global state.

## Refresh semantics

The ordinary refresh operation remains:

```text
construct a new provider
```

Example:

```text
provider A loads entry version 1
file changes to version 2
provider A still returns cached version 1

construct provider B
provider B reads version 2
```

No filesystem watcher, TTL, background refresh thread, or mandatory public
cache-clear API is added.

This is deterministic and matches the T32 freeze.

## Provider isolation

Every arbitrary external-description cache is an instance field.

Separate providers may therefore:

- point at different explicit roots;
- capture different system-discovery snapshots;
- use different environment/user/default-source policies;
- observe different file generations;
- cache different descriptions for the same requested name.

They do not synchronize through process-global external-entry state.

Static built-in terminal profiles remain the separate deterministic built-in
contract and are not an arbitrary external-description cache.

## `TerminalDatabase` as a provider

T39 makes:

```csharp
TerminalDatabase : ITerminalDescriptionProvider
```

No new public method is required because `TerminalDatabase.TryLoad` already
matches the provider contract.

This closes the composition gap identified by the T32 architecture.

A caller can now compose system lookup with the immutable built-in database
directly:

```csharp
TerminalDatabase database =
    new(
        new ITerminalDescriptionProvider[]
        {
            new SystemTerminalDescriptionProvider(),
            TerminalDatabase.BuiltIn,
        });
```

The result is explicit first-provider-wins behavior:

```text
system provider
    |
    | miss
    v
TerminalDatabase.BuiltIn
```

No built-in provider list is exposed, copied, or mutated.

Nested `TerminalDatabase` composition is ordinary provider composition; it does
not create a process-global registry.

## Sample behavior

`Icod.TermInfo.Sample` now demonstrates the system-to-built-in composition for
its ordinary environment resolution path.

The explicit `--profile` command-line option continues to mean an explicitly
selected built-in profile.

Without that option, the sample resolves the environment through:

```text
SystemTerminalDescriptionProvider
    -> TerminalDatabase.BuiltIn
    -> explicit Dumb fallback if no requested profile resolves
```

This demonstrates arbitrary host terminfo acquisition without sacrificing the
deterministic built-in fallback.

## Built-in isolation

System acquisition never mutates `TerminalDatabase.BuiltIn`.

A system provider which loads an arbitrary external terminal does not cause
that terminal name to become visible through the built-in database.

Built-in objects retain their established identity and behavior before and
after system lookup.

## Public API impact

T39 adds no new exported public type and no new public member.

`TerminalDatabase` gains the existing public provider interface as an
implemented interface.

The exact exported type set therefore remains unchanged.

T40 remains responsible for the final 0.9 public API baseline/freeze.
