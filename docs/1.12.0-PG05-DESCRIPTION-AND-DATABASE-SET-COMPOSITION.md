# Icod.TermInfo 1.12.0 — PG05 Description and Database-Set Composition

**Tranche:** PG05 — `TerminalDescription` and database-set composition  
**Development version:** `1.12.0-Alpha-5`  
**Baseline:** accepted PG04 lifecycle-aware placement planner  
**Primary package:** `Icod.TermInfo.Inspection`

## Purpose

PG05 connects the protocol-neutral advanced-placement model to immutable `TerminalDescription` metadata and to the frozen ordered database-set precedence model established in 1.10.

This tranche does not add a second precedence algorithm and does not infer capabilities from terminal names, brands, aliases, or protocol heuristics.

## Public surface

PG05 adds exactly two public types:

```text
PersistentRasterPlacementInspector
PersistentRasterPlacementDatabaseSetInspection
```

Together with PG01–PG04, the cumulative approved 1.12 Inspection API ledger now contains fourteen `PersistentRasterPlacement*` public types.

## Reserved description semantics

Static description inspection recognizes exactly two Icod-owned extended Boolean capabilities:

```text
IcodPersistentRasterSourceRectangle
IcodPersistentRasterSignedZOrder
```

They map respectively to:

```text
PersistentRasterPlacementSubject.SourceRectangle
PersistentRasterPlacementSubject.SignedZOrder
```

A present recognized Boolean contributes positive `CapabilityDerived` evidence. Absence contributes no negative evidence and therefore leaves the subject `Unknown` unless stronger caller evidence is supplied.

A recognized reserved capability encoded with a non-Boolean value is rejected with `InvalidOperationException`. Unrecognized graphics capabilities, including ordinary raster-display declarations, do not imply either advanced-placement semantic.

No terminal-name or brand guessing is permitted.

## Caller evidence

Direct description inspection may additionally receive caller-supplied placement evidence. Static capability-derived evidence is collected first and the existing PG03 classifier remains authoritative for precedence:

```text
Verified
    >
Declared
    >
CapabilityDerived
```

Same-tier positive and negative evidence remains `Contradicted`; PG05 does not collapse conflicts into a Boolean answer.

This allows runtime probes or application knowledge to strengthen or contradict static metadata without changing the static description itself.

## Frozen database-set composition

Database-set inspection delegates effective-definition selection exclusively to:

```csharp
TermInfoDatabaseSet.LookupCanonicalName(...)
```

The frozen 1.10 semantics therefore remain authoritative:

- lookup keys are canonical names only;
- aliases remain provenance and do not become canonical lookup keys;
- repeated canonical definitions preserve occurrence order;
- the first conclusive occurrence is the effective winner;
- later occurrences remain shadow evidence;
- an incomplete database before a later observation makes the result `Indeterminate`;
- an incomplete database after an already-known winner does not invalidate that winner.

PG05 introduces no independent root-ordering, alias-resolution, or incompleteness logic.

## Occurrence and effective profiles

`PersistentRasterPlacementDatabaseSetInspection` preserves:

```text
DatabaseSet
Lookup
OccurrenceProfiles
EffectiveProfile
```

`OccurrenceProfiles` are produced in exact `Lookup.Occurrences` order and contain only evidence derived from their own terminal descriptions. Caller evidence is deliberately not projected onto shadowed or otherwise non-effective occurrences.

`EffectiveProfile` is non-null only when the frozen lookup status is `WinnerKnown`.

When caller evidence is supplied and a winner is known, that evidence is layered onto the winner only after the effective-description boundary has been established. Consequently:

- caller evidence can strengthen or contradict the known winner;
- caller evidence cannot alter which root wins;
- caller evidence cannot manufacture a winner when lookup precedence is `Indeterminate`;
- caller evidence cannot turn a conclusive absence into an observed terminal;
- shadows remain faithful static observations rather than application-specific projections.

This ordering is the central PG05 composition invariant.

## Determinism and immutability

Occurrence profiles are snapshotted into a read-only collection and retain the frozen lookup order. Classification remains ordinal and culture-independent through the existing placement classifier and database-set APIs.

PG05 introduces no unbounded semantic vocabulary: the static mapping contains exactly two recognized placement subjects and continues to use the existing bounded placement-evidence options.

## Frozen compatibility boundaries

PG05 does not change:

- any 1.11 lifecycle enum, request, profile, planner, plan, issue, or composition type;
- the PG01–PG04 placement semantics already approved;
- JSON schema versions 1, 2, or 3;
- the frozen 1.11 Inspection API fingerprint;
- the production package dependency graph.

The cumulative 1.12 additions ledger now includes the two PG05 public types so the exact 1.11 surface can continue to be reconstructed independently.
