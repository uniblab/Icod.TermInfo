and records the package, command, sample, and distribution evidence required

is permitted between a green Alpha-8 release gate and stable publication.

## 3. Frozen planning behavior

The stable score is lexicographic in this exact order:

1. `LocalDirectiveCount`;
2. `CancellationCount`;
3. `ParentCount`;
4. `RenderedUtf8ByteCount`;
5. `SelectedCandidateIndices` in ordinal integer sequence order.

The default and supported bounds are frozen as:

| Bound | Default | Supported maximum |
| --- | ---: | ---: |
| Candidate count | 64 | 256 |
| Selected parent count | 2 | 256 |
| Evaluated plan count | 4,097 | 1,000,000 |
| Generated source length | 4,194,304 | 67,108,864 |

The zero-parent baseline is evaluated first. Legal ordered plans then appear by
increasing selected-parent depth and lexicographic candidate-index sequence.
Candidate positions are distinct, one position cannot repeat within one plan,
and candidate input is snapshotted at most once.

Exhaustive planning rejects a request before evaluation when the complete legal
space exceeds the configured budget. A non-exhaustive result is returned only
when the caller explicitly enables it; it contains the best plan in the exact
evaluated prefix and reports `IsExhaustive == false`.

Cancellation is observed at the stable RP04 boundaries during candidate
snapshot, ordered enumeration, and around synchronous synthesis. Cancellation
or a bounds failure returns no partial result.

## 4. Frozen orchestration behavior

`Plan` consumes a caller-owned ordered candidate sequence. `PlanFromCatalog`
consumes one explicit, complete, conventional, issue-free catalog.
`PlanFromDirectory` inspects one explicit conventional database root and does
not perform environment or platform-default discovery.

Catalog candidates use canonical names, remain in ordinal canonical-name order,
exclude target identity intersections, collapse equivalent physical copies,
and reject conflicting copies. Missing, unsupported, unavailable, partial, or
issue-bearing catalogs do not produce false exhaustive evidence.

## 8. Package-consumer and sample closure

The isolated Inspection package consumer requires exactly 29 exported types and
executes direct planning, explicit catalog planning, and explicit directory
planning from packed dependencies on all three supported TFMs.

The deterministic Toolchain sample remains the reusable end-to-end planning
proof:

```text
parse and resolve target/candidates
-> plan relative source
-> reparse and resolve selected source
-> compile and publish
-> reacquire through Runtime
-> compare with the original target
```

Release verification runs it twice in separate processes and requires
byte-identical output. ToolSuite retains the direct and routed command
walkthrough for `--plan-use`.
