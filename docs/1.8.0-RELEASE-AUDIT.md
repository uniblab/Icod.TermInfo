## 1. Purpose and status

RP08 closes the 1.8 development program without adding another feature tranche.
The stable release promotes the validated `1.8.0-Alpha-8` surface to `1.8.0`,
freezes the additive Inspection planning API, and makes the existing API,
package, router, archive, sample, command, and cross-platform gates responsible
for the complete 1.8 contract.

This is a pre-publication audit. It does not claim that 1.8.0 has been merged,
tagged, or published. Those actions remain under repository-owner authority.
After publication, the pending commit and tag fields must be replaced in the
stable release record with the exact published evidence.

No feature or semantic change is permitted between a successful Alpha-8 gate
and the stable version transition.

## 5. Planning semantic contract

The planner selects deterministic ordered parents for the unchanged 1.7
synthesizer. Its score is lexicographic over:

```text
local directive count
cancellation count
parent count
rendered UTF-8 byte count
selected candidate-index sequence
```

Candidate input order is therefore the final tie break. The planner snapshots
the caller sequence at most once and treats candidate positions as distinct.
The same position cannot occur twice in one plan.

Enumeration is stable: zero-parent baseline, then increasing selected-parent
depth, then lexicographic candidate-index sequence. The selected parent list,
score indices, and emitted `use=` order remain identical.

## 6. Bounds and completeness contract

| Bound | Default | Supported maximum |
| --- | ---: | ---: |
| Candidate count | 64 | 256 |
| Selected parent count | 2 | 256 |
| Evaluated plan count | 4,097 | 1,000,000 |
| Generated source length | 4,194,304 | 67,108,864 |

Complete plan-count arithmetic is checked and budget aware. Exhaustive mode
rejects a request before evaluation when the complete legal space does not fit
the evaluation budget. Non-exhaustive planning requires explicit caller opt-in
and returns the best result in the deterministic evaluated prefix with
`IsExhaustive == false`.

Cancellation is observed at the frozen candidate-snapshot, enumeration, and
synthesis boundaries. No partial plan is returned after cancellation or a
bounds failure.

## 7. Catalog and directory planning

`PlanFromCatalog` requires an explicit, complete, conventional, issue-free
catalog. `PlanFromDirectory` inspects one explicit conventional root and does
not perform host discovery.

Canonical catalog names provide candidate references in ordinal order. Alias
publications do not multiply candidates. Equivalent physical copies collapse;
conflicting copies fail. Target name and alias intersections are excluded.
Partial or issue-bearing catalogs never produce exhaustive planning evidence.

## 8. Semantic and oracle evidence

Every accepted plan is produced by the frozen 1.7 synthesizer and proven by the
existing source-resolution comparison path:

```text
Plan(target, candidates, options)
-> generated source plus selected parent representations
-> TermInfoSourceParser
-> TermInfoSourceResolver
-> TerminalDescriptionComparer
-> AreEqual == true
```

RP07 adds deterministic seeded target/candidate universes and an independent
brute-force oracle. It compares exhaustive winners and bounded-prefix winners,
exercises score ties and candidate permutations, and records reproducible seeds
for failures. Culture, insertion order, target framework, host family, and
repeated-process output are permanent determinism dimensions.

The pinned ncurses 6.5.20250216 corpus remains checked-in offline evidence. CI
does not depend on a host ncurses installation.

## 9. Command contract

RP06 exposes planning through the existing `infocmp` command:

```text
infocmp --plan-use target candidate [candidate ...]
```

The command remains a thin adapter over Inspection. It maps explicit
acquisition, renderer controls, planning bounds, cancellation, diagnostics, and
exit status without duplicating planning logic. Existing inspection,
comparison, and `-u` synthesis modes remain unchanged.

Planning is validated through:

- direct `infocmp` execution;
- routed `icod-terminfo infocmp` execution;
- isolated `Icod.TermInfo.Tools` package installation; and
- matching-host standalone archive execution.

Before stable tagging, the exact intended release commit must pass:

- clean restore, build, and test on Windows, Linux, and macOS;

  API baselines;

- assembly version `1.0.0.0` for all reusable libraries;
- planner unit, semantic, generated-state, oracle, corpus, boundary, and
  determinism tests;
- package structure and isolated package-consumer checks;
- deterministic Toolchain execution;
- direct and routed `infocmp --plan-use` checks;
- router package installation and smoke;
- all six archive structure checks and matching-host smoke; and
- exact release asset count and checksum verification.

## 14. Stable publication protocol

The only permitted post-gate source change is the coordinated stable-release
transition. It updates version metadata, release-facing documentation, package
notes, and their contract assertions without changing behavior or public API:

```text
1.8.0-Alpha-8 -> 1.8.0
```

After that exact commit is validated on `main`, the owner may create tag
`v1.8.0` and run publication. The tag must identify the exact validated current
`main` HEAD and match the centralized suite version.

This audit deliberately leaves the stable merge, tag, and publication as
pending owner actions.

## 15. Deferred work

The release does not include unbounded planning, implicit host-wide discovery,
arbitrary scoring callbacks, intermediate shared-parent creation, multi-target
source factoring, historical author-intent reconstruction, new termcap behavior,
historical binary dialects, live terminal sessions, probing, PTYs, curses
presentation, terminal emulation, or graphics protocols.
