## Accepted public surface

HDB05 adds:

```text
BerkeleyDbTerminalCatalogReader
BerkeleyDbTerminalCatalogReaderOptions
BerkeleyDbTerminalCatalogEntry
BerkeleyDbTerminalCatalogEntryKind
```

The reader owns one canonical absolute database path and a private immutable
option snapshot. `Read()` and `Read(CancellationToken)` return a new immutable
catalog snapshot and do not cache results.

Options expose:

```text
CompiledTermInfoParserOptions ParserOptions
int MaximumDatabaseSize
int MaximumRecordCount
int MaximumIndexHops
```

The entry exposes the exact publication `Name`, its `Canonical` or `Alias`
`Kind`, and the Runtime-owned parsed `TerminalDescription`.

No raw database record, page, bucket, cursor, environment, transaction, or
write API is public.

## Accepted storage and logical semantics

The internal complete-record reader:

1. validates one acquired Hash-v9 image;
2. scans ascending page/item order;
3. reconstructs inline and off-page keys and values;
4. rejects unsupported encountered structures, odd pairs, duplicate exact keys,
   and the next record beyond the inclusive limit;
5. supports both byte orders and existing overflow validation;
6. checks cancellation between pages and records; and
7. returns owned records sorted by unsigned lexicographic byte key.

The logical catalog:

1. indexes exact raw byte keys;
2. parses every marker-0 record, including unreferenced orphans;
3. emits only marker-2 publications;
4. decodes publication keys as strict UTF-8 and applies the shared exact-name
   safety rules;
5. follows marker-2 targets with content-based cycle detection and an inclusive
   hop bound;
6. parses compiled payloads only through `CompiledTermInfoParser`;
7. classifies a publication by ordinal comparison with parsed canonical/alias
   identity;
8. shares one parsed `TerminalDescription` instance for publications reaching
   the same marker-0 key; and
9. returns entries sorted by ordinal name, then kind, then canonical terminal
   name.

Structural failures are discovered in page/item order. Once extraction is safe,
logical envelope failures are discovered in raw byte-key order. Physical
Hash-page placement is never a public ordering contract.

## Resource, ownership, and error contracts

Each public read is all-or-nothing and bounded by:

- maximum database size;
- maximum record count;
- parser maximum entry size plus the ncurses marker byte;
- maximum index hops;
- validated Hash-v9 page geometry and overflow lengths; and
- cancellation.

The file is opened read-only, acquired once, and closed before enumeration and
parsing continue. Concurrent reads use independent images and state. A read is
fresh but does not promise an atomic snapshot against same-length external
writes.

Exception boundaries are:

- malformed/unsupported Berkeley DB structures and ncurses envelopes:
  `BerkeleyDbDatabaseFormatException`;
- malformed compiled terminfo:
  `CompiledTermInfoFormatException`;
- a valid compiled entry that does not declare a publication:
  `InvalidDataException`;
- filesystem failures: original I/O exception types; and
- cancellation: `OperationCanceledException`.

## Compatibility and non-goals

- Runtime public API remains unchanged and Runtime has no Berkeley DB dependency.
- Production remains pure managed, read-only, and free of P/Invoke/native
  assets.
- Reusable assembly identity remains `1.0.0.0`.
- Public API is equivalent across net8/net9/net10.
- Existing HDB03 exact lookup and HDB04 system discovery remain unchanged.
- Native big-endian producer interoperability is not claimed; big-endian
  coverage is synthetic.
- HDB05 does not add catalog caching, system-wide catalog composition, partial
  results, raw storage-key exposure, Inspection/tool integration, JSON changes,
  writes, transactions, recovery, or support for other Berkeley DB access
  methods/revisions/features.
