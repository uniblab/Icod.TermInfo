# 1.17.0 UC00 — Unified catalog contract

**Status:** Proposed for review; not an implemented or frozen API.

**Authority:** [1.17 roadmap](../Icod.TermInfo-1.17.0-Unified-Directory-Hashed-Catalogs-Roadmap.md).

**Audited baseline:** `78116dfc39e272c2ad5c8e2aaf9499dd7e80b37e` (PR #48),
whose production source is the published 1.16 implementation.

## 1. Intent and decisions

Provide one immutable, read-only catalog for one explicit conventional directory
or ncurses Hash-v9 file. A consumer can enumerate actual publication names and
their parsed terminals without interpreting storage formats. Preserve provenance,
diagnostics, and resource controls. No migration, mixed-source precedence,
comparison engine, JSON expansion, or command switches enter this release.

The recommended design is a new **`Icod.TermInfo.Catalogs`** package referencing
Runtime, Inspection, and BerkeleyDb. Inspection continues to reference only
Runtime/Source; BerkeleyDb continues to reference only Runtime. Compiler is a
test/fixture dependency only. No existing library references Catalogs.

| Alternative | Benefit | Cost / decision |
| --- | --- | --- |
| New composition package | Existing dependency boundaries remain intact; common model has one owner | Adds package, tests, consumer and API freeze; recommended |
| Put facade in Inspection | Fewer packages | Makes BerkeleyDb a dependency of every Inspection consumer; rejected |
| Put facade in BerkeleyDb or Runtime | Fewer packages | Reverses established ownership/dependencies; rejected |

The package is `LGPL-3.0-or-later`, assembly version `1.0.0.0`, C# 13, targeting
`net8.0;net9.0;net10.0`. Distribution becomes eight nupkg/seven reusable-library
snupkg. Tools retains its current dependencies and archive contents.

## 2. Audit findings and required seams

1. `TermInfoDatabaseInspector.Catalog.cs` materializes `GetDirectories` and
   `GetFiles` arrays. It retains parsed physical entries **before** checking their
   placement. Its duplicate list groups canonical identities, so an ordinary
   canonical file plus two alias files counts as a duplicate canonical identity.
   These existing behaviors must remain intact.
2. `BerkeleyDbTerminalCatalogReader.Read` returns actual publication names and
   parsed descriptions, not raw bytes. `NcursesCatalogReader` caches descriptions
   per storage key and parses orphan storage records too. Aliases share the
   target description. Invalid publications reject the whole hashed read.
3. Hashed database size, physical record count, stored item size and index hops
   are bounded, but several limit failures become
   `BerkeleyDbDatabaseFormatException`. Parsing errors can also escape as
   `CompiledTermInfoFormatException`; an identity mismatch is `InvalidDataException`.
   Messages cannot be used as stable error codes.
4. The hashed image read and its stability verification do not currently observe
   the catalog cancellation token. Existing physical-record limits alone also
   allow large cumulative decoded-item allocations.

Consequently, simply wrapping the two public readers cannot deliver the proposed
limits or typed limit failures. Add **opt-in bounded methods** using the existing
traversal/decoder/parser internals. Existing methods keep their behavior and
exception contracts. No second storage decoder, parser, production friend
assembly, or cross-package internal access is introduced.

public static TermInfoDatabaseCatalog InspectDirectoryBounded(
    string root,
    TermInfoDatabaseCatalogReadOptions? options = null,
    CancellationToken cancellationToken = default);

`TermInfoDatabaseCatalogLimitException : Exception` has this public constructor:
`(string sourcePath, string limitName, long limit, Exception? innerException = null)`
and get-only `string SourcePath`, `string LimitName`, `long Limit` properties.
Its message is explanatory, not a machine contract. Exception construction
validates a fully qualified nonblank path, a known limit name, and a positive
limit. The bounded method normalizes its input path before constructing failures.

The new method returns the **existing physical model**, including invalid-placement
entries and old duplicate-canonical semantics. Only the later Catalogs adapter
filters invalid publications. A distinct method name avoids making existing
calls such as `InspectDirectory(root, null)` ambiguous.

## 3. Catalogs public surface

Namespace `Icod.TermInfo.Catalogs`. The complete planned surface has **11 public
types**: seven sealed classes and four enums. UC01 introduces the ten model and
option types; UC04 adds the reader. Public result constructors are not exposed.
The small lower-layer additions are two Inspection types plus one method and
two BerkeleyDb types plus one method, not additions to Runtime.

### Inputs and reader

```csharp
public enum TerminalCatalogSourceKind {
    ConventionalDirectory = 0, BerkeleyDbHash = 1
}
public sealed class TerminalCatalogSource {
    public TerminalCatalogSource(string path, TerminalCatalogSourceKind kind);
    public string Path { get; }
    public TerminalCatalogSourceKind Kind { get; }
}
public sealed class TerminalCatalogReadOptions {
    public TerminalCatalogReadOptions(
        CompiledTermInfoParserOptions? parserOptions = null,
        int maximumCandidateCount = 131_072,
        int maximumEntryCount = 65_536,
        int maximumIssueCount = 4_096,
        long maximumParsedBytes = 67_108_864,
        int maximumDatabaseSize = 67_108_864,
        int maximumRecordCount = 65_536,
        int maximumIndexHops = 16,
        long maximumDecodedBytes = 67_108_864);
    // Get-only properties: ParserOptions plus all eight numeric arguments
    // with PascalCase names and the same types.
}
public sealed class TerminalCatalogReader {
    public TerminalCatalogReader(TerminalCatalogSource source,
        TerminalCatalogReadOptions? options = null);
    public TerminalCatalogSource Source { get; }
    public TerminalCatalog Read();
    public TerminalCatalog Read(CancellationToken cancellationToken);
}
```

Constructor validation follows parameter order. Null path/source throws
`ArgumentNullException`; empty/whitespace path throws `ArgumentException`;
undefined enums and invalid numbers throw `ArgumentOutOfRangeException`.
Source checks path text, then kind, then `Path.GetFullPath`; it does no I/O.
All counts/byte limits are positive; hops is inclusive `0..1024`. Parser limits
retain Runtime's inclusive `1..16_777_216` range and `1_048_576` default.
No cross-budget inequalities are required: a smaller aggregate than one entry
is useful for deliberate rejection. Null options means defaults. Every options
object snapshots parser options; readers snapshot options. No public constants,
builders, setters, async API, lazy enumeration, or equality policy are added.

`Read` checks cancellation before I/O. Input source kind is explicit. Relative
paths resolve when the source is constructed, not against a later current
directory. The method does not consult environment variables, provider search
paths, suffixes, or fallback locations.

### Results

```csharp
public enum TerminalCatalogEntryKind { Canonical = 0, Alias = 1 }
public enum TerminalCatalogStatus {
    Complete = 0, Partial = 1, Missing = 2,
    UnsupportedSource = 3, Unavailable = 4, InvalidStore = 5
}
public enum TerminalCatalogIssueKind {
    MalformedEntry = 0, InvalidPlacement = 1, PermissionFailure = 2,
    IoFailure = 3, LinkSkipped = 4, DuplicatePublication = 5,
    InvalidHashedStore = 6, UnsupportedSource = 7, MissingSource = 8
}
```

| Sealed class | Get-only properties |
| --- | --- |
| `TerminalCatalog` | `TerminalCatalogSource Source`, `TerminalCatalogStatus Status`, `IReadOnlyList<TerminalCatalogEntry> Entries`, `IReadOnlyList<TerminalCatalogIssue> Issues`, `IReadOnlyList<string> DuplicatePublicationNames`, `bool HasIssues` |
| `TerminalCatalogEntry` | `string PublicationName`, `TerminalCatalogEntryKind Kind`, `TerminalDescription Terminal`, `string SourcePath`, `string? EntryPath` |
| `TerminalCatalogIssue` | `TerminalCatalogIssueKind Kind`, `string SourcePath`, `string? EntryPath`, `string? PublicationName`, `string Message` |

`SourcePath` is the requested root/file, not a synthetic locator. Directory
entries use their real absolute `EntryPath`; hashed entries have null `EntryPath`
and use `PublicationName` as the logical key. Issues may identify a subdirectory
in `EntryPath`; root/whole-store issues use null. Human-readable messages are not
stable codes and contain no raw terminal capability bytes.

Internal constructors take properties in table order; the catalog constructor
takes `IEnumerable<T>` inputs for its three lists and derives `HasIssues`.
Constructors copy collections, reject null elements, validate enum/path/name
invariants, and retain immutable Runtime descriptions. Catalog construction
sorts lists. Adapters derive and budget duplicate names/issues before constructing
results; public callers cannot construct inconsistent results. Its internal signature is
`(TerminalCatalogSource source, TerminalCatalogStatus status,
IEnumerable<TerminalCatalogEntry> entries, IEnumerable<TerminalCatalogIssue> issues,
IEnumerable<string> duplicatePublicationNames)`.
Production adapters enforce budgets before invoking result construction; the
constructor is internal, not a new public unbounded-input API. UC01 unit fixtures
exercise it through test-only internals access.

Entry constructors require a nonblank publication name, a non-null terminal,
canonical/alias membership matching the kind, an absolute source path, and a
null or absolute entry path. Issue constructors require a defined kind, absolute
source path, null or absolute entry path, null or nonblank publication name, and
a nonblank message. Catalog construction requires every contained source path
to equal `Source.Path` ordinally and entry-path nullability to match the source
kind. Complete requires no issues; Partial requires at least one issue; Missing,
UnsupportedSource, Unavailable and InvalidStore require no entries and at least
one issue. Supplied duplicate names must be distinct and match the repeated
publication groups; the adapter supplies exactly one duplicate issue per group.

The seventh class is `TerminalCatalogLimitException : Exception`, with public
constructor `(TerminalCatalogSource source, string limitName, long limit,
Exception? innerException = null)` and get-only `Source`, `LimitName`, `Limit`.
It validates non-null source, one of the common limit names in section 5, and a
positive limit except that `MaximumIndexHops` permits zero. It never contains a
partial catalog. Lower typed limit failures are retained as its inner exception.

## 4. Identity, status, and ordering

Directory adapters exclude physical entries carrying `InvalidPlacement` at the
same exact ordinal path. Other physical parsed entries use the basename as
publication name, classified by exact canonical/alias membership. Preserve the
existing platform-aware *layout* rules; terminal names remain ordinal on every
platform. Do not normalize Unicode or manufacture rows from alias declarations.

Duplicate publication groups retain every occurrence. Add one
`DuplicatePublication` issue per repeated publication name, with null entry path,
source root, and that name; expose distinct sorted names in the duplicate list.
Different aliases pointing to the same canonical name are not duplicates.
Duplicates do not select winners or compare descriptions. They count as issues
and make the unified catalog partial. A hashed duplicate key is invalid data,
not a partial duplicate group.

| Observation | Unified status | Entries / issues |
| --- | --- | --- |
| Readable empty or wholly valid source | Complete | Observed entries; no issues |
| Directory candidate errors, skipped links, or duplicate publications | Partial | Valid observed publications plus typed issues, possibly zero entries |
| Root missing at initial acquisition | Missing | Empty; one `MissingSource` issue |
| Requested directory is a file, or requested hashed source is a directory | UnsupportedSource | Empty; one `UnsupportedSource` issue |
| Root cannot be inspected / enumerated at all | Unavailable | Empty; permission or I/O issue |
| Root enumeration fails after yielding candidates | Partial | Retain acquired directory candidates and an I/O/permission issue |
| Any malformed or unsupported hashed bytes/envelopes/compiled entry | InvalidStore | Empty; one `InvalidHashedStore` issue |
| Hashed I/O fails during acquisition | Unavailable | Empty; permission or I/O issue |
| Argument error / cancellation / bounded resource overrun | Exception | No result |

Unsupported **source kind** is distinguishable from invalid hashed **data**.
Malformed versus unsupported hashed content deliberately shares one issue code:
the released lower-layer errors cannot reliably separate them. This refines the
roadmap's initial diagnostic ambition without adding a public format taxonomy.
Do not infer content classification from an exception's English message.

Known lower format exceptions are handled only around the hashed acquisition
call. Catch typed budget failures before I/O handling. Never blanket-catch
`Exception`, `ArgumentException`, or allocation/programming errors. A directory
file disappearing after discovery is a candidate I/O issue, not a missing root.
If a root disappears before any observations, report Missing; after observations,
report Partial with an I/O issue. Source replacement does not imply a snapshot.

Entry order is ordinal `PublicationName`, then ordinal `EntryPath ?? SourcePath`,
then numeric kind. Issue order is ordinal `EntryPath ?? SourcePath`, numeric kind,
ordinal `PublicationName ?? ""`, then ordinal message. Duplicate names are
ordinal. Sorting is deterministic for equivalent observations, not across
different host error messages or concurrent source mutations.

Explicit root symlinks/junctions are allowed, matching current acquisition.
Directory child links/reparse points are skipped and reported, never traversed.
Hard-linked regular files are separate publication occurrences. This is not a
filesystem security sandbox: path replacement races and cancellation of a
blocking OS call are not guaranteed to be prevented.

## 5. Budget and allocation contract

All maxima are inclusive. Check cancellation, then reserve budget, then allocate
or retain the bounded item. Budget arithmetic compares against remaining capacity
before addition so `long.MaxValue` configurations cannot overflow. No silently
truncated success is returned. No automatic retries or budget refunds occur.

| Common limit name | Default | Counting / enforcement point |
| --- | --- | --- |
| `MaximumCandidateCount` | 131,072 | Every child yielded while enumerating the root or an eligible immediate directory, including ignored names and nested directories; reserve before retaining its path |
| `MaximumEntryCount` | 65,536 | Directory: retained physical parses, even if misplaced, with a conservative capacity check before the next parse; hashed: actual publication rows before resolution/append |
| `MaximumIssueCount` | 4,096 | Every retained acquisition issue plus one issue per duplicate publication group; reserve before append |
| `MaximumParsedBytes` | 67,108,864 | Directory: full length of every candidate admitted for reading, charged before buffer allocation, including malformed inputs and copies; hashed: compiled payload length once per storage key before parsing, including orphan storage records |
| `MaximumEntrySize` | 1,048,576 | Directory compiled file or hashed compiled payload length before parse/allocation; Runtime permits up to 16,777,216 |
| `MaximumDatabaseSize` | 67,108,864 | Hashed image length before allocating image |
| `MaximumRecordCount` | 65,536 | Physical hashed key/value pairs, including orphan storage and publication/index records, before extracting the next pair |
| `MaximumIndexHops` | 16 | Followed links per hashed publication; range 0..1024 |
| `MaximumDecodedBytes` | 67,108,864 | Sum of decoded hashed key/value lengths, charged before each item allocation, including repeated references to overflow storage |
| `MaximumStoredItemSize` | parser maximum + 1 | Existing hashed key/value extraction cap, including marker; derived from parser option, not an additional public setting |

Inspection exception names are its first five applicable limits above.
BerkeleyDb exception names are `MaximumDatabaseSize`, `MaximumRecordCount`,
`MaximumIndexHops`, `MaximumDecodedBytes`, `MaximumParsedBytes`,
`MaximumEntrySize`, `MaximumStoredItemSize`, and `MaximumPublicationCount`.
The latter maps to common `MaximumEntryCount`; its numeric value is unchanged.
Catalogs accepts only the ten common names in the table.

Directory bounds are intentionally conservative: invalid-placement entries still
consume the physical entry budget before filtering. Aliases stored as separate
files consume bytes separately. Hashed aliases reuse descriptions but consume
physical-record, decoded-byte, and publication budgets. Limits measure input
work and retained items, **not exact CLR heap bytes**. Object/string/index/copy
overheads are bounded functions of these counts and bytes, not included in the
numeric byte totals. A small decoded/parsed budget does not reduce the separate
maximum image allocation.

### Bounded directory algorithm

1. Validate/snapshot inputs, check cancellation, inspect root attributes.
2. Lazily enumerate root children with `Directory.EnumerateFileSystemEntries`;
   count all yielded children before filtering. Collect only eligible immediate
   subdirectories within the candidate budget and sort that bounded list.
3. Enumerate each eligible directory's immediate children lazily, using the same
   cumulative candidate budget. Do not recurse. Collect bounded candidate paths
   and sort them before processing. Root ordinary files and nested directories
   are counted but ignored; inspect attributes without opening child links.
4. For each file, open once, obtain length, check per-entry size, check physical
   entry capacity, reserve aggregate parsed bytes, allocate/read, check for
   length change, and call Runtime parser. Charge the retained-entry counter
   only after a successful parse; conservatively fail at the earlier capacity
   check once full, even if the next candidate might have been malformed.
5. Preserve old physical-model placement diagnostics and duplicate-canonical
   computation. Reserve each issue before append. Freeze the bounded result.

Lazy enumerators are disposed even when `MoveNext` throws. A failure before any
root observations returns unavailable/missing as appropriate; a failure after
observations retains only observed candidates and adds an issue. Candidate N+1
may be yielded to detect overrun, but is never retained. No call to `GetFiles`,
`GetDirectories`, unbounded `ToArray`, or `OrderBy` precedes candidate accounting.
Legacy `InspectDirectory` keeps its traversal path; share file parsing, placement,
issue construction and finalization helpers, not a new parser implementation.

### Bounded hashed algorithm

Reserve the image size, read in chunks with cancellation, and repeat the existing
stability verification with cancellation checkpoints. Validate an item's encoded
length using the existing inline/overflow rules before reserving decoded bytes
and allocating its output. Check records before item extraction; check ncurses
publication capacity before resolution; check distinct storage payload bytes
before parsing/caching. Check hops before following each link. Malformed layout
still takes its existing format path; a valid length exceeding a configured
budget takes the typed limit path. Keep legacy policy/error selection explicit.

Directory and hashed sorting check cancellation before and after the bounded
sort. Enumeration/read/normalization loops check at each item or chunk. Synchronous
OS calls themselves are not interruptible. Reads retain no handles after return
and no cross-call cache. Multiple reads on the same reader have independent state.

## 6. Acceptance examples and tests

| Fixture | Required observation |
| --- | --- |
| `sample` declares `a`,`b`; only canonical file/key exists | One canonical publication; aliases remain declarations |
| Canonical plus separately published `a`,`b` | Three rows, kinds canonical/alias/alias, no duplicate publication issue |
| Literal and hex copies of `sample` | Two retained rows, one duplicate name and one issue, Partial |
| Misplaced valid file plus valid sibling | Bad publication excluded from unified rows; issue retained; old Inspection still exposes both physical parses |
| Child alias symlink plus canonical file | Link skipped/issue retained; alias not manufactured; Partial |
| Valid hashed publication plus malformed orphan storage | InvalidStore, no partial hashed rows |
| Cyclic/missing hashed target or mismatched identity | InvalidStore, no rows, no exception-message classification |
| Exact candidate/entry/issue/byte/record/hop maximum | Accepted when all other limits permit it |
| Next item/byte/link beyond any maximum | Typed limit exception before associated allocation/retention |
| Canceled before read or during discovery/image verification | OperationCanceledException, no result; handles/enumerators disposed |
| Different culture or input enumeration order | Same sorted observations for equivalent, unchanged source contents |

UC01 proves model immutability, enum/default validation, bounded directory
acquisition, and exact legacy reconstruction. UC02 maps physical observations;
UC03 adds the bounded hashed method and adapter; UC04 provides common dispatch
and parity tests. UC05 covers OS/races/aggregate adversarial tests. UC06/UC07 own
consumer qualification and final release evidence. The UC01 plan is
[here](superpowers/plans/2026-09-27-uc01-unified-catalog-foundation.md).

## 7. Compatibility and review decision

Freeze additive manifests independently: remove the two Inspection types and
`InspectDirectoryBounded` to reconstruct the 1.14 Inspection surface; remove
the two BerkeleyDb types and `ReadBounded` to reconstruct the 1.16 twelve-type
surface. Then run the existing historical reconstruction chains unchanged.
Old API baselines and JSON v1–v6 files must not be regenerated to hide changes.
All APIs and package dependency groups must match across the three TFMs.

The reviewed source files and test expectations substantiate the design; they
do not constitute an implementation experiment or a passing 1.17 qualification.
The package placement, exact proposed signatures, opt-in lower-layer methods,
budget accounting, and combined invalid-hashed diagnostic are ready for review.
UC00 remains awaiting that review; UC01 has not started.
