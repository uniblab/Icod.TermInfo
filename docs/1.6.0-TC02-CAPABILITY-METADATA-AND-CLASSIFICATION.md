# Icod.TermInfo 1.6.0 TC02 — Capability Metadata and Classification

**Development version:** `1.6.0-Alpha-2`
**Tranche:** TC02
**Status:** Implementation patch

## Objective

TC02 gives `Icod.TermInfo.Termcap` one authoritative semantic view of historical
two-character capability codes without converting a parsed entry or resolving
`tc=` inheritance.

The standard mapping authority remains the frozen Runtime catalog:

```text
StandardCapabilityCatalog
    -> StandardCapabilityMetadata<TCapability>.TermcapCode
    -> BooleanCapability / NumericCapability / StringCapability
```

The Termcap package does not copy the Runtime's standard capability identities,
short names, long names, binary indexes, or value kinds into a second maintained
table.

## Public classification surface

TC02 adds:

```text
TermcapCapabilityCatalog
TermcapStandardCapabilityMapping
TermcapCapabilityClassifier
TermcapCapabilityClassificationResult
TermcapCapabilityClassification
```

`TermcapCapabilityCatalog` derives one canonical mapping for every entry exposed
by the Runtime `StandardCapabilityCatalog`. Each mapping retains the exact Runtime
managed enum identity together with its terminfo short/long names, compiled-table
index, value kind, and canonical termcap code.

`TermcapCapabilityClassifier` operates on a parsed `TermcapSourceField` and
reports mapping state without changing the field or constructing a new terminal
description.

## Classification states

A field is classified as one of:

```text
Standard
ObsoleteStandard
ObsoleteAlias
Ambiguous
Unmapped
Reference
```

`ObsoleteStandard` identifies the historical termcap-only compatibility
capabilities which the selected Runtime metadata baseline retains with `OT...`
terminfo short names, such as termcap `bs` -> terminfo `OTbs`.

`ObsoleteAlias` is reserved for the direct obsolete non-standard translations
listed by the selected ncurses `captoinfo` compatibility baseline. TC02 records
only alias code -> canonical termcap code -> origin. The target semantic identity
is then resolved through `StandardCapabilityCatalog`; the alias table therefore
does not become a second standard capability catalog.

The adopted direct alias set is the AT&T, XENIX, Tektronix, and IRIX table from
ncurses `captoinfo(1m)`. More complex compatibility transformations, including
XENIX box-drawing composition into `acs_chars`, remain conversion policy for
TC04 rather than classification aliases.

## Type expectations

For a unique mapping, classification exposes both:

- the value kind implied by active source syntax;
- the value kind required by the Runtime capability identity.

A source field such as `co#80` therefore classifies as the Runtime numeric
`Columns` capability with no mismatch, while syntactically valid `co` remains
mapped to `Columns` but reports a Boolean-vs-numeric value-kind mismatch.

Cancellation and disabled fields retain their semantic target mapping but do not
invent a source value kind. `tc=` is classified separately as `Reference`.

TC02 does not turn a mismatch into a parser error because parsing remains
syntactic. Later resolution/conversion policy can decide how to report or reject
the semantic mismatch while retaining source provenance.

## Unknown and ambiguous codes

Unknown or vendor codes remain `Unmapped`; the original `TermcapSourceField`
remains available unchanged.

The catalog groups mappings by exact ordinal two-character code. If a selected
compatibility baseline ever assigns more than one Runtime identity to the same
code, the classifier reports `Ambiguous` and exposes every candidate in stable
order rather than silently selecting one.

## TC01 corrective closure

The TC01 branch state contained one C# scope error in `DecodeString`: the control
escape path declared a local named `translated` while the enclosing loop later
declared another `translated` local. TC02 renames the inner value and restores
compilation before adding the classification layer. No parser semantics change.

## Explicit non-goals

TC02 does not:

- resolve `tc=` inheritance;
- apply cancellation or inherited precedence;
- convert a termcap entry into `TerminalDescription`;
- synthesize `acs_chars` from vendor box-drawing capabilities;
- read `TERMCAP`, `TERMPATH`, files, or process-global environment;
- add conversion commands or router behavior;
- modify Runtime, Source, Compiler, or Inspection public APIs.

## TC02 gate

TC02 is complete when:

- the TC01 parser builds on all three target frameworks;
- every Runtime standard capability has a canonical termcap mapping derived from
  the Runtime catalog;
- Boolean, numeric, and string expectations are observable;
- Runtime `OT...` compatibility capabilities and the adopted obsolete alias table
  are explicit;
- unknown/vendor fields remain explicit;
- mapping order and ambiguity behavior are deterministic;
- no conversion or inheritance behavior is introduced.
