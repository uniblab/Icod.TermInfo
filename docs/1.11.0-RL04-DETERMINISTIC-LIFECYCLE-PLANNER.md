## Public contract

RL04 adds the protocol-neutral bounded lifecycle planning surface:

```text
PersistentRasterLifecycleRequest
PersistentRasterLifecyclePlanStatus
PersistentRasterLifecyclePlanStep
PersistentRasterLifecyclePlanIssue
PersistentRasterLifecyclePlan
PersistentRasterLifecyclePlanner
```

The plan status vocabulary is frozen as:

```text
Success       = 0
Indeterminate = 1
Impossible    = 2
```

`PersistentRasterLifecycleRequest.MaximumSupportedPlacementCount` is `256`.

## Planning semantics

Planning consumes one RL03 `PersistentRasterLifecycleProfile` and one validated semantic request. It produces ordered RL01 operations only; it does not create or expose protocol identifiers.

Supported requirements produce ordinary plan steps. `Unknown` or `Contradicted` requirements remain admissible but make the plan `Indeterminate`, add structured issues, and mark affected steps as requiring consumer-owned runtime verification. `Unsupported` requirements make the plan `Impossible` and suppress executable steps.

Ephemeral raster display never satisfies persistent upload. Acknowledged upload is represented as a requirement on `UploadResource`, not as a new wire/protocol operation.

Multiple placement requests produce one deterministic `CreatePlacement` step per placement. When ordinary placement creation is supported but multiple-placement support is unknown or contradicted, the first placement remains ordinary and only additional placements require runtime verification.

Cleanup order is deterministic: placement deletion precedes resource deletion when both are requested.

## Determinism and bounds

Request validation rejects empty requests, invalid placement counts, mixed ephemeral/persistent requests, and acknowledgement requirements without upload. Plan collections are immutable snapshots, step sequence indices are contiguous and zero-based, and planning is culture-independent and repetition-independent.
