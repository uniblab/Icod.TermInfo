# Icod.TermInfo 1.8.0 RP01 - Planning Contract and API Foundation

**Development version:** `1.8.0-Alpha-1`
**Tranche:** RP01
**Status:** implementation contract
**Published baseline:** `1.7.0`
**Next tranche:** RP02 - Zero- and Single-Parent Planning

## Objective

RP01 establishes the public and internal contract for bounded relative-source
planning without implementing plan search. Planning remains separate from the
frozen 1.7 explicit synthesizer:

```text
explicit ordered parents -> TerminalDescriptionSourceSynthesizer
candidate parent positions -> TerminalDescriptionSourcePlanner
```

The planner will eventually select ordered parents and delegate source production
unchanged to the synthesizer. RP01 validates and snapshots planning inputs,
freezes score and result semantics, and then throws `NotSupportedException`.
Operational zero- and single-parent evaluation begins in RP02.

The production dependency graph remains:

```text
Icod.TermInfo.Inspection
    -> Icod.TermInfo.Source
    -> Icod.TermInfo
```

Inspection acquires no production Compiler or Termcap dependency. Runtime,
Source, Compiler, Termcap, and the stable 1.7 synthesis members remain frozen.

## Public planning surface

RP01 adds four public Inspection types:

```text
TerminalDescriptionSourcePlanningOptions
TerminalDescriptionSourcePlanningScore
TerminalDescriptionSourcePlan
TerminalDescriptionSourcePlanner
```

Candidate input and selected-parent output reuse the frozen
`TerminalDescriptionSourceSynthesisParent` type. A second candidate wrapper would
duplicate the already reviewed pairing of exact `UseName` source identity with
an effective `TerminalDescription` and would create conversion and API-regret
cost without adding semantics.

The planner exposes three deliberate overloads:

```csharp
TerminalDescriptionSourcePlanner.Plan( target, candidates );
TerminalDescriptionSourcePlanner.Plan( target, candidates, options );
TerminalDescriptionSourcePlanner.Plan(
	target,
	candidates,
	options,
	cancellationToken
);
```

Options are non-null in explicit-policy overloads. The first overload creates the
canonical policy. The token overload is the sole cancellation seam, avoiding
mutable token state in the options object.

## Candidate identity and snapshot contract

Every supplied sequence position is a distinct candidate. The planner does not
deduplicate by `UseName`, effective description, reference equality, canonical
name, alias, or capability content. Equal values at distinct positions remain
distinct deterministic tie-break inputs.

The caller-owned sequence is enumerated at most once. RP01 snapshots accepted
positions into an immutable list before any future plan evaluation. Validation
occurs in this order:

1. validate target, sequence, options, and scalar option construction;
2. observe cancellation before enumeration;
3. enumerate in caller order;
4. observe cancellation at each item boundary;
5. reject a null item;
6. exclude an obvious self-reference;
7. retain the accepted candidate position or reject the first overflow item;
8. observe cancellation after enumeration.

An obvious self-reference is a `UseName` which equals the target canonical name
or one of its aliases under ordinal, case-sensitive comparison. Excluded self
references do not consume the accepted-candidate limit. The implementation stops
on the first non-self item beyond the limit, which is the minimum evidence needed
to prove overflow.

The planner cannot infer source-graph cycles from effective descriptions. Source
graphs and provenance not represented by candidate values remain caller-owned.

## Planning options and bounds

`TerminalDescriptionSourcePlanningOptions` is immutable and retains the supplied
immutable synthesis options by reference. Its canonical policy is:

| Option | Default | Supported maximum |
| --- | ---: | ---: |
| Candidate positions | 64 | 256 |
| Selected ordered parents | 2 | 256 |
| Evaluated plans | 4,097 | 1,000,000 |
| Generated source length | 4,194,304 UTF-16 code units | 67,108,864 UTF-16 code units |
| Allow non-exhaustive result | false | true |

The candidate maximum matches the frozen synthesis parent hard maximum. The
selected-parent hard maximum also reuses that synthesis bound so planning cannot
promise a parent list which the synthesizer must reject.

The default evaluated-plan count is exact combinatorial evidence for exhaustive
zero-, one-, and ordered two-parent enumeration over 64 candidates:

```text
1 zero-parent plan
+ 64 one-parent plans
+ (64 * 63) ordered two-parent plans
= 4,097 plans
```

The default therefore covers the roadmap's common search space without silently
returning a bounded result. Larger or deeper spaces require a caller-selected
policy. A budget-limited result is permitted only when
`AllowNonExhaustiveResult` is true, and its `IsExhaustive` value must be false.

The generated-source bounds reuse the frozen Source lexer bounds. This
coordinates future parse/resolve verification with a reviewed existing resource
policy rather than inventing a second source-length scale. Source length is
measured in UTF-16 code units for this bound; score size remains UTF-8 bytes.

All options validate at construction. The selected-parent limit cannot exceed
the candidate limit or the selected synthesis options' parent limit. At least one
plan evaluation is required because the zero-parent baseline is always a real
candidate when it can be represented safely.

## Frozen lexicographic score

`TerminalDescriptionSourcePlanningScore` is immutable and compares components in
this exact lexicographic order:

1. fewer emitted local capability directives;
2. fewer emitted cancellations;
3. fewer selected ordered parents;
4. fewer UTF-8 bytes in generated source;
5. lexicographically earlier selected candidate-index sequence.

A Boolean, numeric, string, or extended declaration counts as one local
directive. A standard or extended cancellation counts as both one local
directive and one cancellation. Identity header fields do not count. Parent
references are represented by the parent-count component.

UTF-8 byte count excludes a byte-order mark and observes the deterministic LF
source contract. Candidate indices are zero-based positions in the accepted
post-self-exclusion snapshot. They are compared as integers without culture.

The score constructor rejects negative counts, a cancellation count greater than
the local-directive count, a candidate-index count different from the parent
count, negative indices, and repeated indices. It copies the supplied sequence.

The type implements `IComparable<TerminalDescriptionSourcePlanningScore>` and
`IEquatable<TerminalDescriptionSourcePlanningScore>`. Equality is component
equality, including the complete candidate-index sequence. Comparison with null
follows normal .NET ordering: every score sorts after null.

## Immutable plan result

`TerminalDescriptionSourcePlan` is produced only by the planner and exposes:

- `SelectedParents`, copied in exact emitted `use=` order;
- `Source`, the deterministic generated LF source;
- `Score`, the frozen score and selected candidate-index evidence;
- `EvaluatedPlanCount`, including valid and rejected plans actually evaluated;
- `IsExhaustive`, true only when all legal plans under the active limits were
  evaluated;
- `CandidateCount`, the accepted non-self snapshot size.

These properties are the structured planning evidence. RP01 deliberately avoids
an untyped string evidence collection, mutable search-node exposure, or another
public diagnostic hierarchy before an operational planner demonstrates a need.

The result copies its parent sequence and validates internal consistency against
the score and considered candidate count. It does not expose mutable arrays.

## Zero-parent baseline

The zero-parent plan is plan depth zero and is enumerated before every parented
plan. It is valid when the frozen synthesizer can produce complete effective
source within the active planning and synthesis bounds. It participates in the
same score and may win.

RP01 does not evaluate this baseline. RP02 makes zero- and single-parent planning
operational together so baseline comparison and first parent selection cannot
acquire different undocumented scoring behavior.

## Exhaustive and bounded reporting

`IsExhaustive` is evidence, not an optimization hint. It may be true only when
every legal plan within the accepted candidate snapshot and selected-parent limit
was evaluated. A budget-limited result must report false and may be returned only
when the options explicitly permit it.

Exhaustive enumeration order beginning in RP02 is frozen as:

```text
zero parents
one parent in candidate-index order
two ordered parents in lexicographic candidate-index order
later depths in the same order
```

Wall-clock time, task scheduling, hash iteration, and culture never terminate or
order a search. The plan-evaluation count is the sole budget.

## Exception and cancellation contract

Normal candidate inferiority is not exceptional. Public planner operations use:

- `ArgumentNullException` for null required arguments;
- `ArgumentException` for null candidate items or candidate overflow;
- `ArgumentOutOfRangeException` while constructing invalid options or scores;
- `InvalidOperationException` when exhaustive planning is required but the active
  budget cannot cover the legal plan space, or when no valid representable plan
  exists;
- `OperationCanceledException` for caller cancellation;
- existing synthesis argument, representation, and resource exceptions when a
  whole request cannot be represented;
- `NotSupportedException` only for the temporary RP01 operational boundary.

Future per-plan synthesis failures caused by candidate inferiority are rejected
plans, not whole-request exceptions, unless the target or policy makes every plan
unrepresentable.

## RP01 gate

RP01 is complete when:

- the coordinated development version is `1.8.0-Alpha-1`;
- the exact frozen 1.7 Inspection baseline remains unchanged;
- the four additive planning types are present on all target frameworks;
- every public planning member has contract tests and XML documentation;
- options and scores reject invalid construction deterministically;
- candidate input is enumerated at most once and copied immutably;
- duplicate/equivalent positions remain distinct;
- obvious ordinal target self-references are excluded;
- overflow inspection stops after the first item proving overflow;
- score comparison follows the frozen five-component order;
- plan results distinguish exhaustive from budget-limited search;
- cancellation is observed at deterministic snapshot boundaries;
- Runtime, Source, Compiler, and Termcap APIs remain frozen;
- Inspection retains only Runtime and Source production dependencies;
- no operational search behavior exists outside the written RP02 contract.

RP02 may then implement the zero-parent baseline and single-parent enumeration
against this frozen request, score, result, exception, and cancellation contract.
