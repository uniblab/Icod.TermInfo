# Icod.TermInfo 1.4.0 T11 — Differential Validation, Hostile Input, and Freeze

**Development version:** `1.4.0-Alpha-11`

## Objective

T11 is the final implementation tranche in the 1.4 program. It adds no new
command semantics and no new reusable-library public API. Its purpose is to
prove that the T01-T10 command suite is corpus-backed, bounded under hostile
input, API-frozen, and structurally ready for the separate stable-release
closure step.

## Differential corpus

Normal CI continues to use the checked-in compiled-terminfo corpus under:

```text
tests/Icod.TermInfo.Tests/fixtures/compiled-terminfo/
```

That corpus records both source descriptions and compiled entries generated by
the pinned ncurses fixture environment documented in the fixture README. Normal
tests do not invoke host `tic`, `infocmp`, or `toe`, do not install ncurses, and
do not depend on the uncontrolled host terminfo database.

Developer-only corpus regeneration remains an explicit maintainer operation.
Changing fixture provenance or moving to a newer pinned ncurses environment is a
reviewed corpus change, not an implicit CI dependency.

## `tic` differential validation

T11 runs the checked-in source/compiled pairs through the real managed `tic`
command:

```text
checked-in .ti source
        |
        v
    Icod tic
        |
        v
temporary conventional database
        |
        v
Icod Runtime parse
        |
        +-----------------------------+
                                      |
checked-in ncurses compiled entry --> semantic comparison
```

The comparison uses `TerminalDescriptionComparer`. Byte-for-byte identity is not
required unless another frozen contract explicitly requires it.

The differential cases include:

- legacy compiled format;
- wide numeric compiled format;
- standard Boolean/numeric/string capabilities;
- cancellations;
- padding-bearing strings;
- high-byte string data;
- ncurses extended Boolean/numeric/string capabilities.

## `infocmp` differential validation

T11 installs the checked-in ncurses-produced compiled entries into controlled
conventional database roots, acquires them through the real managed `infocmp`,
renders effective source with `-x`, reparses that source through the Source
engine, and compares the resulting effective description with the original
compiled entry semantically.

This validates the external-corpus path for:

- explicit database acquisition;
- canonical identity;
- aliases and descriptions;
- standard capability rendering;
- extended capability rendering;
- effective-source reparsing.

The established T06/T07/T10 command tests remain the authoritative coverage for
`-d`, `-c`, `-n`, width/sort controls, comparison database selection, quiet
presentation, and CLI conflict handling.

## `toe` differential validation

T11 constructs a controlled conventional database tree from the same checked-in
ncurses-produced entries and runs the real managed `toe -s` command twice.

The expected report is derived from parsed compiled identities/descriptions and
is compared exactly with `toe` output. The repeated run must be identical.

This external-corpus gate validates:

- canonical identity from compiled content rather than filenames;
- description reporting;
- controlled-root selection;
- deterministic ordinal sorting;
- repeatable output.

The established T08/T09/T10 tests retain coverage for multiple roots, `-a`,
headings, duplicate visibility/semantic markers, malformed entries, source
dependency graphs, cycles, missing parents, and command-line hardening.

## Hostile-input validation

T11 treats the hostile-input gate as a cumulative suite contract rather than
duplicating lower-layer tests in command projects.

The full solution test matrix already exercises the bounded contracts for:

```text
argument fuzzing and unsupported options
option-value boundaries
very large source documents
very long terminal/source identities
path traversal attempts
malformed conventional directory trees
truncated and oversized compiled entries
duplicate names and aliases
deep inheritance graphs
inheritance cycles
permission and I/O failures
cancellation
filesystem replacement/failure cases
```

T11 adds an explicit command-boundary malformed-UTF-8 test for `tic`. The same
invalid byte sequence is submitted twice and must produce the same bounded
`TIC0005` failure without output or publication.

No hostile-input case is permitted to become an unbounded recursive traversal,
unbounded inheritance expansion, silent partial success, or host-dependent
diagnostic order.

## API freeze

Alpha-11 does not add library public API.

The release-readiness baseline remains:

```text
Runtime     docs/1.0.0-PUBLIC-API-BASELINE.txt
Source      docs/1.1.0-SOURCE-PUBLIC-API-BASELINE.txt
Compiler    docs/1.2.0-COMPILER-PUBLIC-API-BASELINE.txt
Inspection  docs/1.3.0-INSPECTION-PUBLIC-API-BASELINE.txt  (historical)
Inspection  docs/1.4.0-INSPECTION-PUBLIC-API-BASELINE.txt  (active/frozen)
```

All four reusable assemblies retain `AssemblyVersion` `1.0.0.0`, continue to
target `net8.0;net9.0;net10.0`, and retain their existing one-way dependency
graph. `Icod.CommandFramework` remains command-layer-only. Inspection retains no
production Compiler dependency.

## Artifact validation

T10 established six deterministic framework-dependent command-suite archives.
T11 adds `.github/scripts/verify-tool-archives.sh` and requires PR, main, and tag
CI to run it after archive construction and before archive upload.

The verifier requires exactly these six versioned archives:

```text
win-x64
win-arm64
linux-x64
linux-arm64
osx-x64
osx-arm64
```

For every archive it checks:

- safe relative archive member paths;
- `TOOL-SUITE.txt`;
- exact version, RID, `net10.0`, and framework-dependent deployment markers;
- `tic`, `infocmp`, and `toe` launchers;
- each command's managed assembly, `.deps.json`, and `.runtimeconfig.json`;
- Runtime, Source, Compiler, Inspection, and CommandFramework managed
  dependencies;
- root and per-command documentation;
- absence of `.pdb`, `.csproj`, and `.sln` payload files;
- executable command launchers in POSIX tar archives.

The coordinated package verifier continues to validate the four `.nupkg` and
four `.snupkg` artifacts. The release workflow continues to require fourteen
pre-checksum artifacts and fifteen final GitHub Release assets after adding
`SHA256SUMS.txt`.

## CI contract

T11 normal CI therefore proves:

```text
Windows / Linux / macOS solution build and tests
                +
four-package structural/API/package-consumer validation
                +
checked-in differential corpus
                +
six tool-suite archive builds
                +
six tool-suite archive structural verification
```

No normal CI leg requires native ncurses commands.

## Freeze boundary

T11 intentionally does not add:

- new `tic`, `infocmp`, or `toe` switches;
- termcap conversion;
- hashed/Berkeley DB support;
- global-tool packages;
- self-contained runtime bundles;
- NativeAOT;
- installer/signing/notarization work;
- new reusable-library public API.

Those remain post-1.4 work unless separately approved.

## Gate

T11 is complete when Alpha-11 passes the repository Staging/Release matrices on
Windows, Linux, and macOS, the differential command tests pass against the
checked-in corpus, all API/package gates remain exact, and the six archive
artifacts pass structural verification.

Stable `1.4.0` versioning, release-commit validation, tag creation, package
publication, final archive smoke execution, checksum publication, and GitHub
Release creation remain the separate **1.4.0 release closure** step.
