# Icod.TermInfo 1.11.0 RL02 — Lifecycle Evidence Model

**Development version:** `1.11.0-Alpha-2`  
**Tranche:** RL02  
**Published baseline:** `1.10.0`  
**Primary package:** `Icod.TermInfo.Inspection`  
**Status:** validated and frozen

## Objective

RL02 introduces immutable, protocol-neutral evidence values that can describe persistent-raster lifecycle facts without forcing a final support judgment.

The tranche deliberately separates **raw evidence** from **classification**. Evidence may be positive or negative, may originate from different provenance classes, and may coexist in contradictory forms. RL03 owns the deterministic mapping from those facts to `PersistentRasterLifecycleSupportStatus` values.

No live terminal probing, protocol execution, image/placement identity, runtime ownership, or cleanup behavior is introduced by RL02.

## Public additions

RL02 adds exactly four public types to `Icod.TermInfo.Inspection`:

```text
PersistentRasterLifecycleEvidenceSubject
PersistentRasterLifecycleEvidenceKind
PersistentRasterLifecycleEvidence
PersistentRasterLifecycleEvidenceOptions
```

Together with the two RL01 types, the explicitly approved 1.11 Inspection additions are recorded in `docs/1.11.0-INSPECTION-PUBLIC-API-ADDITIONS.txt`.

## Evidence subjects

The exact evidence-subject membership and numerics are:

```text
RasterDisplay         = 0
PersistentUpload      = 1
AcknowledgedUpload    = 2
PlacementCreation     = 3
MultiplePlacements    = 4
PlacementUpdate       = 5
PlacementDeletion     = 6
ResourceDeletion      = 7
```

This eight-dimensional subject vocabulary is intentionally distinct from the six RL01 lifecycle **operations**. `AcknowledgedUpload` and `MultiplePlacements` are semantic facts that affect classification and planning but are not standalone execution operations.

## Evidence kinds

The exact provenance-kind membership and numerics are:

```text
CapabilityDerived = 0
Declared          = 1
Verified          = 2
```

The numeric values are frozen identifiers, not an implicit sorting or precedence contract. RL03 defines evidence precedence explicitly; consumers must not infer policy merely from the integer values.

Semantics:

- `CapabilityDerived` identifies deterministic facts recognized from static terminal capability metadata.
- `Declared` identifies facts explicitly supplied by a caller without a live verification result.
- `Verified` identifies facts supplied by a caller as the result of verification performed outside `Icod.TermInfo`.

`Icod.TermInfo` itself does not own live terminal probing.

## Immutable evidence value

`PersistentRasterLifecycleEvidence` records:

```text
Subject
IsPositive
Kind
SourceLabel
SourceOrdinal
```

Construction rules are frozen as follows:

- `Subject` must be a defined `PersistentRasterLifecycleEvidenceSubject` value.
- `Kind` must be a defined `PersistentRasterLifecycleEvidenceKind` value.
- `SourceLabel` must be non-null and non-whitespace.
- `SourceLabel` is preserved exactly; RL02 does not trim, normalize, case-fold, or reinterpret it.
- `SourceOrdinal` must be non-negative.
- `IsPositive` is retained as a raw assertion and is not converted into a support status by RL02.

An evidence value therefore never contains a `PersistentRasterLifecycleSupportStatus` property.

## Snapshot contract

`PersistentRasterLifecycleEvidence.Snapshot(...)` creates a bounded immutable snapshot of an input sequence.

The canonical ordering is:

```text
1. SourceOrdinal ascending
2. Subject numeric value ascending
3. Kind numeric value ascending
4. IsPositive (false before true)
5. SourceLabel using StringComparer.Ordinal
```

The ordering is deterministic and culture-independent.

Snapshot semantics additionally freeze these rules:

- source enumeration is copied; later mutation of the source collection does not affect the snapshot;
- duplicate evidence values are retained rather than deduplicated;
- null input is rejected;
- null elements are rejected;
- no classification or contradiction resolution occurs during snapshotting;
- the returned list is read-only.

## Bounds

`PersistentRasterLifecycleEvidenceOptions` freezes these bounds:

```text
DefaultMaximumEvidenceCount   = 256
MaximumSupportedEvidenceCount = 4096
```

Caller-selected bounds must be within `1..4096` inclusive. Snapshot enumeration fails when the configured maximum would be exceeded.

These bounds are part of the release's deterministic resource policy and are not inferred from ambient machine capacity.

## Evidence versus classification

RL02 intentionally permits inputs such as:

```text
CapabilityDerived: PersistentUpload = positive
Declared:          PersistentUpload = negative
Verified:          PersistentUpload = positive
```

All three facts can coexist in one immutable snapshot. RL02 does not choose a winner and does not collapse them into `Supported`, `Unsupported`, or `Contradicted`.

RL03 will classify this evidence according to an explicit precedence policy while retaining the canonical evidence snapshot so that lower-precedence and contradictory facts remain inspectable.

## Deferred to RL03+

RL02 does not yet add:

- evidence precedence;
- final support-state classification;
- lifecycle profiles;
- planning requests or plan steps;
- database-set lifecycle composition;
- machine-readable lifecycle profile/plan documents.

RL03 begins the first deterministic interpretation of the frozen RL02 evidence model.
