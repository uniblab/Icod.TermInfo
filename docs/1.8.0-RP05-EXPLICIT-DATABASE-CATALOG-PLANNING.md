# Icod.TermInfo 1.8.0 RP05 - Explicit Database Catalog Planning

**Development version:** `1.8.0-Alpha-5`
**Roadmap tranche:** RP05
**Implementation base:** `1503afc7b81d10be4fd3c31cdc99e2c8f134e629`

## Purpose

RP05 composes the bounded relative-source planner with the existing Inspection
catalog. It adds explicit catalog orchestration without changing the frozen 1.4
catalog contract, the frozen 1.7 synthesizer, or the RP01 through RP04 score and
search contracts.

The operation remains opt-in and explicit:

```text
effective target
+ explicit TermInfoDatabaseCatalog
    -> validate complete catalog
    -> derive deterministic canonical candidates
    -> TerminalDescriptionSourcePlanner
    -> selected relative source
```

or:

```text
effective target
+ explicit conventional directory root
+ optional parser limits
    -> TermInfoDatabaseInspector.InspectDirectory
    -> complete catalog validation
    -> deterministic canonical candidates
    -> TerminalDescriptionSourcePlanner
```

Neither form performs implicit host discovery, reads Runtime discovery
environment variables, or searches platform default database locations.

## Public orchestration

RP05 adds two methods to the existing planner type:

```csharp
TerminalDescriptionSourcePlan plan =
	TerminalDescriptionSourcePlanner.PlanFromCatalog(
		target,
		catalog,
		planningOptions,
		cancellationToken
	);
```

and:

```csharp
TerminalDescriptionSourcePlan plan =
	TerminalDescriptionSourcePlanner.PlanFromDirectory(
		target,
		explicitRoot,
		planningOptions,
		parserOptions,
		cancellationToken
	);
```

The optional planning policy defaults to the RP04 bounded policy. Directory
planning passes the parser options and cancellation token directly through the
existing explicit catalog inspector before candidate preparation.

No new public type is introduced. `TermInfoDatabaseCatalog` and its entries,
issues, duplicate-name evidence, and root-state contract remain unchanged.

## Completeness gate

Planning is permitted only when the catalog is:

- `TermInfoDatabaseCatalogKind.ConventionalDirectory`; and
- issue-free.

A missing root, unsupported store, unavailable root, malformed entry, invalid
placement, permission failure, I/O failure, or skipped link prevents planning.
The operation throws before evaluating a plan and therefore cannot label a
partial catalog candidate universe exhaustive.

An empty, issue-free conventional directory is complete. It supplies an empty
candidate set, so the ordinary zero-parent baseline may be returned.

## Candidate identity and ordering

Catalog planning uses a canonical-name-only policy. Aliases do not become
additional candidate positions and are never substituted for canonical emitted
`use=` names.

The existing catalog order is canonical name followed by physical path, both
ordinal. The first physical occurrence of each canonical name therefore fixes
ordinal canonical-name order for planning candidates. Filesystem enumeration
and publication order do not affect candidate indices.

The selected `UseName` is exactly the canonical catalog name. The underlying
effective `TerminalDescription` remains the parsed immutable catalog value.

## Target and self-reference exclusion

The target canonical name and aliases form one ordinal identity set. A catalog
entry is excluded when its canonical name or any alias intersects that set.

This is stricter than comparing only the emitted canonical candidate name. It
prevents an obvious self-reference from re-entering through a catalog alias.
Entries which merely have equal capabilities but declare no shared identity are
not treated as self-references.

## Duplicate physical entries

Conventional databases commonly publish one compiled entry beneath its
canonical name and aliases. The catalog deliberately retains those physical
files and reports duplicate canonical names.

RP05 collapses semantically identical physical copies into one canonical
candidate. It compares the complete effective description, including identity
metadata and standard and extended capabilities.

If physical copies for one canonical name differ, the catalog contains
conflicting physical entries. Planning rejects the catalog rather than choosing
one by path, hiding the ambiguity, or claiming complete selection.

## Bounds and cancellation

The existing planning policy remains authoritative for:

- maximum canonical non-self candidate count;
- maximum selected parent count;
- maximum evaluated plan count;
- maximum generated source length; and
- exhaustive versus explicitly bounded results.

The candidate limit is checked while canonical candidates are prepared. The
cancellation token is observed before catalog inspection, throughout catalog
traversal and entry reads, between catalog entries, before generic planning, and
at every RP04 planning boundary.

Parser resource limits are snapshotted by the existing catalog inspector. A
parser-limit failure becomes a catalog issue and fails the completeness gate.
No partial plan or catalog-derived result escapes cancellation or failure.

## Verification

RP05 tests use temporary controlled compiled databases and prove:

- explicit catalog and explicit directory forms select the same plan;
- canonical candidates retain ordinal order regardless of publication order;
- alias publications collapse without duplicate candidate instability;
- target canonical and alias identities are excluded;
- malformed or otherwise issue-bearing catalogs cannot claim completeness;
- missing roots are not treated as complete empty catalogs;
- conflicting duplicate physical entries are rejected;
- parser limits, candidate bounds, and cancellation remain effective; and
- emitted source uses canonical catalog names only.

Package smoke also exercises catalog planning through the public packaged API.

## Compatibility result

The frozen catalog types and inspection behavior remain unchanged. The RP01
planning types, RP02 through RP04 search behavior, and frozen 1.7 synthesis API
remain unchanged. Inspection retains only Runtime and Source production
dependencies, and every reusable assembly retains version `1.0.0.0`.

All coordinated packages and commands advance to `1.8.0-Alpha-5`.
