## Discovery architecture

The optional provider consumes Runtime's internal immutable discovery snapshot
and ordered logical locations. Friend access is internal only; Runtime gains no
public API. The existing Runtime `SystemTerminalDescriptionProvider` is
unchanged.

Precedence is preserved:

1. encoded `TERMINFO`;
2. the `TERMINFO` logical location;
3. the non-Windows user `.terminfo` location;
4. `TERMINFO_DIRS`, including empty components that expand defaults in place;
5. final platform defaults.

Equivalent logical locations are deduplicated by Runtime policy.

At each logical location:

1. an existing exact directory uses Runtime's directory provider;
2. an existing exact non-directory uses the explicit BerkeleyDb provider;
3. only when the exact location is absent is its regular `.db` companion tried.

Exact paths therefore precede companions, matching the reviewed ncurses
`check_existence` behavior.

## Snapshot, cache, retry, and error semantics

Environment values and all parser/database/index limits are snapshotted at
construction. File-system shape is inspected at lookup time, allowing a
higher-precedence source created after construction or after an earlier cached
success to be observed according to the existing provider contract.

Outer and underlying providers cache successful results only. Exact failed or
missed Lazy instances are removed, so missing sources and replacement after a
malformed failure remain retryable. Concurrent successful loads publish the same
`TerminalDescription` reference.

Missing locations are clean misses and discovery continues. Once a supported
hashed source is reached, malformed or unsupported containers and ncurses
envelopes fail explicitly. Parser, identity, and I/O failures preserve their
established exception distinctions.

## Boundaries and limits

- Production remains pure managed, read-only, and free of P/Invoke/native
  Berkeley DB deployment.
- Native Berkeley DB remains a Linux/macOS CI fixture producer and oracle.
  Windows consumes Linux-generated stores without Berkeley DB installed.
- Qualified native terminal identities are ASCII. Broader non-ASCII producer
  interoperability is not claimed.
- Big-endian Hash-v9 coverage remains synthetic.
- Validation covers encountered storage and envelope structures; it is not a
  general-purpose Berkeley DB validator and does not provide an atomic snapshot
  against external writes.
