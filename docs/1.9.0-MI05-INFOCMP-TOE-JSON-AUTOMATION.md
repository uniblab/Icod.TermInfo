# Icod.TermInfo 1.9.0 MI05 - infocmp and toe JSON Automation

**Development version:** `1.9.0-Alpha-5`

**Status:** implemented

**Next tranche:** MI06 - Samples, Package Consumers, and Cross-Host Hardening

## Purpose

MI05 composes the frozen version-1 Inspection JSON renderer through the existing
`infocmp`, `toe`, and `icod-terminfo` command surfaces. It also exposes the
frozen RP05 explicit-catalog planning path without adding reusable API, a new
package, a new executable, or implicit host discovery.

The renderer, schema, comparison semantics, catalog semantics, source synthesis,
planning score, bounds, and cancellation boundaries remain owned by
`Icod.TermInfo.Inspection`.

## Supported command forms

`infocmp` accepts these machine-readable forms:

```text
infocmp --json target
infocmp --json -d left right
infocmp --json --plan-use target candidate [candidate ...]
infocmp --json --plan-use --all-candidates -B directory target
```

The first form uses `TERM` when the target operand is omitted, consistently with
the existing one-terminal command. The forms select exactly one appropriate
version-1 document:

| Command operation | Document kind |
| --- | --- |
| effective terminal inspection | `terminalDescription` |
| two-terminal semantic difference | `comparison` |
| explicit-candidate planning | `sourcePlan` |
| explicit-directory all-candidates planning | `sourcePlan` |

`toe` accepts one machine-readable form:

```text
toe --json directory
```

It renders the exact `TermInfoDatabaseCatalog` returned for that explicit root
as one `databaseCatalog` document. Missing, unavailable, unsupported, malformed,
or otherwise incomplete state remains explicit catalog evidence. An incomplete
catalog is data, not a request to fall back to human listing or host discovery.

Every form is also available through the router by prefixing it with
`icod-terminfo` and the command name.

## All-candidates planning

`--all-candidates` is accepted only with `--plan-use`. It requires:

- exactly one explicit `-B directory`;
- exactly one target operand;
- no explicit candidate operands; and
- the existing planning bounds and exhaustive/bounded policy.

The command acquires the target through the established first-terminal path and
then calls `TerminalDescriptionSourcePlanner.PlanFromDirectory`. That reusable
operation owns all catalog requirements:

- only the caller-selected conventional directory is inspected;
- the catalog must be complete and issue-free;
- semantic canonical-name ambiguity is rejected;
- accepted candidates retain canonical catalog order;
- the target is excluded through the frozen planning identity contract; and
- planning limits and cancellation are observed at their established stable
  boundaries.

There is no environment search, system database enumeration, or inferred
candidate directory. Omitting `--json` preserves the established planning
presentation contract and writes only `plan.Source`.

## Option interactions

JSON is an additive representation selector. Existing human-readable forms are
unchanged.

For non-planning JSON, human source-layout controls `-0`, `-1`, `-w`, `-s`, and
`-x` are rejected because they do not describe the JSON document. Comparison
presentation modes `-c`, `-n`, and `-q` are rejected; JSON comparison is the
structured two-terminal difference result. More than two comparison operands
are rejected because one command invocation produces one document. Relative
synthesis `-u` remains a source-producing operation and is not a JSON form.

Planning source and bound controls remain accepted with JSON because they affect
the actual generated source and planning evidence represented by the document.

`toe --json` requires exactly one explicit directory and rejects `-a`, `-h`,
and `-s`, source dependency modes, discovery, and multiple roots.

## Streams, framing, diagnostics, and status

Successful JSON commands write:

```text
TermInfoJsonRenderer.Render(value) + "\n"
```

The renderer owns the complete JSON bytes. The command adds exactly one LF and
no other stdout framing. Successful commands leave stderr empty.

Acquisition, catalog-inspection, planning, or rendering failures produce no
partial stdout document. Usage diagnostics and operational diagnostics remain
on stderr. Status mapping is unchanged:

| Status | Meaning |
| --- | --- |
| `0` | success |
| `1` | operational, inspection, planning, or rendering failure |
| `2` | usage error |
| `130` | cancellation |

Cancellation before or during the operation produces no partial JSON document.

## Router and distribution evidence

The router does not parse JSON or planning options. It forwards the selected
command arguments, standard streams, cancellation token, diagnostics, and exit
status. Direct and routed output is therefore required to be byte-for-byte
identical.

The installable tool package smoke and every one of the six standalone archive
smokes parse real `terminalDescription`, `comparison`, `sourcePlan`, and
`databaseCatalog` outputs with PowerShell `ConvertFrom-Json`. The smoke catalog
planning case uses an explicit conventional directory without alias ambiguity
and verifies target exclusion.

## Compatibility boundary

MI05 adds no reusable public type or member and does not change the packaged
version-1 JSON Schema. Runtime remains dependency-free; Source, Compiler, and
Termcap retain their frozen public contracts; Inspection retains its MI04 public
surface; and the router retains five-command dispatch and six-archive topology.

MI06 owns package-only consumers, expanded samples, culture/process determinism,
pathological inputs, and cross-host hardening. MI05 does not preempt that work.
