# Icod.TermInfo 1.4.1 Release Audit

**Release version:** `1.4.1`
**Runtime assembly version:** `1.0.0.0`
**Source assembly version:** `1.0.0.0`
**Compiler assembly version:** `1.0.0.0`
**Inspection assembly version:** `1.0.0.0`
**Status:** Final release candidate — main Release validation and tag publication remain

## Purpose

Version 1.4.1 is a documentation/metadata patch release over the published
1.4.0 tool-suite release. It corrects stale release-facing statements which
still described `tic`, `infocmp`, `toe`, `Icod.Terminal`, or the Inspection 1.4
API baseline as future/active development work.

This release SHALL NOT add production behavior, change command semantics, change
the supported target-framework matrix, or modify any frozen public API baseline.

The publication boundary is immutable tag `v1.4.1`. Ordinary pull requests and
pushes to `main` validate candidates but do not publish packages.

## Frozen library contract

The patch release SHALL preserve exactly:

- `docs/1.0.0-PUBLIC-API-BASELINE.txt` as the Runtime API;
- `docs/1.1.0-SOURCE-PUBLIC-API-BASELINE.txt` as the Source API;
- `docs/1.2.0-COMPILER-PUBLIC-API-BASELINE.txt` as the Compiler API;
- `docs/1.3.0-INSPECTION-PUBLIC-API-BASELINE.txt` as the historical Inspection
  1.3 baseline;
- `docs/1.4.0-INSPECTION-PUBLIC-API-BASELINE.txt` as the frozen Inspection 1.4
  API;
- exact net8/net9/net10 API equivalence for all four libraries;
- assembly version `1.0.0.0` for all four reusable assemblies;
- Runtime dependency-free;
- Source depending only on Runtime;
- Compiler depending on Runtime and Source;
- Inspection depending on Runtime and Source and not on Compiler.

No 1.4.1 API-baseline file is created. All four library projects SHALL declare
both `Version` and `PackageVersion` exactly `1.4.1`.

## Frozen command contract

`tic`, `infocmp`, and `toe` SHALL retain the exact released 1.4.0 command
semantics and each SHALL:

- target `net10.0`;
- report version `1.4.1`;
- remain non-packable solution executables;
- retain the T10 CLI/presentation contract and T11 differential/hostile-input
  validation gates;
- use `Icod.CommandFramework` only in the command layer;
- introduce no command-to-command project dependency.

The command projects SHALL declare `Version` exactly `1.4.1`.

## Documentation and metadata corrections

The 1.4.1 release is allowed to change release-facing documentation and metadata
only. The correction set includes:

- current install examples and package/command version text;
- package release notes;
- the root README's released tool-suite and sibling-layer descriptions;
- current `VERSIONING.md`, `COMPATIBILITY.md`, `RELEASING.md`, and contributing
  guidance;
- explicit historical labeling for the unversioned future-work planning
  inventory;
- coordinated-version tests which intentionally guard the current package and
  command version.

Historical 1.0-1.4.0 tranche records, published release audits, and frozen API
baseline files remain unchanged.

## Artifact contract

The release contains fourteen checksummed package/archive artifacts:

```text
4 .nupkg
4 .snupkg
6 framework-dependent tool-suite archives
```

The tool archives are:

```text
Icod.TermInfo.Tools.1.4.1.win-x64.zip
Icod.TermInfo.Tools.1.4.1.win-arm64.zip
Icod.TermInfo.Tools.1.4.1.linux-x64.tar.gz
Icod.TermInfo.Tools.1.4.1.linux-arm64.tar.gz
Icod.TermInfo.Tools.1.4.1.osx-x64.tar.gz
Icod.TermInfo.Tools.1.4.1.osx-arm64.tar.gz
```

`SHA256SUMS.txt` covers all fourteen artifacts, producing fifteen final GitHub
Release assets.

The user supplies the .NET 10 runtime. The archives remain framework-dependent
suite archives rather than NuGet global tools, self-contained bundles,
NativeAOT images, installers, or signed/notarized platform packages.

## Archive execution gate

After the six archives are built and structurally verified, CI SHALL download
them onto matching Windows, Linux, and macOS runners and execute the actual
release payload.

The smoke gate SHALL:

1. run `tic --version`, `infocmp --version`, and `toe --version` and require
   `1.4.1`;
2. use the unpacked `tic` to publish the controlled release-smoke source entry;
3. use the unpacked `infocmp` to acquire/render that entry;
4. use the unpacked `toe` to enumerate that entry.

Package publication SHALL remain downstream of this smoke gate and the complete
Windows/Linux/macOS Release validation matrix.

## Required final validation

Before tag creation, the 1.4.1 finalization commit SHALL pass the complete
`main` workflow, including:

- Release restore/build/test on Windows, Linux, and macOS;
- all four package verifiers;
- all four package-reference-only consumers across net8/net9/net10;
- frozen API and cross-target API-equivalence checks;
- the existing differential corpus and hostile-input tests;
- construction and structural verification of all six tool archives;
- unpacked release-archive smoke on matching Windows/Linux/macOS runners.

Equivalent local validation remains documented in `docs/RELEASING.md`.

## Tag publication

Tag `v1.4.1` SHALL:

1. identify the exact 1.4.1 finalization commit already validated on `main`;
2. identify a commit contained in `main`;
3. match all four library `Version`/`PackageVersion` values and all three command
   `Version` values exactly;
4. repeat the complete Release matrix;
5. rebuild and structurally verify all six tool archives;
6. repeat the unpacked archive smoke gate on Windows/Linux/macOS;
7. publish the four validated `.nupkg` files to NuGet.org;
8. publish the same four `.nupkg` files to GitHub Packages;
9. create the GitHub Release with four `.nupkg`, four `.snupkg`, six tool
   archives, and `SHA256SUMS.txt`.

NuGet trusted publishing must authorize all four package IDs for `release.yaml`
and the `Release` environment before the tag is pushed.

## Final sign-off

The 1.4.1 release is complete only when:

- the `v1.4.1` tag workflow succeeds;
- all four version 1.4.1 packages are visible on NuGet.org;
- all four version 1.4.1 packages are visible in GitHub Packages;
- the GitHub Release contains exactly fifteen expected assets;
- fresh consumers can restore all four final packages;
- the six command archives remain downloadable and their checksums match;
- `v1.4.1` still identifies the exact validated release commit.

Do not move or recreate a published release tag. Any later package, archive,
source, documentation, command-contract, or API-baseline change requires a new
version and a new validated immutable tag.
