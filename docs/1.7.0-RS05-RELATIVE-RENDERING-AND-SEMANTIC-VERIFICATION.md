# Icod.TermInfo 1.7.0 RS05 — Relative Rendering and Semantic Verification

**Development version:** `1.7.0-Alpha-5`
**Tranche:** RS05
**Status:** implementation contract
**Previous tranche:** RS04 — Ordered Multi-Parent Semantics and Reference Fidelity
**Next tranche:** RS06 — `infocmp -u`

## Objective

RS05 turns the relative synthesis semantics established by RS01 through RS04
into a release-quality rendering contract and makes semantic round-trip
verification a permanent regression gate.

The reusable implementation remains in `Icod.TermInfo.Inspection`. RS05 adds no
public API and does not add a production dependency on `Icod.TermInfo.Compiler`.
Compiler participation is deliberately limited to tests and the deterministic
Toolchain sample.

## Frozen rendering contract

For one target and its exact caller-supplied ordered parent list, synthesis emits
one complete relative terminfo source entry in this deterministic sequence:

1. target identity header;
2. standard Boolean declarations or cancellations;
3. standard numeric declarations or cancellations;
4. standard string declarations or cancellations;
5. extended declarations or cancellations;
6. ordered `use=` references.

No local capability directive is emitted when the inherited aggregate already
provides exactly the target value. Parent references remain present in exact
caller order even when one is semantically redundant.

## Target identity

The header is rendered from the target alone. It preserves:

- canonical `Name`;
- `Aliases` in target order;
- representable `Description`.

Parent identity never replaces or augments target header identity. The same
lossless Source 1.1 identity validation used by the existing effective renderer
remains authoritative.

## Layout and ordering controls

RS05 freezes relative synthesis against the already public Inspection rendering
concepts exposed through `TerminalDescriptionSourceSynthesisOptions`:

- `TerminalDescriptionSourceLayout.Canonical`;
- `TerminalDescriptionSourceLayout.SingleLine`;
- `TerminalDescriptionSourceLayout.OneCapabilityPerLine`;
- selected `LineWidth`;
- selected `TerminalDescriptionSourceCapabilityOrder`;
- safe extended-capability emission policy.

Canonical layout wraps string fields deterministically at the selected width.
Single-line layout emits one logical source line. One-capability-per-line layout
keeps each complete capability directive on one physical line and does not use
canonical continuation wrapping.

Standard capabilities use the selected existing order. Extended values keep the
RS03 kind-then-ordinal-name order. Cancellations occupy the ordering position of
the capability state they remove rather than a separate cancellation bucket.

## String escaping and wrapping

Relative rendering reuses the effective renderer's source encoder. Semantic
string characters are never normalized merely for display. In particular:

- ESC uses `\E`;
- carriage return uses `\r`;
- newline uses `\n`;
- tab, backspace, form feed, spaces, backslash, commas, carets, colons, and pipes
  retain the established reversible Source spelling;
- non-printable Latin-1 bytes use the established octal form.

Canonical wrapping occurs between encoded character tokens and never inserts a
semantic carriage return into the rendered source.

## LF-only source invariant

Generated terminfo source text is independent of repository file line endings.
Repository source files are maintained under the repository's CRLF policy, but
`TerminalDescriptionSourceSynthesizer.Synthesize` must return text which:

```text
is non-empty
contains no '\r' characters
ends with exactly an LF source line terminator
```

RS05 adds a defensive internal postcondition at the synthesis composition seam
so both zero-parent effective rendering and parent-relative rendering are checked
against that contract. This is not a new public API.

The LF requirement is the portable Windows/Linux/macOS output contract. The CI
matrix exercises the same regression tests on each supported host.

## Source semantic verifier

The primary permanent correctness gate constructs:

```text
relative child source
+ full effective parent source entries
```

and executes:

```text
TermInfoSourceParser
    -> TermInfoSourceResolver
    -> TerminalDescription
    -> TerminalDescriptionComparer
    -> AreEqual == true
```

This gate compares target identity and the complete effective standard and
extended capability universe. It uses the real Source parser/resolver as the
oracle and does not introduce a duplicate inheritance implementation in tests.

## Compiler semantic verifier

RS05 also makes the secondary integration path permanent:

```text
same combined source
    -> TermInfoSourceCompiler
    -> CompiledTermInfoParser
    -> TerminalDescriptionComparer
    -> AreEqual == true
```

`Icod.TermInfo.Inspection` production code does not reference Compiler. The
existing Inspection test project already references Compiler specifically for
cross-layer evidence, so this verification leaves the package dependency graph
unchanged.

## Rendering regression matrix

The RS05 contract suite covers:

- canonical relative layout;
- single-line layout;
- one-capability-per-line layout;
- selected canonical width;
- terminfo-name capability ordering;
- long escaped strings containing punctuation, ESC, CR, LF, and backslash;
- target identity and aliases;
- inherited no-op elimination;
- cancellation-heavy standard and extended entries;
- several ordered `use=` references;
- minimal local delta;
- culture changes;
- LF-only output;
- Source parser/resolver round trips;
- Compiler/compiled-parser round trips.

Equal semantic inputs and options therefore have a byte-stable textual contract
that is insensitive to current culture, dictionary insertion order, and host
line-ending convention.

## Deterministic Toolchain sample

The `Icod.TermInfo.Toolchain.Sample` now includes relative synthesis in its
controlled, host-independent path. It:

1. parses and resolves a fixed base and child;
2. synthesizes the child relative to the base;
3. verifies LF-only relative output;
4. combines the relative child with the rendered base;
5. reparses and resolves that synthesized document and compares it to the target;
6. compiles the synthesized document;
7. publishes it into a unique temporary conventional database;
8. reacquires the compiled child through Runtime;
9. compares the acquired description with the original target;
10. writes the relative source only after every semantic gate succeeds.

The sample continues to avoid host `TERM`, host terminfo databases, and native
ncurses tools.

## Public API and dependency boundary

RS05 adds no public members. It does not change:

- `Icod.TermInfo` public API;
- `Icod.TermInfo.Source` public API;
- `Icod.TermInfo.Compiler` public API;
- `Icod.TermInfo.Termcap` public API;
- the additive Inspection public surface established through RS03;
- command semantics;
- reusable target frameworks;
- assembly version `1.0.0.0`;
- Inspection's Runtime-and-Source-only production dependency graph.

The exact stable 1.7 Inspection API baseline remains RS08 work. `infocmp -u`
remains RS06 work.

## Versioning

```text
1.7.0-Alpha-5
```

## RS05 gate

RS05 is complete when:

- the coordinated development version is `1.7.0-Alpha-5`;
- relative rendering is frozen across all three supported layouts;
- selected width and standard capability ordering remain deterministic;
- target identity, cancellations, and ordered parent references are preserved;
- output is non-empty, LF-terminated, and contains no carriage returns;
- long escaped strings remain semantically reversible;
- minimal and cancellation-heavy cases pass Source semantic verification;
- the same synthesized documents pass Compiler/compiled-parser verification;
- culture changes do not alter output;
- the deterministic Toolchain sample exercises synthesis end to end;
- no public API or command-semantic change is introduced;
- Runtime, Source, Compiler, and Termcap frozen contracts remain intact;
- Inspection retains Runtime-and-Source-only production dependencies.

RS06 may then expose the proven engine through `infocmp -u` without changing the
RS05 rendering or verification contract.
