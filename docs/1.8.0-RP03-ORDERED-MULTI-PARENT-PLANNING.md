# Icod.TermInfo 1.8.0 RP03 - Ordered Multi-Parent Planning

**Development version:** `1.8.0-Alpha-3`
**Roadmap tranche:** RP03
**Implementation base:** `62a6f8045df7c9e0627e5ced91c071597ff4a738`

## Purpose

RP03 extends the operational RP02 planner from zero- and single-parent plans to
the ordered permutations of distinct candidate positions up to the active
selected-parent bound. It does not add public API. It preserves the frozen 1.7
synthesis contract, including leftmost parent precedence and exact `UseName`
spelling.

## Search domain and order

For `n` accepted candidate positions and depth limit `d`, the exhaustive plan
space is:

```text
1 + P(n, 1) + P(n, 2) + ... + P(n, min(n, d))
```

The first plan is the zero-parent baseline. The planner then enumerates depth
one through the active maximum depth. Within each depth, candidate-index
sequences are ordered lexicographically. For three candidates and depth two,
the exact order is:

```text
[]
[0]
[1]
[2]
[0, 1]
[0, 2]
[1, 0]
[1, 2]
[2, 0]
[2, 1]
```

One candidate position cannot occur twice in a plan. Different positions remain
distinct even when they hold equal descriptions, canonical names, or aliases.
The selected candidate sequence is converted to parent descriptors in the same
order and passed unchanged to the synthesizer.

The plan-count calculation is bounded by the configured evaluation budget. It
does not need to represent a larger factorial plan space. When the legal space
exceeds the budget, the existing RP01 policy either rejects the request before
evaluation or, after explicit opt-in, returns the best lexicographic prefix with
`IsExhaustive` set to `false`.

## Semantics and scoring

Every plan delegates source production to the frozen 1.7 synthesizer. Therefore
ordered collisions retain leftmost parent precedence, while later parents can
add capabilities absent from earlier parents. Local additions, overrides, and
standard or extended cancellations are included in the existing frozen score:

1. local directive count;
2. cancellation count;
3. parent count;
4. rendered UTF-8 byte count;
5. selected candidate-index sequence.

Invalid synthesis combinations are rejected individually and still count as
evaluated plans. This includes two distinct candidate positions whose exact
references cannot coexist under synthesis validation. No invalid plan aborts
evaluation of the remaining legal candidate-position sequences, and no target
is approximated.

## Verification

RP03 adds an independent oracle which creates the exhaustive small-space index
set without using the production recursion. For each index sequence the oracle:

- calls the public synthesizer;
- parses the generated source;
- derives local-directive and cancellation counts from the source model;
- constructs the frozen score independently;
- compares the exact best source, score, parent identities, evaluation count,
  candidate count, and exhaustive result with the production planner.

Hand-authored cases cover:

- a two-parent standard collision whose winning leftmost order matters;
- a higher configured-depth winner;
- extended additions, overrides, and inherited cancellation;
- equal descriptions exposed through distinct aliases and candidate positions;
- the deterministic prefix returned by an opted-in evaluation budget.

Generated three-candidate spaces cover every ordered plan through depth three.
Every winning plan is also reparsed and resolved with its selected parent
descriptions to prove semantic equality with the target.

Package smoke coverage exercises a two-parent winner and verifies exact selected
parent identity, emitted `use=` order, frozen score evidence, and the exhaustive
five-plan count for two candidates.

## Compatibility result

The public Inspection surface is unchanged from RP01. Runtime, Source, Compiler,
and Termcap public contracts are unchanged. Inspection retains only Runtime and
Source production dependencies, and every reusable assembly retains version
`1.0.0.0`.

RP03 advances all coordinated package and command versions to
`1.8.0-Alpha-3`.
