# Icod.TermInfo 0.8.0 T26 — Profile Composition and Cancellation Fidelity

T26 formalizes the construction-time composition rules used by built-in terminal
profiles and reserves the same semantics for future compiled terminfo loading.

The public `TerminalDescription` model remains an effective immutable view.
Consumers continue to see a capability as either present or absent. Cancellation
is an internal construction state used to prevent an inherited value from
surviving when an authoritative source explicitly cancels it.

## Composition states

While one `TerminalDescriptionBuilder` is being composed, each standard or
extended capability is conceptually in one of three states:

```text
absent
present
canceled
```

These states have intentionally different meanings:

- **absent** — no value has been supplied at this layer;
- **present** — the builder has an effective value;
- **canceled** — an authoritative layer explicitly suppresses the capability.

`Build()` continues to emit only the effective present values. It does not add a
public canceled-state surface.

## Precedence rules

T26 freezes these rules:

1. `Inherit(source)` copies only effective capabilities which are absent in the
   destination builder.
2. An already-present local value wins over an inherited value.
3. A canceled destination slot blocks later inheritance of that capability.
4. `CancelBoolean`, `CancelNumber`, `CancelString`, and `CancelExtended` remove
   an existing value and mark the slot canceled.
5. A later explicit `Set*` operation reintroduces the capability and clears the
   cancellation.
6. Existing public removal operations return a slot to ordinary absence rather
   than creating a cancellation. A later inheritance may therefore fill it.
7. Extended capability names retain ordinal, case-sensitive semantics.
8. Standard capability names cannot be introduced or canceled through the
   extended namespace.

Identity metadata is not inherited by `Inherit`. Canonical name, aliases, and
verbose description belong to the destination profile and must be declared
there explicitly.

These rules let T27 and T28 reuse an effective DEC/xterm base and then apply
authoritative Windows-specific overrides and cancellations without introducing
terminal-name branches in the capability model.

## Why cancellation remains internal

A normal consumer asking for `cup`, `colors`, or an extended capability does not
need to know whether an absent value was never supplied or was explicitly
canceled while composing the profile. The distinction matters only while
resolving inheritance.

Keeping cancellation construction-only preserves the existing public lookup and
enumeration contracts while still making source-level cancellation exact.

The same construction semantics are suitable for the future 0.9 compiled
terminfo parser: a compiled canceled marker can call the same internal
cancellation operation before the immutable effective description is built.

## Existing profile audit

The existing ANSI, DEC VT, and xterm-family fragments were audited against the
new rules.

They already express their current effective data using ordinary `Set*`
operations and do not depend on a false Boolean or `Remove*` call meaning
"canceled." Consequently T26 does not need to rewrite their capability payloads.

T26 tests additionally inherit every existing built-in into a fresh description
and compare all effective Boolean, numeric, string, and extended capability
collections. Existing profile-specific golden tests remain authoritative for
the actual built-in values.

## Profile-data provenance convention

Generated or transcribed profile data added from T26 onward should record its
source next to the profile or fragment using this information:

```text
Provenance source: <upstream file/database>
Upstream revision: <revision/commit/version>
Upstream date: <date when available>
Entry identity: <canonical source entry or entries>
Acquisition: transcribed | generated
Inheritance/source lineage: <use=/base entries when relevant>
```

For the selected 0.8 ncurses baseline, existing profile comments identify
`terminfo.src` revision 1.1267 dated 2026-08-14 where applicable.

When an upstream source contains a cancellation, the managed transcription must
use an explicit internal `Cancel*` operation rather than merely omitting the
capability from a reused base fragment. That rule prevents inherited values from
leaking into the final profile.

Generated data should additionally document the generator and regeneration
command. Normal builds and tests remain network-independent.

## Boundary with later tranches

T26 does not add Windows terminal identities.

- T27 consumes these rules for `winconsole`.
- T28 consumes them for `ms-terminal` and `ms-terminal-direct`.
- T29/0.9 fixture work can represent compiled canceled markers without changing
  the effective public `TerminalDescription` contract.

No process-global terminal state, compiled database parser, or system provider
is introduced by this tranche.
