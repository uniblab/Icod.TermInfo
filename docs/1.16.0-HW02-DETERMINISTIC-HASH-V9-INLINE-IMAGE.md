## Accepted production path

The internal path now performs four separately tested operations:

1. HW01 preflight preserves the exact compiled names-section bytes, excluding
   only the required trailing NUL, as the storage key.
2. `BerkeleyDbNcursesRecordPlanner` emits marker-2 canonical/alias index
   envelopes and the marker-0 compiled-data envelope, rejects duplicate exact
   byte keys, and applies the Berkeley DB writer-specific exact-prefix order.
3. `BerkeleyDbHashV9ImageBuilder` hashes canonically ordered records into two
   fixed 4096-byte bucket pages and writes deterministic little-endian metadata.
4. The existing 1.15 managed reader and catalog reader recover the exact records,
   canonical names, aliases, parsed terminals, and compiled payload bytes.

The accepted HW02 image is exactly 12,288 bytes:

| Page | Purpose | Required type |
| --- | --- | --- |
| `0` | Hash-v9 metadata | `8` |
| `1` | Hash bucket `0` | `13` |
| `2` | Hash bucket `1` | `13` |

Metadata uses Hash magic `0x00061561`, version `9`, page size `4096`, last page
`2`, the accepted character hash `0x5E688DD1`, and a deterministic 20-byte file
identifier derived from the complete ordered record stream with SHA-256. Every
unused byte remains zero; no timestamp, destination, process, random, or host
state enters the image.

Keys and values are packed as inline type-1 items. HW02 accepts payloads through
1,024 bytes, uses checked count/offset/size arithmetic, preserves canonical
record order inside each bucket, and rejects a bucket that exceeds its one-page
capacity. Growth and overflow pages remain owned by HW03.

## Remaining boundary and next gate

HW02 intentionally does not implement:

- bucket growth or additional hash pages;
- collision-growth policy beyond deterministic same-page packing;
- overflow items or overflow chains;
- compiled payloads larger than 1,024 bytes;
- public writer image emission;
- filesystem publication; or
- `tic` integration.

The next implementation gate is **HW03 / Alpha-3 — collisions, overflow, and
bounded growth**. HW03 must preserve the accepted HW02 byte profile for every
image that still fits the two-bucket inline form while adding deterministic,
bounded growth and overflow behavior for larger inputs.
