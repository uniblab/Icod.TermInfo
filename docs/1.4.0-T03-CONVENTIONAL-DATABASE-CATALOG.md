# Icod.TermInfo 1.4.0 — T03 Conventional Database Catalog Enumeration

**Tranche:** T03 — Conventional database catalog enumeration
**Development version:** `1.4.0-Alpha-3`
**Baseline commit:** `b6d19a232d37ca5ba7c7546ac298be762fce199b`
**Previous tranche:** T02 — system database-location inspection
**Status:** implementation candidate

---

## 1. Purpose

T03 adds one reusable, read-only catalog engine for conventional compiled
terminfo directory trees.

T02 answers:

```text
Where would Runtime look for terminal descriptions?
```

T03 answers:

```text
What supported compiled entries are physically present under this explicit
conventional directory root, and what problems were encountered while examining
that root?
```

These remain separate contracts.

T03 does not add `toe` command behavior. `toe` consumes this reusable engine in a
later tranche.

## 2. Layering decision

T03 requires no new Runtime public API and no new Runtime internal friend seam.

The released Runtime already exposes the reusable parser contract needed by
catalog inspection:

```text
CompiledTermInfoParser
CompiledTermInfoParserOptions
TerminalDescription
```

Inspection therefore owns filesystem enumeration and catalog reporting while
Runtime remains authoritative for compiled-entry validity and resource limits.

The production dependency graph remains:

```text
Inspection -> Source -> Runtime
Inspection ----------> Runtime

Compiler   -> Source -> Runtime
Compiler   ------------> Runtime
```

Inspection does not acquire a production Compiler dependency.

The Inspection test project may continue to use Compiler to create deterministic
compiled-entry fixtures.

## 3. Public API additions

T03 adds these Inspection types:

```text
TermInfoDatabaseCatalog
TermInfoDatabaseCatalogEntry
TermInfoDatabaseCatalogIssue
TermInfoDatabaseCatalogIssueKind
TermInfoDatabaseCatalogKind
```

and adds catalog overloads to:

```text
TermInfoDatabaseInspector
```

The normal form is:

```csharp
TermInfoDatabaseCatalog catalog =
	TermInfoDatabaseInspector.InspectDirectory(
		root
	);
```

A caller may supply explicit parser limits:

```csharp
TermInfoDatabaseCatalog catalog =
	TermInfoDatabaseInspector.InspectDirectory(
		root,
		parserOptions
	);
```

Cancellation is explicit rather than process-global:

```csharp
TermInfoDatabaseCatalog catalog =
	TermInfoDatabaseInspector.InspectDirectory(
		root,
		parserOptions,
		cancellationToken
	);
```

The active contract is recorded in:

```text
docs/1.4.0-INSPECTION-PUBLIC-API-BASELINE.txt
```

The frozen 1.3 Inspection baseline remains unchanged.

## 4. Root states

`TermInfoDatabaseCatalogKind` distinguishes:

```text
Missing
ConventionalDirectory
UnsupportedStore
Unavailable
```

### Missing

The explicit root does not exist at inspection time.

This is not represented as a fabricated empty conventional database.

### ConventionalDirectory

The explicit root is a directory and can be inspected as a conventional
terminfo tree.

### UnsupportedStore

The explicit root identifies a non-directory store.

This is the 1.4 boundary for explicitly encountered hashed/Berkeley DB-style or
other non-directory stores. T03 does not guess their representation and does not
add a Berkeley DB dependency.

### Unavailable

The root could not be inspected because of an I/O or permission failure.

The catalog retains an issue describing that failure.

## 5. Enumeration boundary

T03 is intentionally not a recursive filesystem crawler.

For one explicit root it examines only immediate subdirectories whose names are:

```text
one character
```

or:

```text
two hexadecimal digits
```

Those represent the conventional literal first-character and hexadecimal
first-byte layouts.

Directories with other names are ignored by the catalog engine.

Files are examined only when they are immediate children of a recognized
conventional subdirectory.

Nested arbitrary directory trees are never traversed.

## 6. Link and reparse policy

A recognized child directory which is a symbolic link, junction, or other
reparse point is not traversed.

A candidate file which is itself a link/reparse point is not followed.

Both cases produce a deterministic `LinkSkipped` issue.

The caller explicitly selects the catalog root. T03 does not recursively chase
links discovered beneath that root.

This policy prevents catalog enumeration from escaping into an uncontrolled
filesystem graph.

## 7. Candidate parsing

Candidate identity is never inferred solely from its filename.

Each physical file is:

1. opened read-only;
2. bounded by the snapshotted `CompiledTermInfoParserOptions.MaximumEntrySize`;
3. read as one complete candidate;
4. parsed through `CompiledTermInfoParser`;
5. converted into a `TermInfoDatabaseCatalogEntry` only after successful parsing.

A successful catalog entry retains:

```text
absolute physical path
canonical terminal name
aliases
description
immutable TerminalDescription
```

The parser remains authoritative for supported compiled formats, table counts,
offsets, extended sections, and representation validity.

T03 does not reproduce compiled-format parsing inside Inspection.

## 8. Physical placement validation

A successfully parsed physical file is also checked against conventional
placement.

The filename must equal either:

```text
parsed canonical name
```

or one of:

```text
parsed aliases
```

and its containing directory must correspond to that filename's first character
through either the literal or hexadecimal conventional layout.

A successfully parsed but misplaced entry remains visible in `Entries` and also
produces an `InvalidPlacement` issue.

This distinction is deliberate: valid compiled content should not disappear
merely because filesystem placement is incorrect.

## 9. Duplicate identity reporting

The Compiler publishes a canonical entry and may publish alias paths containing
the same compiled bytes.

Catalog enumeration therefore operates on physical files rather than attempting
to collapse entries implicitly.

`Entries` contains every successfully parsed physical candidate.

`DuplicateCanonicalNames` contains canonical names represented by more than one
successfully parsed physical file.

The duplicate-name list is ordinally sorted and immutable.

This provides future `toe` policy enough information to decide how duplicates
should be displayed without hiding physical database structure in the reusable
Inspection layer.

## 10. Issue model

T03 does not fail the complete catalog merely because one physical candidate is
bad.

`TermInfoDatabaseCatalogIssueKind` distinguishes:

```text
MalformedEntry
InvalidPlacement
PermissionFailure
IoFailure
LinkSkipped
```

### MalformedEntry

The file could not be parsed by `CompiledTermInfoParser`, including configured
resource-limit failure.

### InvalidPlacement

The file parsed successfully but its physical filename/directory does not match
an identity declared by the parsed entry.

### PermissionFailure

Filesystem access was denied.

### IoFailure

Another filesystem I/O operation failed.

### LinkSkipped

A link, junction, or reparse candidate was deliberately not followed.

Issues are ordered deterministically by:

```text
absolute path
issue kind
message
```

The catalog exposes `HasIssues` as a convenience without collapsing the issue
collection.

## 11. Error continuation

T03 distinguishes argument/programmer errors from catalog-content problems.

Invalid public arguments continue to throw normal argument exceptions.

Cancellation throws `OperationCanceledException`.

For an otherwise inspectable conventional root, malformed entries and recoverable
per-candidate filesystem failures are retained as issues and enumeration
continues when it is safe to do so.

This is required for later `toe` behavior, where a partially damaged system
database should still yield safely obtainable entries while preserving a final
operational-failure signal at the command layer.

T03 itself does not define command exit codes.

## 12. Deterministic ordering

Successful entries are ordered by:

```text
canonical terminal name, ordinal
physical path, ordinal
```

Issues are ordered by:

```text
physical path, ordinal
issue kind
message, ordinal
```

Duplicate canonical names are ordered ordinally.

The observable catalog does not depend on directory enumeration order, file
creation order, current culture, dictionary insertion order, or hash
randomization.

## 13. Resource limits and cancellation

Parser options are snapshotted at the beginning of the inspection.

The same maximum-entry-size model used by Runtime compiled parsing therefore
applies to catalog candidates.

Cancellation is checked:

- before root traversal;
- while traversing recognized subdirectories;
- before candidate inspection;
- while reading candidate bytes;
- before parsing a completed candidate.

T03 does not introduce process-global cancellation or mutable parser policy.

## 14. Filesystem mutation

Catalog inspection is read-only.

It does not:

- create the root;
- repair directory layouts;
- rename entries;
- delete malformed entries;
- normalize alias files;
- rewrite compiled data;
- update Runtime provider caches.

Filesystem publication remains the Compiler's responsibility.

## 15. Test contract

T03 tests cover:

- missing root;
- empty conventional root;
- explicit non-directory/unsupported store;
- hexadecimal layout;
- literal layout;
- parsed name/alias/description/path retention;
- Compiler alias publications as distinct physical entries;
- duplicate canonical identity reporting;
- literal and hexadecimal copies of one terminal;
- malformed/truncated entry continuation;
- configured parser size-limit failure;
- successfully parsed but invalid placement;
- ignored unrecognized/nested directories;
- creation-order-independent results;
- pre-canceled inspection;
- stable permission/I/O issue classification;
- explicit reparse-point classification;
- bounded conventional-directory-name recognition;
- linked conventional child skipping when the host permits link creation.

The tests use temporary controlled roots and do not depend on the host's system
terminfo installation.

## 16. Package validation

The Inspection package-only smoke consumer SHALL exercise T03 without acquiring
a Compiler production dependency.

It does so against a unique missing temporary root and verifies the public
catalog result shape.

Release verification continues to require:

```text
net8.0
net9.0
net10.0
```

Inspection API equivalence and the active 1.4 Inspection public API baseline.

## 17. Explicit non-goals

T03 does not implement:

- `toe` command output;
- system search-path composition across several catalog roots;
- recursive arbitrary directory crawling;
- Berkeley DB parsing;
- hashed-store enumeration;
- termcap databases;
- filesystem repair;
- byte-for-byte duplicate-content hashing as semantic identity;
- command exit-status policy;
- command presentation formatting.

Those remain later or out-of-scope concerns.

## 18. Gate T03

T03 is complete when:

1. the coordinated development version is `1.4.0-Alpha-3`;
2. Runtime, Source, and Compiler public baselines remain exact;
3. the active Inspection 1.4 baseline contains only reviewed T02/T03 additions
   beyond the frozen 1.3 surface;
4. one explicit conventional root can be enumerated deterministically;
5. literal and hexadecimal layouts are supported;
6. candidate identity comes from parsed content;
7. malformed and recoverable per-candidate filesystem failures remain visible as
   issues without hiding valid entries;
8. duplicate canonical identities are reported deterministically;
9. parser limits and cancellation are honored;
10. child links/reparse points are not recursively followed;
11. the Inspection package still has no production Compiler dependency;
12. the complete solution passes the Windows/Linux/macOS Staging gate.

No `tic`, `infocmp`, or `toe` operational command behavior is required or
permitted by this tranche.
