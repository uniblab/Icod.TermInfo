## Accepted scope

HDB07C closes three deliberately bounded gaps left by HDB07:

1. Production path acquisition now accepts an image only after two complete,
   byte-identical observations through one open file handle.
2. Linux and macOS independently produce and natively verify a big-endian
   Berkeley DB Hash-v9 container containing byte-exact ncurses-produced
   records; Windows verifies the transported Linux fixture without Berkeley
   DB installed.
3. Exact terminal-name handling now supports a UTF-8-first, Latin-1 fallback
   policy for the qualified single-byte ncurses producer subset.

Production remains pure managed and read-only. The existing Runtime
`CompiledTermInfoParser` remains the only semantic parser for compiled-entry
bytes.

## RED-to-GREEN history

### Observed-stability acquisition

RED commit `5c81ab924113d40a44fb1358e3b2df7e6086e2d8` added deterministic
same-length, length-changing, and stable two-observation cases. In normal run
`35152972057`, the Windows, Linux, and macOS BerkeleyDb jobs all reached the
intended test failure before the superseding push cancelled the remaining
workflow jobs.

GREEN commit `e20a0a1488c5bc509adfd688bbf5adf1622f5a5a` passed normal run
`35153323719` and HDB00 run `35153323765`. The path-owned reader performs two
complete observations without retry and without allocating a second
database-sized byte array. The borrowed stream helper remains single-pass and
non-owning.

Unequal observed length or content fails with `IOException` before Hash-v9
parsing. This is detection between the two observations, not an atomic
snapshot: a writer may restore identical bytes between observations or mutate
the file after verification, and HDB07C adds no locking or writer
coordination.

### UTF-8-first provider fallback

RED commit `734cb9f0045fc59e3ba6b3dd25a7e8e63440d022` failed normal run
`35155649749` on the new exact-key expectations. The HDB00 fixture boundary was
unchanged and run `35155649743` passed.

The implementation sequence ended at corrected-stack head
`d1fbb0ccb28b3a1dc5500619cd0567b84ff376b2`, which passed normal run
`35157194595` and HDB00 run `35157194518`. New HDB07C tooling is limited to
C#, cmd/sh, and Windows PowerShell 5.1-compatible PowerShell.

Lookup encodes and tries the exact ordinal UTF-8 key first. Only a clean miss
permits one distinct exact Latin-1 candidate, and only when every requested
character is representable. A found UTF-8 record that is malformed or whose
compiled identity is invalid fails immediately; it never falls through.

## Preserved contracts

HDB07C adds no public type, member, option, exception type, command switch,
diagnostic identifier, JSON field/schema, or package dependency. Reusable
assembly versions remain `1.0.0.0`, and APIs remain equivalent across net8,
net9, and net10.

Runtime and Inspection remain independent of BerkeleyDb. Production contains
no native asset, dynamic native load, P/Invoke, runtime download, writer,
transaction, environment, recovery, repair, or general-purpose Berkeley DB
API. Explicit `infocmp -A/-B` files and explicit human `toe` file operands use
the accepted hashed paths; ambient discovery, frozen JSON routes, and `tic`
directory publication remain unchanged.

## Residual limitations

HDB07C does not claim:

- an atomic snapshot or arbitrary concurrent-writer safety;
- detection when different bytes are restored before the second observation
  or changed after verification;
- a big-endian host;
- automatic encoding detection beyond exact UTF-8 and representable Latin-1
  candidates;
- normalization, case folding, transliteration, best-fit mapping, or locale
  code pages;
- unsupported Berkeley DB access methods, revisions, checksums, encryption,
  subdatabases, duplicate semantics, or legacy page families; or
- hashed writes, transactions, recovery, or general-purpose database APIs.
