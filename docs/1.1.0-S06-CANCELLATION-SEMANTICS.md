# Icod.TermInfo 1.1.0 S06 — Cancellation Semantics

**Development version:** `1.1.0-Alpha-6`
**Tranche:** S06 — Cancellation semantics
**Status:** Implementation complete — validation pending

## Purpose

S06 gives parsed terminfo source a semantic representation for explicit
capability values and `capability@` cancellation declarations. The purpose is
to preserve cancellation as a tombstone while source inheritance is being
resolved, so an inherited value cannot silently reappear after a higher-priority
source entry explicitly removed it.

S06 does **not** locate or recursively resolve `use=` parents. That graph work,
including missing-parent diagnostics, cycles, depth limits, and provider
integration, remains S07.

## Adopted cancellation model

For one semantic capability identity, the Source resolver state has three
meaningful conditions:

```text
not mentioned
present with a value
explicitly cancelled
```

A cancellation therefore cannot be represented merely by deleting a value.
Deletion would make the capability indistinguishable from one which had never
been mentioned and would allow a lower-priority inherited value to reappear.
S06 records a cancellation tombstone instead.

The state mirrors the cancellation discipline already used internally by
`TerminalDescriptionBuilder`:

```text
set value      -> clear tombstone, store value
cancel value   -> remove value, set tombstone
inherit value  -> only if neither value nor tombstone exists
inherit cancel -> only if neither higher-priority value nor tombstone exists
```

The runtime builder itself is not changed. A resolved `TerminalDescription`
does not retain source cancellation provenance, so Source needs its own
short-lived semantic state until resolution is complete.

## Standard capabilities

Standard capabilities use the exact S05 runtime identities:

- `BooleanCapability`;
- `NumericCapability`;
- `StringCapability`.

Short and long source spellings which S05 maps to the same standard capability
therefore also share one cancellation tombstone. For example, cancellation of a
long variable name blocks inheritance of the corresponding short-name value.

Boolean, numeric, and string standard capabilities use separate value and
cancellation collections, matching the stable runtime semantic model.

## Extended capabilities

Known and unknown extended capabilities use the accepted S05 canonical
case-sensitive name. All extended value kinds share one namespace, just as they
do in `TerminalDescription`.

An extended cancellation removes any current extended value of that name and
records one name tombstone. A later higher-priority value of any extended kind
for the same name clears the tombstone and replaces the value.

## Local source fields

`TermInfoSourceCapabilityState.CreateLocal` applies semantic capability fields
in source order.

This gives deterministic behavior when a source entry explicitly repeats a
capability: a later local declaration replaces the earlier local value or
cancellation. That behavior matches the left-to-right processing used by the
selected ncurses compatibility family for repeated explicit fields.

The following do not enter semantic capability state:

- `use=` references — S07 owns inheritance lookup and ordering;
- period-prefixed disabled capabilities;
- invalid/reserved capability names;
- standard declarations written using the wrong value kind;
- numeric/string declarations whose values could not be decoded.

Those fields and their diagnostics remain preserved by the unresolved S04/S05
model.

## Parent-state merge contract

S06 provides two distinct merge operations because local declarations and
multiple `use=` parents have different precedence roles.

`TermInfoSourceCapabilityState.OverlayHigherPriority` composes parent states.
S07 will begin with an empty parent aggregate, process the **rightmost** `use=`
parent first, and then move leftward. Each newly processed leftward parent is
overlaid as higher priority, replacing an earlier imported parent value or
tombstone when the same capability is present.

`TermInfoSourceCapabilityState.Inherit` then applies that completed parent
aggregate beneath the child's explicit local state. Anything already present
in the child wins:

```text
local value        > inherited value
local cancellation > inherited value
local value        > inherited cancellation
local cancellation > inherited cancellation
```

This separation captures the adopted terminfo rule precisely: rightmost parents
are processed first, but later leftward parent merges can replace their imported
state, while an explicit declaration in the child still outranks every parent.

S06 tests both operations directly with already-resolved parent states. S07
will add the actual `use=` graph traversal which selects and orders those states.

## Source-parent cancellation provenance

A source parent may itself contain cancellation declarations. While resolving
source-to-source inheritance, S06 preserves those tombstones so they can have
the same effect as an inline cancellation in the child resolution state.

There is an important boundary for later provider work: an already compiled
`TerminalDescription` normally represents only effective presence/absence and
does not retain enough information to distinguish an explicit source
cancellation from an ordinary missing capability. S07 must not invent
cancellation provenance when a parent provider can supply only resolved runtime
data.

## Cloning

The semantic state supports an internal deep `Clone` operation. Values and
cancellation tombstones are copied into independent mutable collections. This is
included now because recursive S07 resolution will need to cache or reuse a
resolved parent without allowing one child merge to mutate another child's
state.

## API boundary

`TermInfoSourceCapabilityState` is deliberately internal in S06. Tests receive
friend-assembly access through:

```csharp
[assembly: InternalsVisibleTo("Icod.TermInfo.Source.Tests")]
```

No new public Source API is required for cancellation semantics, so
`docs/1.1.0-SOURCE-PUBLIC-API-BASELINE.txt` remains unchanged in this tranche.
If S07 or S08 reveals a compelling external use case, any promotion can receive
an explicit API-regret review rather than being frozen prematurely.

## Validation coverage

S06 tests cover:

- standard Boolean cancellation;
- standard numeric cancellation;
- standard string cancellation;
- known and unknown extended cancellation;
- cancellation replacing a local value;
- a later local value replacing a cancellation;
- local cancellation blocking an inherited value;
- local value blocking an inherited cancellation;
- right-to-left multiple-parent composition for values and tombstones;
- ignored disabled and semantically invalid fields;
- clone independence;
- continued `1.0.0.0` assembly identity;
- absence of S06 internal machinery from the reviewed public API baseline.

## Gate S06

S06 is complete when local values, cancellations, inherited values, multiple
parent states, and extended capabilities all obey deterministic tombstone
semantics without constructing a `TerminalDescription` or resolving a `use=`
graph.

The next tranche is **S07 — `use=` inheritance resolver**.
