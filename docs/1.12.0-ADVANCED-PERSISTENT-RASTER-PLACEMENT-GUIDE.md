# Icod.TermInfo 1.12.0 — Advanced Persistent-Raster Placement Guide

Version 1.12 extends the protocol-neutral persistent-raster planning foundation from 1.11 with exactly two advanced placement semantics:

- pixel-space source rectangles; and
- signed z-order / stacking order.

The release deliberately does **not** move concrete graphics execution into TermInfo. `Icod.TermInfo.Inspection` answers whether a semantic requirement is supported, unsupported, unknown, or contradicted and whether a requested placement is currently admissible. Rectangle coordinates, z-index values, resource/placement identities, wire encoding, acknowledgements, and terminal I/O remain downstream responsibilities.

## Relationship to the 1.11 lifecycle planner

The 1.11 lifecycle layer answers questions such as:

- can a persistent raster resource be uploaded?
- can a placement be created?
- can multiple placements, updates, deletions, or resource deletion be relied upon?

The 1.12 placement layer is orthogonal. It answers whether an otherwise-admissible placement may additionally require:

```text
PersistentRasterPlacementSubject.SourceRectangle
PersistentRasterPlacementSubject.SignedZOrder
```

`PersistentRasterPlacementPlanner` consumes an already-produced `PersistentRasterLifecyclePlan`. It does not reinterpret lifecycle evidence or replace the 1.11 planner.

## Evidence and classification

Placement evidence uses the same provenance precedence model as the lifecycle layer:

```text
Verified > Declared > CapabilityDerived
```

The reusable four-state support vocabulary remains:

```text
Unknown
Supported
Unsupported
Contradicted
```

Static absence remains `Unknown`. Same-precedence positive and negative evidence produces `Contradicted`. Lower-precedence contradictory facts remain inspectable but do not override a higher-precedence conclusion.

Example:

```csharp
using Icod.TermInfo.Inspection;

PersistentRasterPlacementProfile profile =
	PersistentRasterPlacementClassifier.Classify(
		new[] {
			new PersistentRasterPlacementEvidence(
				PersistentRasterPlacementSubject.SourceRectangle,
				isPositive: true,
				PersistentRasterPlacementEvidenceKind.Verified,
				"runtime verification",
				0
			),
			new PersistentRasterPlacementEvidence(
				PersistentRasterPlacementSubject.SignedZOrder,
				isPositive: true,
				PersistentRasterPlacementEvidenceKind.Verified,
				"runtime verification",
				1
			),
		}
	);
```

Evidence snapshots are immutable, canonically ordered, culture-independent, and bounded. The default maximum evidence count is 256 and the supported maximum is 4096.

## Static `TerminalDescription` evidence

PG05 recognizes only two explicit Icod-owned extended Boolean declarations:

```text
IcodPersistentRasterSourceRectangle
IcodPersistentRasterSignedZOrder
```

A present Boolean contributes positive `CapabilityDerived` evidence for the corresponding placement subject. Mere absence does not become negative evidence.

This is intentionally not terminal-brand inference. Names such as `xterm`, Kitty, WezTerm, or Windows Terminal do not implicitly establish placement semantics.

## Ordered database-set composition

Database-set placement inspection reuses the frozen ordered-database precedence model.

For a canonical terminal name:

- occurrence profiles preserve physical lookup order;
- an effective placement profile exists only when the effective terminal definition is conclusive;
- an earlier incomplete root prevents a later observation from being promoted to an effective winner; and
- caller-supplied evidence is applied only after an effective database winner has been established.

Caller evidence therefore cannot manufacture certainty across an indeterminate database-precedence boundary.

## Planning outcomes

A placement request must require at least one of the two 1.12 semantics.

The planner returns one of:

```text
Satisfied
RequiresRuntimeVerification
Indeterminate
Impossible
```

The decision model is conservative:

- lifecycle `Impossible` is `Impossible`;
- required placement `Unsupported` or `Contradicted` is `Impossible`;
- otherwise lifecycle `Indeterminate` remains `Indeterminate`;
- otherwise a required placement subject that is `Unknown` produces `RequiresRuntimeVerification`;
- otherwise the request is `Satisfied`.

Example:

```csharp
PersistentRasterPlacementPlan placementPlan =
	PersistentRasterPlacementPlanner.Plan(
		lifecyclePlan,
		profile,
		new PersistentRasterPlacementRequest(
			requireSourceRectangle: true,
			requireSignedZOrder: true
		)
	);
```

TermInfo does not choose concrete values for the two required semantics.

## Terminal execution handoff

After TermInfo has produced a satisfactory semantic plan, a consuming application may use `Icod.Terminal 1.12.0` to supply execution values such as:

```csharp
using Icod.Terminal;

TerminalRasterSourceRectangle sourceRectangle = new(
	8,
	4,
	320,
	180
);
TerminalRasterPlacementOptions options = new() {
	SourceRectangle = sourceRectangle,
	ZIndex = -2,
};
```

The rectangle and z-index above are not TermInfo data. They belong to the application/Terminal execution layer.

The checked-in `samples/Icod.TermInfo.PersistentRasterPlacement.Sample` demonstrates this boundary. PG07 also provides a package-reference-only downstream consumer which combines the freshly produced Inspection package with published stable `Icod.Terminal 1.12.0` on `net8.0`, `net9.0`, and `net10.0`.

No production TermInfo package depends on `Icod.Terminal`.

## Version-4 machine-readable automation

Version 1.12 adds a separate JSON schema identity:

```text
urn:icod:terminfo:inspection:json:4
```

It contains exactly:

```text
persistentRasterPlacementProfile
persistentRasterPlacementPlan
```

Example rendering uses the same bounded deterministic renderer family:

```csharp
string profileJson = TermInfoJsonRenderer.Render( profile );
string planJson = TermInfoJsonRenderer.Render( placementPlan );
```

JSON versions 1, 2, and 3 are unchanged historical contracts. Version 4 is additive rather than an in-place widening of the 1.11 lifecycle schema.

## Explicitly deferred

Version 1.12 does not introduce:

- relative-placement graphs;
- Unicode placeholder placement;
- animation or frame lifecycle;
- absolute screen-coordinate placement;
- scene graphs;
- backend/protocol preference negotiation;
- Kitty-specific ids or raw wire fields;
- image pixels or codecs; or
- live terminal probing owned by TermInfo.

Those boundaries are deliberate. The next negotiation layer should be designed only when multiple real execution alternatives and their live capability evidence exist.
