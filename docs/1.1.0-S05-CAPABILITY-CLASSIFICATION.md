# Icod.TermInfo 1.1.0 — S05 Capability Classification

**Development version:** `1.1.0-Alpha-5`
**Tranche:** S05 — Capability classification
**Packages:** `Icod.TermInfo`, `Icod.TermInfo.Source`

## Purpose

S05 classifies capability-bearing fields in the S04 unresolved source model
without applying cancellation or `use=` inheritance. Classification is a
source-layer concern, but the standard-capability identities are taken directly
from the stable `Icod.TermInfo` runtime catalog.

The tranche does not construct `TerminalDescription` values.

## Standard capability authority

`StandardCapabilityCatalog` remains the single authoritative standard
capability table. `Icod.TermInfo.Source` does not copy the Boolean, numeric, or
string capability lists.

For each standard capability, S05 accepts:

- the traditional terminfo short name (`ShortName`); and
- the long/variable terminfo name (`LongName`).

Both spellings classify as `Standard`, normalize to the same canonical short
name, and expose the exact runtime enum identity:

- `BooleanCapability`;
- `NumericCapability`; or
- `StringCapability`.

The expected `TermInfoCapabilityValueKind` is retained as `StandardValueKind`.
This permits later resolver/materializer tranches to consume the same semantic
identifier used by compiled parsing and built-in profiles.

## Compatibility-name policy

S05 deliberately does **not** treat a distinct termcap code as a terminfo source
alias. Termcap conversion and compatibility are scheduled for 1.5.0, where
loss and historical mappings can be handled explicitly.

Consequently a spelling such as the termcap `co` code for terminfo `cols` is not
silently rewritten to `cols` by the 1.1 source parser. If otherwise valid, it is
accepted as an extended capability name.

Matching is ordinal and case-sensitive.

## Extended capability classification

Valid non-standard names remain open-ended, matching the purpose of ncurses
extended capability compilation. S05 distinguishes:

- `KnownExtended` — names with established semantics in the selected ncurses
  user-capability family or names already present in Icod's built-in terminal
  profiles;
- `UnknownExtended` — valid names which are not currently recognized by those
  sources.

The built-in-profile portion is derived from the runtime
`TerminalProfiles`/`TerminalDescription.ExtendedCapabilities` data rather than
maintaining a second copied list in `Icod.TermInfo.Source`.

Unknown extended names are not errors. They remain available for later
resolution and compilation.

## Invalid and reserved names

`Invalid` is used for capability names which cannot safely represent a terminfo
source capability, including the reserved source keyword `use`, leading-period
names after the disabled-field marker has been removed, whitespace/control
characters, and source delimiter/operator characters.

Invalid names produce:

```text
TIS0020  InvalidCapabilityName
```

The field remains in the unresolved document for diagnostics and tooling.

## Standard value-kind mismatch

When a standard capability is written using the wrong source operator, S05
preserves the standard semantic identity and reports:

```text
TIS0021  StandardCapabilityTypeMismatch
```

For example, a Boolean standard capability written with a numeric `#` value is
still identifiable as that standard Boolean capability, but the parse result
contains an error.

Cancellation and disabled fields do not assert a local value kind and therefore
do not receive this diagnostic merely from their unresolved syntax. Their
classification is retained for S06.

## Public unresolved-field additions

`TermInfoSourceField` now exposes:

- `CapabilityClassification`;
- `CanonicalCapabilityName`;
- `StandardValueKind`;
- `StandardBooleanCapability`;
- `StandardNumericCapability`;
- `StandardStringCapability`.

`use=` fields return `null` for these capability-classification properties.

## Validation

S05 tests cover:

- every standard short name in `StandardCapabilityCatalog`;
- every standard long name in `StandardCapabilityCatalog`;
- exact runtime Boolean/numeric/string semantic identities;
- canonical short-name normalization;
- known and unknown extended capabilities;
- the explicit non-termcap-alias policy;
- invalid/reserved names;
- standard source-kind mismatches;
- cancellation and disabled-field classification without resolution;
- the existing checked-in `.ti` fixture corpus.

The package smoke consumer also exercises classification through the packed
`Icod.TermInfo.Source` package.

## S05 gate

S05 is complete when every standard source capability accepted by the parser
maps to the same runtime semantic identifier used by the compiled path and the
built-in profiles, while extended and invalid names remain explicitly and
deterministically distinguishable.

## Next tranche

S06 applies cancellation semantics to the classified unresolved model. It must
reuse the existing runtime builder/inheritance cancellation behavior where
practical rather than creating a second semantic implementation.
