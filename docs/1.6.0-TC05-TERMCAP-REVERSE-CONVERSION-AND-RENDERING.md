# Icod.TermInfo 1.6.0 TC05 — Termcap Reverse Conversion and Rendering

**Development version:** `1.6.0-Alpha-5`
**Tranche:** TC05 — Reverse conversion and rendering
**Package:** `Icod.TermInfo.Termcap`
**Status:** implemented for the TC05 gate

## Purpose

TC05 adds the lossless reverse interoperability path from the frozen Runtime
`TerminalDescription` model to conventional termcap source. It deliberately does
not add acquisition, environment lookup, filesystem policy, command routing, or
new dependencies on `Icod.TermInfo.Source`.

The public surface is centered on:

```text
TermcapRenderer
TermcapRenderOptions
TermcapRepresentabilityResult
TermcapRenderResult
TermcapRenderDiagnostic
TermcapRenderDiagnosticCodes
TermcapRenderDiagnosticSeverity
```

`TermcapRenderer.Analyze` performs representability preflight without emitting
text. `TermcapRenderer.Render` performs the same preflight and returns `Text ==
null` whenever an error would require semantic loss or guessing.

## Standard capability mapping

TC05 does not maintain a second Runtime-to-termcap capability table. It reverses
the TC02 Runtime-derived `TermcapCapabilityCatalog` and selects the canonical
mapping for the Runtime identity.

Before a standard capability is admitted to the render plan, the renderer also
checks the complete mapping set for the proposed two-character code using the
same value-kind selection rule used by TC02 classification. The code is emitted
only when a termcap field of that kind would classify back to the same Runtime
identity. A historical collision therefore remains nonrepresentable rather than
being silently resolved in the reverse direction.

Boolean capabilities render as the bare two-character field, numeric
capabilities use canonical decimal `#` syntax, and strings use canonical `=`
syntax after reverse string conversion.

## Extended capabilities

A Runtime extended capability is representable only when its name is an exact
parser-safe two-character termcap code which remains unmapped by TC02. The
reserved `tc` code, disabled-field-leading `.` syntax, mapped standard/historical
codes, and names outside conventional printable termcap code syntax are rejected.

Extended Boolean values render as present fields. Extended numeric values use
nonnegative decimal syntax. Extended strings use the ordinary nonparameterized
string path; a value which would be interpreted as a classic parameter program
is rejected because TC04 intentionally has no parameter profile for unmapped
fields.

## Header representability

The TC04 header rule is preserved exactly:

- the first component is the canonical Runtime name;
- following non-whitespace components are aliases;
- the final whitespace-bearing component is the verbose description.

Canonical names and aliases therefore must be trim-stable, contain no whitespace,
and contain no `|`, `:`, CR, or LF separator data. A non-null Runtime description
must be trim-stable, contain at least one whitespace character, and contain no
header separators or physical newlines. A Runtime description such as `Verbose`
with no whitespace is explicitly nonrepresentable because TC04 would parse it as
an alias.

## Strings and historical-safe escaping

Termcap string rendering is deterministic and parser-round-trippable. Canonical
escapes are used for common controls, backslash and caret are escaped, remaining
control bytes use three-digit octal, and traditional rendering is restricted to
one-byte values.

A literal colon is always emitted as:

```text
\072
```

TC05 does not emit `\:`. The parser splits fields on literal colon characters
before string decoding, so octal is the historical-safe representation which
preserves the byte without relying on a nonstandard field-separator escape.

A terminal mandatory terminfo delay suffix in TC04's exact `$<.../>` grammar is
moved back to traditional leading termcap padding. Multiple, embedded, optional,
or otherwise unsupported delay programs are rejected rather than approximated.

## Parameter programs

Parameterized standard capabilities use an exact inverse of the TC04 classic BSD
operator subset. The reverse converter recognizes the canonical Runtime programs
which TC04 produces for:

```text
%%
%d
%2
%3
%.
%+x
%>xy
%r
%i
%n
%B
%D
```

It also accepts native terminfo `%i` for the common global-increment form and
renders it as classic `%i`; TC04 canonicalizes that form back to explicit Runtime
parameter expressions on the next conversion.

The inverse decoder tracks the two classic parameter expressions and output
position, performs bounded deterministic backtracking across non-output classic
operators, and only succeeds when the Runtime program has an exact classic
termcap representation. Programs using the broader terminfo stack language which
cannot be expressed by this adopted subset produce
`TREN0006` (`ParameterProgramNotRepresentable`).

## Stable field ordering and wrapping

All rendered fields are sorted by exact two-character termcap code using ordinal
ordering. The Runtime header preserves its canonical name and alias order.

Physical wrapping uses a caller-selected preferred maximum line length, defaulting
to 80. Wrapping occurs only between complete colon-terminated fields. A
continuation is emitted as backslash plus LF with no indentation on the next
physical line. This is intentional: the TC01 parser preserves continuation-line
whitespace in the logical record, so indentation would alter the following field.
An indivisible header or field may exceed the preferred width rather than being
split unsafely.

## Representability diagnostics

TC05 diagnostics are deterministic and identify the failing Runtime capability
when applicable. The stable codes are:

```text
TREN0001  header not representable
TREN0002  standard capability not representable
TREN0003  extended capability name not representable
TREN0004  numeric value not representable
TREN0005  string value not representable
TREN0006  parameter program not representable
TREN0007  extended capability collision
```

No diagnostic is silently downgraded into output. A render result with an error
has no text.

## Round-trip gate

Representative Runtime descriptions converted from TC04 termcap source are
rendered and then passed through the existing TC01 parser, TC03 resolver, and
TC04 semantic converter. The tests cover:

- canonical Boolean, numeric, string, and extended fields;
- historical-safe colon, control, caret, and backslash escaping;
- deterministic ordering and physical wrapping;
- leading termcap padding / Runtime delay-suffix reversal;
- `%i`, `%r`, `%2`, `%3`, `%n`, `%B`, and `%D` classic parameter semantics;
- explicit rejection of negative numeric values, nonrepresentable headers, and
  extended-code collisions.

The gate is semantic: an accepted description must return to equivalent adopted
Runtime semantics without hidden approximation.

## Operational boundary

TC05 performs no process-global discovery and reads no environment variables or
filesystem paths. In particular, it does not inspect `TERMCAP`, `TERMPATH`, or
conventional termcap database locations.

Those acquisition concerns remain TC06. `captoinfo`, `infotocap`, router wiring,
and coordinated tool distribution remain TC07.
