# Icod.TermInfo 1.2.0 C03 — Extended Capability Emission

**Tranche:** C03
**Development version:** `1.2.0-Alpha-3`
**Runtime assembly identity:** `Icod.TermInfo, Version=1.0.0.0`
**Source assembly identity:** `Icod.TermInfo.Source, Version=1.0.0.0`
**Compiler assembly identity:** `Icod.TermInfo.Compiler, Version=1.0.0.0`
**Status:** implementation candidate; build/test/package validation required

## Purpose

C03 extends the deterministic C02 legacy `0432` writer with the ncurses
extended-capability section already supported by `CompiledTermInfoParser`.

The reviewed public operation remains unchanged:

```text
CompiledTermInfoWriter
    TerminalDescription -> byte[]
```

No new Compiler public API is introduced by C03. Runtime and Source public APIs
remain frozen, and the dependency graph remains:

```text
Compiler -> Runtime
Source   -> Runtime
```

Compiler does not depend on Source before C05.

## Extended section layout

When a `TerminalDescription` contains no extended capabilities, C03 emits the
same conventional entry produced by C02 and appends nothing.

When extended capabilities are present, C03 writes the frozen ncurses layout:

```text
conventional entry
optional zero alignment byte
five-short extended header
extended Boolean bytes
optional zero numeric-alignment byte
extended numeric values
extended string-value offsets
extended capability-name offsets
extended string table
```

The five unsigned 16-bit header fields are:

1. extended Boolean count;
2. extended numeric count;
3. extended string count;
4. extended string-table item count;
5. extended string-table byte size.

The string-table item count is exactly:

```text
extended string values
+ Boolean names
+ numeric names
+ string names
```

Every multi-byte field remains little-endian.

## Deterministic ordering

C03 never depends on dictionary enumeration order.

Extended capabilities are first partitioned by value kind. Within each kind,
capability names are ordered with `StringComparer.Ordinal`:

```text
Boolean names
numeric names
string names
```

The same order controls the value arrays and the capability-name sequence.
Therefore equivalent `TerminalDescription` values produce byte-for-byte
identical extended sections even when their builders received extended
capabilities in different insertion orders.

## Extended Boolean values

An effectively present extended Boolean is emitted as:

```text
0x01
```

`TerminalDescription` does not retain cancellation tombstones, so C03 does not
invent `0xfe` cancellation values or absent named Boolean entries.

A false Boolean is not an effective present capability in the public builder
model. If such a value were nevertheless presented to the writer, C03 fails
rather than emitting a named absent value which would not round-trip
semantically.

## Extended numeric values

C03 continues to emit legacy `0432`, so extended numerics use signed 16-bit
little-endian storage exactly like C02 standard numerics.

Representable present values are:

```text
0..32767
```

Negative values collide with compiled sentinel semantics and values greater
than `32767` require the C04 `01036` format-selection work. C03 rejects both
cases deterministically instead of truncating or wrapping.

## Extended strings and names

Extended string values and extended capability names use the same strict
reversible Latin-1 contract as C01/C02:

- every managed character must fit one Latin-1 byte;
- embedded NUL is rejected;
- the writer supplies the terminating NUL byte.

The extended string table stores all extended string values first in ordinal
string-capability order. It then stores all capability names in Boolean,
numeric, string order.

Extended string-value offsets are non-negative signed 16-bit offsets relative
to the beginning of the complete extended string table.

Extended capability-name offsets are non-negative signed 16-bit offsets
relative to the beginning of the name portion of that table. This is the exact
contract consumed by the existing runtime parser.

Every start offset is checked before narrowing to `short`. The complete shared
extended string table must fit the unsigned 16-bit byte-size field in the
extended header.

## Alignment

The extended header begins on an even byte boundary. If the conventional entry
ends at an odd offset, C03 inserts one zero byte before the extended header.

The extended numeric table also begins on an even byte boundary. If the
extended Boolean bytes leave it at an odd offset, C03 inserts one zero byte
before the first numeric value.

Both alignment bytes are zero, matching the runtime parser's strict validation.

## Standard/extended composition

C03 does not alter the C02 standard-table algorithm. A single output entry may
contain both standard and extended capabilities:

```text
TerminalDescription
    -> conventional standard section
    -> optional ncurses extended section
    -> CompiledTermInfoParser
    -> semantically equivalent TerminalDescription
```

Standard capability ordering remains exclusively
`StandardCapabilityCatalog.BinaryIndex`. Extended ordering remains exclusively
ordinal, case-sensitive name ordering within each kind.

## Validation

C03 tests cover:

- simultaneous standard and extended semantic round-trip;
- extended Boolean, numeric, and string round-trip;
- direct five-short extended-header assertions;
- deterministic Boolean/numeric/string kind grouping;
- ordinal, case-sensitive name ordering;
- string-value offsets relative to the complete extended string table;
- name offsets relative to the name-table start;
- exact value-first/name-second extended string-table layout;
- conventional-to-extended header alignment;
- extended Boolean-to-numeric alignment;
- insertion-order-independent byte output;
- legacy extended numeric boundary success and failure;
- strict Latin-1 and embedded-NUL failures for extended names and strings;
- signed extended string-value offset overflow;
- signed extended name offset overflow;
- unsigned extended string-table-size overflow;
- fresh Compiler package consumption with standard and extended capabilities.

The Compiler public API baseline remains unchanged from C01/C02.

## Scope boundary

C03 does not add:

- `01036` automatic or explicit format selection;
- filesystem/database-layout output;
- source-language compilation;
- native `tic`, `infocmp`, or ncurses dependencies.

Those remain later tranches.

## C03 gate

C03 is complete when all extended capability kinds survive
writer → parser round-trip, direct binary-layout tests confirm the frozen
ncurses representation, the Compiler API baseline remains unchanged, package
consumers pass on net8.0/net9.0/net10.0, and the Windows/Linux/macOS CI matrix
is green.

C04 may then introduce explicit legacy-versus-wide numeric format policy without
changing the C03 extended-section ordering and offset contract.
