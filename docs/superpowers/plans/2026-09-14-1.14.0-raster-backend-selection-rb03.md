# Icod.TermInfo 1.14.0 RB03 Candidate Evaluation Plan

**Goal:** Evaluate one `RasterBackendCandidate` deterministically by composing backend availability with the frozen 1.11 lifecycle planner and optional frozen 1.12 placement planner.

**Baseline:** accepted RB02 / `1.14.0-Alpha-2` head `6321de472a6e54a8382dd214996c22a4cf62e816`, workflow #875 / run `34865731077`.

**Primary package:** `Icod.TermInfo.Inspection`

## Constraints

- Preserve the accepted RB01/RB02 contracts and exact historical reconstruction chain.
- Add exactly one new public type in RB03: `RasterBackendPlanner`.
- RB03 exposes only single-candidate evaluation. Multi-candidate selection, preference validation, fallback ordering, canonical candidate ordering, and `RasterBackendSelectionPlan` construction remain RB04.
- Public RB03 behavior is:

```csharp
public static class RasterBackendPlanner {
	public static RasterBackendCandidateEvaluation Evaluate(
		RasterBackendCandidate candidate,
		RasterBackendSelectionRequest request
	);
}
```

- `Evaluate` must reject null candidate/request.
- The evaluator must always call `PersistentRasterLifecyclePlanner.Plan(candidate.LifecycleProfile, request.LifecycleRequest)` and retain that exact plan in the returned evaluation.
- When `request.PlacementRequest` is non-null, the evaluator must always call `PersistentRasterPlacementPlanner.Plan(lifecyclePlan, candidate.PlacementProfile, request.PlacementRequest)` and retain that exact plan. When no placement request exists, `PlacementPlan` is null.
- Running the frozen planners for retention does not weaken backend-availability precedence. Candidate status is resolved in this order:
  1. backend `Unsupported` => `Impossible`;
  2. backend `Unknown` or `Contradicted` => `RequiresRuntimeVerification`;
  3. backend `Supported` + lifecycle `Impossible` => `Impossible`;
  4. backend `Supported` + lifecycle `Indeterminate` => `RequiresRuntimeVerification`;
  5. backend `Supported` + lifecycle `Success` + no placement request => `Satisfied`;
  6. backend `Supported` + placement `Impossible` => `Impossible`;
  7. backend `Supported` + placement `RequiresRuntimeVerification` or `Indeterminate` => `RequiresRuntimeVerification`;
  8. backend `Supported` + placement `Satisfied` => `Satisfied`.
- Backend kind (`Sixel` vs `KittyGraphics`) must never alter lifecycle or placement truth.
- No backend availability classification occurs in RB03; the candidate already carries an immutable `RasterBackendProfile`.
- No evidence is merged, synthesized, reordered, or reclassified by RB03.
- No live terminal I/O or `Icod.Terminal` dependency.
- TDD is mandatory: tests-only RED before production implementation.
