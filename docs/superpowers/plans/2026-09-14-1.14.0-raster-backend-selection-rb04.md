# Icod.TermInfo 1.14.0 RB04 Deterministic Backend Selection Plan

**Goal:** Turn one or two RB03 candidate evaluations into an explicit deterministic selection plan without hidden backend ranking.

**Accepted baseline:** RB03 / `1.14.0-Alpha-3` exact head `22f38e9c6516bec9d5f6b8662f00e9b5bace7c2b`, workflow #885 / run `34871582203`.

**Primary package:** `Icod.TermInfo.Inspection`

## Constraints

- Reuse the existing public `RasterBackendPlanner`, `RasterBackendSelectionRequest`, `RasterBackendSelectionOptions`, `RasterBackendCandidateEvaluation`, and `RasterBackendSelectionPlan` types frozen by RB01/RB03.
- Add no new public type in RB04.
- Add one reviewed public method to `RasterBackendPlanner`:

```csharp
public static RasterBackendSelectionPlan Plan(
	IEnumerable<RasterBackendCandidate> candidates,
	RasterBackendSelectionRequest request,
	RasterBackendSelectionOptions? options = null
)
```

- `candidates` is snapshotted exactly once and must contain one or two non-null candidates with unique backend identities.
- An empty candidate sequence is rejected as meaningless selection input.
- More than two candidates are rejected by the frozen two-backend bound.
- Duplicate backend candidates are rejected as caller ambiguity.
- `request` is required.
- `options = null` is equivalent to new `RasterBackendSelectionOptions()` and therefore means no caller ranking.
- A non-empty preference order must be a complete set-equal ordering of the candidate backends. Partial preference, preference for an absent candidate, or any cardinality mismatch is rejected.
- Candidate evaluation delegates only to `RasterBackendPlanner.Evaluate(...)`; RB04 must not duplicate RB03 lifecycle/placement rules.
- Stored `CandidateEvaluations` are canonicalized by backend numeric identity for deterministic output only.
- Canonical output order must never decide the winner.

## Selection semantics

### Explicit complete preference

Walk `PreferenceOrder` exactly as supplied by the caller:

1. skip `Impossible`;
2. first `RequiresRuntimeVerification` stops and returns overall `RequiresRuntimeVerification` with `SelectedBackend = null`;
3. first `Satisfied` returns overall `Selected` with that backend;
4. all impossible returns `Impossible`.

An unverified preferred backend therefore blocks fallback to a lower-ranked satisfied backend.

### No preference

Count non-impossible evaluations independent of input/canonical order:

- zero => `Impossible`;
- exactly one `Satisfied` => `Selected` with that backend;
- exactly one `RequiresRuntimeVerification` => overall `RequiresRuntimeVerification` and no selected backend;
- more than one non-impossible => `RequiresPreference` and no selected backend.

This means two satisfied candidates, or one satisfied plus one unverified candidate, require explicit caller preference.
