# Icod.TermInfo 1.14.0 — Raster Backend Capability Evidence, Selection, and Planning Design

## Context

Stable `Icod.TermInfo 1.13.0` completes the first persistent-raster semantic stack in three layers:

- 1.11 defines protocol-neutral persistent-raster lifecycle evidence, classification, requests, and deterministic advisory planning;
- 1.12 adds advanced placement requirements for source rectangles and signed z-order while preserving the 1.11 lifecycle model; and
- 1.13 adds backend-neutral caller-owned runtime observations plus deterministic integration into the frozen lifecycle and placement evidence models.

Those releases intentionally avoid protocol/backend identity. That boundary was correct while the main problem was proving semantic support independently of implementation technology.

The next problem is different. A caller may have more than one concrete raster backend available and needs to know which backend can satisfy a semantic request. `Icod.Terminal 1.13.0` provides a useful downstream reality check because it has real Sixel and Kitty Graphics execution paths, live capability evidence, ordinary raster display, and a separate persistent-raster semantic capability. TermInfo must still not become a live protocol engine.

Version 1.14 therefore adds a backend-scoped advisory layer above the frozen 1.11-1.13 semantics.

## Goal

Introduce an additive `Icod.TermInfo.Inspection` model that can:

1. represent evidence that a concrete raster backend is available or unavailable;
2. combine that backend-availability result with caller-owned lifecycle and placement profiles for the same backend;
3. evaluate each backend candidate by delegating to the existing 1.11 lifecycle and 1.12 placement planners;
4. select a backend only when the caller's policy makes the choice deterministic;
5. preserve unknown, contradicted, unsupported, and preference-required outcomes rather than guessing; and
6. render the resulting backend profile and selection plan through additive JSON version 6.

The design closes the semantic chain:

```text
static terminal description / caller backend evidence
        |
        v
backend availability profile
        |
        +---- per-backend 1.11 lifecycle profile
        |
        +---- per-backend 1.12 placement profile
        |
        v
backend candidate
        |
        v
existing lifecycle + placement planners
        |
        v
candidate evaluation
        |
        +---- explicit caller preference policy
        |
        v
backend selection plan
        |
        v
caller / Icod.Terminal performs execution
```

## Non-goals

1.14 does not add:

- terminal I/O;
- active probing;
- request/response routing;
- Sixel encoding or transmission;
- Kitty APC framing or transmission;
- image/resource/placement identifiers;
- terminal generation/session identity;
- pixel buffers, quantization, compression, or image codecs;
- scene graphs, layout, cursor placement, animation, or replay policy;
- terminal-brand or terminal-name heuristics;
- hidden protocol fallback;
- hidden backend ranking;
- generic JSON deserialization;
- changes to the frozen 1.11 lifecycle semantics;
- changes to the frozen 1.12 placement semantics; or
- backend identity retrofitted into the frozen 1.13 runtime-observation types.

No production TermInfo project may reference `Icod.Terminal`.

## Architectural boundary

### Backend identity is a new layer

The 1.13 runtime-observation types are intentionally backend-neutral and remain frozen. 1.14 SHALL NOT add a backend property to them, reinterpret their meaning, or create a second runtime-evidence precedence system.

Instead, callers maintain backend-specific semantic contexts. Each backend candidate carries:

- one backend-availability profile;
- one existing `PersistentRasterLifecycleProfile`; and
- one existing `PersistentRasterPlacementProfile`.

A caller that performs backend-specific live verification may use the 1.13 integration API independently for each backend and then compose each strengthened result into a 1.14 candidate.

### Backend availability is separate from lifecycle semantics

A backend being available for ordinary raster use does not imply persistent upload, placement creation, update, deletion, resource deletion, source rectangles, or signed z-order.

The backend-availability classifier therefore answers only whether the concrete backend itself is believed usable:

```text
Unknown
Supported
Unsupported
Contradicted
```

Persistent lifecycle and placement capability truth remain owned by their existing profiles.

### Initial backend identities

The initial closed backend vocabulary is responsibility-equivalent to:

```text
Sixel
KittyGraphics
```

Exact public type/member names are frozen in RB01.

No `iTerm`, brand, emulator, OSC, DCS, APC, or control-family identity is added in 1.14.

### Static inspection is conservative

TermInfo may derive Sixel backend-availability evidence only from explicit terminal capability metadata already carried by `TerminalDescription`.

The existing extended Boolean `Sixel` advertisement may produce positive capability-derived backend evidence. Its absence SHALL remain `Unknown`; absence is not negative evidence.

1.14 SHALL NOT infer Kitty Graphics support from terminal names, profile names, environment variables, emulator brands, or unrelated capabilities. If no explicit TermInfo metadata establishes Kitty availability, Kitty remains `Unknown` until caller evidence says otherwise.

### No hidden preference

Backend identity numeric order, candidate input order, terminal name, and implementation familiarity SHALL NOT act as a preference policy.

If multiple backend candidates remain viable and the caller has not supplied a complete explicit preference order, the overall selection result SHALL report that preference is required rather than silently choosing one backend.

## Public model

RB01 SHALL freeze public responsibilities equivalent to the following concepts.

### Backend identity

```text
RasterBackendKind
    Sixel
    KittyGraphics
```

Numeric identities SHALL be explicit and stable.

### Backend evidence provenance

Use a dedicated backend evidence kind with the same semantic precedence categories already proven by lifecycle evidence:

```text
CapabilityDerived
Declared
Verified
```

The new type is separate from `PersistentRasterLifecycleEvidenceKind` so the frozen lifecycle contract does not become a generic backend contract by accident.

### Backend availability evidence

An immutable evidence assertion is responsibility-equivalent to:

```text
RasterBackendEvidence
    Backend
    IsPositive
    Kind
    SourceLabel
    SourceOrdinal
```

There is intentionally no lifecycle or placement subject on this evidence. It answers only backend availability.

Evidence validation SHALL reuse the same style of bounded deterministic provenance used by the persistent-raster evidence stack:

- defined backend value;
- defined evidence kind;
- non-empty bounded source label;
- non-negative source ordinal;
- bounded total evidence count.

### Backend availability profile

```text
RasterBackendProfile
    Backend
    Status
    Evidence
```

The profile snapshots and canonically orders evidence and exposes the deterministic classified status.

### Classifier precedence

Classification SHALL use the existing proven policy shape:

1. `Verified` evidence outranks `Declared` evidence;
2. `Declared` evidence outranks `CapabilityDerived` evidence;
3. within the highest present precedence, only positive evidence means `Supported`;
4. only negative evidence means `Unsupported`;
5. both polarities mean `Contradicted`; and
6. no evidence means `Unknown`.

Lower-precedence contradictions do not override a higher-precedence conclusion.

### Backend candidate

A backend candidate is responsibility-equivalent to:

```text
RasterBackendCandidate
    BackendProfile
    LifecycleProfile
    PlacementProfile
```

The candidate does not own live state. All three component profiles are immutable snapshots or immutable values.

The backend identity on the candidate SHALL match the backend identity of the backend profile.

A candidate SHALL NOT infer lifecycle or placement facts from its backend kind.

### Selection request

The selection request composes the frozen semantic request types instead of inventing parallel raster semantics:

```text
RasterBackendSelectionRequest
    LifecycleRequest : PersistentRasterLifecycleRequest
    PlacementRequest : PersistentRasterPlacementRequest?
```

`PlacementRequest = null` means the caller requests no advanced 1.12 placement semantics. This preserves valid lifecycle-only selection requests because the frozen `PersistentRasterPlacementRequest` intentionally rejects an empty request.

Selecting a raster backend always requires the backend itself to be supported. Lifecycle requirements are always evaluated by the existing planner; placement requirements are evaluated by the existing placement planner only when `PlacementRequest` is non-null.

1.14 does not add alpha, pixel-format, compression, transport-size, latency, or quality requirements. Those remain possible future semantic dimensions after they have an independently justified model.

### Preference policy

Preference is caller policy and is represented separately from semantic requirements.

```text
RasterBackendSelectionOptions
    PreferenceOrder : IReadOnlyList<RasterBackendKind>
```

When supplied, the preference order SHALL be explicit, unique, and complete for the candidate set being planned. A partial preference list is rejected rather than interpreted as hidden fallback policy.

An empty preference order means the caller has supplied no backend ranking.

### Candidate evaluation

Each candidate evaluation retains the evidence used to reach its result:

```text
RasterBackendCandidateEvaluation
    Candidate
    LifecyclePlan
    PlacementPlan
    Status
```

Candidate status is responsibility-equivalent to:

```text
Satisfied
RequiresRuntimeVerification
Impossible
```

Mapping is deterministic:

- backend `Unsupported` -> `Impossible`;
- backend `Unknown` or `Contradicted` -> `RequiresRuntimeVerification`;
- backend `Supported` continues into the frozen lifecycle planner;
- lifecycle `Impossible` -> `Impossible`;
- lifecycle `Indeterminate` -> `RequiresRuntimeVerification`;
- lifecycle `Success` with `PlacementRequest = null` -> `Satisfied`;
- lifecycle `Success` with a non-null placement request continues into the frozen placement planner;
- placement `Impossible` -> `Impossible`;
- placement `RequiresRuntimeVerification` or `Indeterminate` -> `RequiresRuntimeVerification`;
- placement `Satisfied` -> `Satisfied`.

### Selection plan

The overall result is responsibility-equivalent to:

```text
RasterBackendSelectionPlan
    Request
    Options
    CandidateEvaluations
    Status
    SelectedBackend
```

Overall status is responsibility-equivalent to:

```text
Selected
RequiresRuntimeVerification
RequiresPreference
Impossible
```

## Selection semantics

### With explicit preference

A complete explicit preference order acts as deterministic fallback policy.

Candidates are considered in caller preference order:

1. an `Impossible` candidate is skipped;
2. the first `RequiresRuntimeVerification` candidate stops selection and produces `RequiresRuntimeVerification` for that preferred backend; and
3. the first `Satisfied` candidate is selected.

This means a caller that says `KittyGraphics, Sixel` does not silently fall through to Sixel merely because Kitty has not yet been verified. The caller chose to prefer Kitty; the planner reports that the preferred non-impossible candidate requires verification.

If every preferred candidate is impossible, the plan is `Impossible`.

### Without explicit preference

No hidden ranking is introduced.

- If every candidate is impossible, the plan is `Impossible`.
- If exactly one candidate is not impossible, the plan reflects that candidate: `Selected` when satisfied, otherwise `RequiresRuntimeVerification`.
- If more than one candidate is not impossible, the plan is `RequiresPreference` regardless of backend enum value or input order.

The canonical evaluation order is for deterministic output only and SHALL NOT choose the winner.

### Duplicate backend candidates

A selection operation accepts at most one candidate per backend identity. Duplicate candidates for the same backend are rejected as caller ambiguity rather than merged implicitly.

## Composition with 1.13 runtime integration

1.14 SHALL reuse 1.13 instead of cloning it.

A convenience API may be added in RB05 to compose:

```text
RasterBackendProfile
+ PersistentRasterRuntimeIntegrationResult
    -> RasterBackendCandidate
```

The integration result already contains strengthened lifecycle and placement profiles. The convenience composition merely packages those existing profiles beside backend availability.

It SHALL NOT:

- relabel backend-neutral observations;
- recompute evidence ordinals;
- change 1.13 conclusive/inconclusive behavior;
- create another evidence precedence model; or
- treat an inconclusive runtime observation as backend availability evidence.

Backend availability evidence remains separately caller-owned.

## Inspection from TerminalDescription

RB02 SHALL add a conservative inspector responsibility-equivalent to:

```text
RasterBackendInspector.Inspect(TerminalDescription)
```

The initial inspection contract:

- recognizes explicit positive Sixel capability metadata as `CapabilityDerived` support evidence for the Sixel backend;
- does not synthesize negative Sixel evidence from absence;
- produces no Kitty evidence from terminal identity or brand heuristics;
- remains deterministic and culture-independent; and
- does no I/O.

If future standardized TermInfo metadata can establish additional backend facts, those additions require an explicit later review rather than being inferred heuristically in 1.14.

## JSON version 6

RB06 SHALL add additive JSON version 6 while preserving versions 1 through 5 byte-for-byte under their existing inputs.

The initial v6 document kinds are exactly:

```text
rasterBackendProfile
rasterBackendSelectionPlan
```

`rasterBackendProfile` SHALL expose:

- schema identifier/version;
- backend stable name;
- classified availability status;
- canonical backend evidence and provenance.

`rasterBackendSelectionPlan` SHALL expose:

- request lifecycle/placement requirements;
- explicit preference order;
- overall selection status;
- selected backend or explicit null;
- every candidate evaluation in canonical backend order;
- each candidate's backend status;
- lifecycle-plan evidence needed to explain admissibility;
- placement-plan evidence needed to explain admissibility; and
- whether runtime verification or explicit preference is the remaining blocker.

The renderer remains output-only. 1.14 does not add JSON deserialization.

## Bounds and determinism

RB01/RB08 SHALL freeze bounded defaults consistent with existing Inspection resource limits.

At minimum, the implementation SHALL bound:

- backend evidence count;
- source-label length;
- candidate count;
- preference count; and
- JSON output size through the existing renderer options.

Given the closed 1.14 backend vocabulary, candidate count may be capped more tightly than generic Inspection collections.

All public collections SHALL snapshot caller input exactly once. Canonical output SHALL be independent of:

- input collection implementation;
- input enumeration order where order is not semantic;
- current culture;
- process identity;
- timestamps; and
- host terminal brand.

Preference order is semantic and therefore preserved exactly when supplied.

## Downstream qualification with Icod.Terminal

Production TermInfo remains independent of Terminal.

RB07 SHALL use a package-reference-only consumer against published stable `Icod.Terminal 1.13.0` and the freshly packed TermInfo/Inspection artifacts.

The adapter remains caller-owned and explicit. Qualification may rely only on documented public Terminal semantics; it SHALL NOT inspect Terminal internals.

The intended demonstration is:

1. TermInfo static metadata can establish a Sixel backend candidate when explicit Sixel capability metadata is present;
2. Terminal's live semantic capability verification remains owned by Terminal;
3. caller policy may map a conclusive Terminal persistent-raster result into Kitty backend availability plus backend-specific 1.13 semantic observations because that mapping is adapter policy, not TermInfo inference;
4. each backend receives its own 1.13 integration context;
5. TermInfo evaluates both candidates using frozen lifecycle/placement planners; and
6. the 1.14 planner either selects according to an explicit preference order or reports the precise remaining blocker.

The sample SHALL make any Terminal-to-backend mapping assumption visible in source and documentation.

## Testing strategy

Every feature tranche SHALL use a clean RED -> GREEN checkpoint before alpha acceptance.

Required coverage includes:

- enum validation and frozen numeric identities;
- evidence precedence;
- compatible duplicates;
- highest-precedence contradictions;
- lower-precedence contradiction shadowing;
- static Sixel detection;
- static absence remains unknown;
- no Kitty brand/name inference;
- immutable snapshots;
- candidate uniqueness;
- preference completeness/uniqueness;
- input-order independence;
- explicit preference semantics;
- no-preference ambiguity;
- lifecycle planner delegation;
- placement planner delegation;
- composition from 1.13 integration results;
- culture independence;
- repeated-process determinism;
- exact JSON v6 schema validation;
- package-reference-only consumer validation on `net8.0`, `net9.0`, and `net10.0`;
- production no-`Icod.Terminal` dependency assertion;
- installed tool/package topology regression; and
- all six archive RID regressions.

## Release shape

The recommended release uses eight reviewable tranches:

```text
RB01  Contract and public API regret gate
RB02  Backend evidence, classifier, and conservative static inspection
RB03  Backend candidate composition and frozen-planner evaluation
RB04  Deterministic preference-aware backend selection
RB05  1.13 runtime-integration composition and orchestration
RB06  JSON v6 backend profile and selection-plan automation
RB07  Icod.Terminal 1.13 package-only qualification and samples
RB08  Adversarial hardening, exact freeze, documentation, and release closure
```

Each tranche corresponds to one prerelease checkpoint, with `1.14.0-Alpha-8` intended as the final prerelease if RB01-RB08 remain the complete release scope.

## Deferred work

The following remain explicitly deferred beyond 1.14:

- iTerm-style image backend identity;
- backend-specific wire/protocol capabilities;
- alpha/pixel-format/quality requirements;
- performance scoring;
- latency/bandwidth ranking;
- terminal-brand preference tables;
- automatic backend ranking without caller policy;
- scene/layout selection;
- live endpoint health;
- persistent resource lifetime management;
- Berkeley DB terminfo acquisition;
- historical vendor terminfo dialects; and
- JSON input/deserialization.

## Success criteria

1.14 is successful when a consumer can provide backend-scoped availability plus existing lifecycle/placement semantic profiles and receive a deterministic, auditable backend selection plan without teaching TermInfo how to probe or execute either protocol.

A successful release must preserve the 1.13 production dependency boundary, preserve JSON v1-v5, preserve the frozen 1.11/1.12/1.13 semantics, and make every unresolved choice explicit as either missing runtime verification or missing caller preference.
