# Icod.TermInfo 1.12.0 Advanced Persistent-Raster Placement Semantics Design

## Status

Approved architectural direction for the `1.12.0` development line.

Primary release roadmap:

`Icod.TermInfo-1.12.0-Advanced-Persistent-Raster-Placement-Semantics-and-Planning-Roadmap.md`

Baseline: stable `1.11.0` on `main` after repository-wide coding-convention normalization.

Downstream semantic target: stable `Icod.Terminal 1.12.0` advanced persistent-raster placement geometry.

---

## 1. Problem statement

Icod.TermInfo 1.11 established protocol-neutral persistent-raster lifecycle evidence, classification, planning, description/database-set composition, and version-3 machine-readable automation. It deliberately stopped short of advanced placement semantics.

Icod.Terminal 1.12 now has a bounded advanced placement execution surface:

- pixel-space source rectangles; and
- signed z-order.

TermInfo needs a matching semantic layer that can answer whether those requirements are statically known, contradicted, unsupported, or require live verification without importing Terminal's concrete execution values or protocol state.

The 1.12 design must remain additive. Frozen 1.11 lifecycle types and JSON v3 must not be widened in place.

---

## 2. Chosen architecture

1.12 introduces a new parallel placement-semantics family inside `Icod.TermInfo.Inspection`.

It reuses the frozen 1.11 support-state vocabulary:

```csharp
PersistentRasterLifecycleSupportStatus
```

but does not add values to:

```csharp
PersistentRasterLifecycleEvidenceSubject
PersistentRasterLifecycleOperation
```

The new feature enum is deliberately small:

```csharp
public enum PersistentRasterPlacementFeature {
    SourceRectangle = 0,
    SignedZOrder = 1,
}
```

TermInfo placement requirements are Boolean semantic requirements. They do not carry rectangle coordinates or actual z-order values.

The execution values remain downstream concerns:

```text
TermInfo: require SourceRectangle semantic support
Terminal: TerminalRasterSourceRectangle concrete value

TermInfo: require SignedZOrder semantic support
Terminal: int? ZIndex concrete value
```

---

## 3. Public model responsibilities

The 1.12 public family should be responsibility-equivalent to:

```text
PersistentRasterPlacementFeature
PersistentRasterPlacementEvidenceKind
PersistentRasterPlacementEvidence
PersistentRasterPlacementProfile
PersistentRasterPlacementRequirements
PersistentRasterPlacementPlanStatus
PersistentRasterPlacementPlanIssueKind
PersistentRasterPlacementPlanIssue
PersistentRasterPlacementPlan
PersistentRasterPlacementOptions
PersistentRasterPlacementClassifier
PersistentRasterPlacementPlanner
PersistentRasterPlacementInspector
```

Names may be adjusted only before PG01 API freeze if repository consistency requires it.

### Evidence

Evidence records one assertion about one placement feature with:

- feature;
- support polarity/status contribution;
- evidence kind/provenance;
- stable source text/identity when applicable;
- whether runtime verification remains required.

Evidence is immutable and bounded.

### Profile

The profile independently exposes support status for:

```text
SourceRectangle
SignedZOrder
```

and retains the complete canonical evidence snapshot.

### Requirements

Requirements represent only whether source cropping and/or signed stacking are needed.

An empty requirements value is invalid because it would add no 1.12 semantic constraint.

### Plan

The placement plan reports whether those requirements are:

```text
Satisfied
RequiresRuntimeVerification
Impossible
Indeterminate
```

The exact final enum names are frozen in PG01 after RED API-contract tests.

The plan retains structured issues and the canonical requirement/profile context needed for deterministic automation.

---

## 4. Lifecycle composition

Placement semantics do not replace the 1.11 lifecycle planner.

A consumer performing persistent placement must first have an admissible 1.11 lifecycle result for the required lifecycle operations. The 1.12 planner then evaluates advanced placement requirements against the 1.12 placement profile.

A supported `SourceRectangle` feature does not imply that persistent upload or placement creation is supported. Conversely, a successful 1.11 placement-creation plan does not imply source cropping or signed z-order support.

The two contracts are orthogonal and composable.

---

## 5. Evidence precedence

Placement classification follows the 1.11 philosophy:

```text
explicit verified semantic evidence
        >
explicit declared semantic evidence
        >
recognized capability-derived evidence
        >
absence / unknown
```

Contradictory positive and negative evidence remains visible. The classifier must not discard conflict to manufacture a Boolean answer.

Unknown means insufficient evidence, not unsupported.

---

## 6. TerminalDescription evidence

Static description evidence may establish a placement feature only where there is a reviewed capability mapping with semantics strong enough to support that conclusion.

Terminal-brand/name heuristics are forbidden.

Absence of a recognized capability contributes no negative evidence by default.

Caller-supplied declared or verified evidence remains the mechanism for strengthening static knowledge when the terminfo database cannot encode a modern extension directly.

---

## 7. Database-set composition

The effective terminal definition remains governed exclusively by the frozen 1.10 database-set precedence model.

Placement inspection over a database set must preserve:

- effective database/root provenance;
- shadowed definitions;
- incomplete earlier roots;
- indeterminate effective definition results;
- caller-supplied placement evidence applied only after the effective-description boundary is established.

1.12 must not create a second precedence algorithm.

---

## 8. JSON versioning

Schemas v1, v2, and v3 remain immutable.

1.12 introduces schema version 4 with exactly:

```text
persistentRasterPlacementProfile
persistentRasterPlacementPlan
```

The v4 renderer must be deterministic, bounded, culture-independent, and UTF-8 bounded under the existing renderer options policy.

No existing document kind changes shape or meaning.

---

## 9. Bounds

PG01 freezes explicit limits before feature implementation.

The design preference is to reuse existing Inspection-wide evidence/output bounds where those limits already serve the same denial-of-service purpose. A new limit is introduced only when placement semantics have a distinct cardinality.

At minimum:

- feature count is fixed at two for 1.12;
- evidence collection size is bounded;
- issue collection size is bounded;
- serialized output uses the existing bounded JSON renderer policy;
- database-set composition retains existing catalog/root bounds.

---

## 10. Error model

Invalid public arguments and undefined enum values use ordinary argument exceptions consistent with the repository.

Ordinary semantic outcomes do not use exceptions:

- unknown evidence;
- unsupported requirements;
- contradictory evidence;
- runtime verification required;
- incomplete database-set evidence.

These are represented in profile/plan state and structured issues.

---

## 11. Downstream integration

The package-only interoperability test may reference both released packages in a dedicated non-production qualification project/tool, but production `Icod.TermInfo.Inspection` must not acquire an `Icod.Terminal` dependency.

Qualification proves this mapping:

```text
PersistentRasterPlacementFeature.SourceRectangle
    <-> TerminalRasterPlacementOptions.SourceRectangle

PersistentRasterPlacementFeature.SignedZOrder
    <-> TerminalRasterPlacementOptions.ZIndex
```

The proof concerns semantic agreement only. TermInfo never constructs terminal resource/placement handles and never owns concrete geometry values.

---

## 12. Explicit non-goals

1.12 does not add:

- relative placement;
- parent/child placement graphs;
- Unicode placeholders;
- animation/frame semantics;
- screen-coordinate layout;
- scene graphs;
- protocol/backend preference;
- protocol negotiation;
- backend ranking;
- live-evidence interchange as a generalized transport contract;
- raw Kitty/Sixel fields;
- public terminal image or placement identifiers;
- raster data or codecs;
- terminal probing owned by TermInfo.

---

## 13. Test strategy

Every tranche follows RED -> minimal implementation -> GREEN -> full affected-suite verification.

PG01 must begin with contract tests that freeze:

- exactly two placement features and their numeric identities;
- reuse of `PersistentRasterLifecycleSupportStatus`;
- no mutation of the 1.11 lifecycle enum/value set;
- no mutation of v3 schema/document-kind contract;
- no `Icod.Terminal` production dependency;
- invalid enum rejection and immutable snapshot expectations for the initial public types.

Later tranches add:

- evidence ordering/contradiction tests;
- culture/repetition determinism;
- planner truth tables;
- lifecycle-composition tests;
- effective database-set precedence and incompleteness tests;
- v4 normalized fixture/schema tests;
- package-only net8/net9/net10 consumers;
- installed tool/archive smoke as release closure requires.

## 15. Future handoff

Multi-protocol preference/negotiation remains intentionally deferred until Terminal has more than one meaningful execution path for the same semantic outcome and there is enough live-verification data to rank candidates without brand heuristics.

A generalized live-evidence interchange contract may precede that negotiation work if needed.
