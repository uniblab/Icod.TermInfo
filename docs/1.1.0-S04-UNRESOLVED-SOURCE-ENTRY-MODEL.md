# Icod.TermInfo 1.1.0 S04 — Unresolved Source-Entry Model

**Development version:** `1.1.0-Alpha-4`
**Package:** `Icod.TermInfo.Source`
**Status:** Implemented; validation pending
**Next tranche:** S05 — Capability classification

## Purpose

S04 composes the lexical/source-location work from S02 with the value semantics
from S03 and introduces the first structured representation of a terminfo source
document.

The S04 model is deliberately unresolved. It preserves what the source says but
does not yet decide what a capability name means in the canonical runtime
catalog, apply cancellations, resolve `use=` inheritance, or construct a
`TerminalDescription`.

## Public model

S04 adds:

- `TermInfoSourceParser` — parses `string` or `TextReader` input;
- `TermInfoSourceParseResult` — returns the document plus deterministic
  diagnostics;
- `TermInfoSourceDocument` — contains entries in document order and retains the
  complete S02 lexical token stream;
- `TermInfoSourceEntry` — preserves canonical name, aliases, description,
  ordered fields, and the entry source span;
- `TermInfoSourceField` — preserves unresolved capability/reference identity,
  decoded S03 values where applicable, exact lexical text, and source span;
- `TermInfoSourceFieldKind` — distinguishes Boolean, numeric, string,
  cancellation, `use=`, and disabled fields.

The model is immutable to callers. Collection-valued properties are copied when
the model is constructed.

## Source-order and provenance contract

Entry order and field order are preserved exactly at the semantic source level.
Duplicate capability declarations and multiple `use=` references are retained
rather than collapsed.

`TermInfoSourceDocument.Tokens` retains the complete lexical token sequence.
This keeps comments, malformed lexical units, exact token text, and source spans
available for later diagnostics and inspection without promoting comments or
formatting into resolved terminal semantics.

Each entry and field retains a `TermInfoSourceSpan`. The entry span begins at the
canonical name and extends through its final semantic header component or field.

## Value-semantics composition

Numeric and string fields are decoded through `TermInfoSourceValueParser`.
Successful values are stored in `NumericValue` or `StringValue`.

If S03 value decoding reports an error, the field is still retained with:

- its unresolved capability name;
- its exact lexical `Text`;
- its source `Span`;
- a `null` decoded value.

The value diagnostics are merged with S02 lexical diagnostics and returned in
deterministic source order through `TermInfoSourceParseResult.Diagnostics`.
This permits diagnostic tooling to inspect recoverable source without losing the
field that caused an error.

## Cancellation and inheritance boundary

S04 records, but does not apply:

```text
capability@
use=parent
```

Cancellation fields remain ordinary unresolved fields with kind
`CancelledCapability`. `use=` declarations remain ordered `UseReference` fields
whose `ReferenceName` is the named parent entry.

No parent lookup, graph construction, precedence processing, cancellation
application, or cycle detection occurs in S04. Those behaviors remain assigned
to S06 and S07.

## Capability-classification boundary

S04 intentionally does **not** distinguish:

```text
standard capability
known extended capability
unknown extended capability
invalid/reserved capability name
```

Doing so here would either duplicate the canonical `Icod.TermInfo` capability
catalog or prematurely couple parsing to classification policy.

S05 will map the unresolved `CapabilityName` values through the existing runtime
metadata and establish the source-name compatibility policy.

## Disabled ncurses fields

The S02 leading-period form is retained as
`TermInfoSourceFieldKind.DisabledCapability`.

Its exact lexical text and unresolved capability name are preserved, but its
value is not interpreted or applied. This keeps the source construct available
for later rendering/inspection while ensuring it has no semantic effect during
S04.

## Error recovery

S04 remains bounded by the S02 source-length policy. Parsing is linear over the
bounded lexical token stream.

Recoverable lexical and value errors do not cause the parser to throw. Examples
include:

- an empty canonical header name already diagnosed by S02;
- a missing `use=` target;
- an invalid numeric spelling;
- an invalid or incomplete string escape.

The unresolved document remains available alongside diagnostics. Programmer
errors such as passing `null` to a public parser API continue to use normal .NET
argument exceptions.

## Validation

S04 tests cover:

- multiple entries in document order;
- aliases and descriptive header components;
- Boolean, numeric, string, cancellation, `use=`, and disabled fields;
- numeric and string value composition from S03;
- duplicate declarations and multiple `use=` references;
- lexical and value error recovery;
- deterministic merged diagnostic order;
- `TextReader` parity;
- preservation of comments in the retained token stream;
- the existing checked-in T29 `.ti` source corpus;
- the absence of `TerminalDescription` from the unresolved public model;
- the reviewed Source public-API baseline.

## S04 completion gate

S04 is complete when supported source can be parsed into immutable unresolved
entries without constructing `TerminalDescription` and without losing
information required by later capability classification, cancellation,
inheritance resolution, or diagnostics.

The next implementation tranche is **S05 — Capability classification**.
