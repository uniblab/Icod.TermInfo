# Icod.TermInfo 1.8.0 RP06 - infocmp Planning Command and Distribution

**Development version:** `1.8.0-Alpha-6`
**Roadmap tranche:** RP06
**Implementation base:** `31fbb8215b6a9acda79a5acc4ed006d3cd87a012`

## Purpose

RP06 exposes the reusable Inspection parent planner through the existing
`infocmp` command and both coordinated tool distributions. The command remains a
thin adapter: it parses policy, acquires the explicitly named target and
candidates, constructs immutable planner options, and writes the returned source.
Candidate search, scoring, semantic validation, bounded enumeration, and source
synthesis remain owned by `Icod.TermInfo.Inspection`.

## Reviewed command form

```text
infocmp --plan-use [options] target candidate [candidate ...]
```

The first operand is the target. Each later operand is one candidate position.
The candidate operand's exact spelling becomes its potential `UseName`, including
an alias spelling. Candidate order supplies the planner's final ordinal
tie-break. Duplicate candidate spellings are rejected as a usage error because
they add no command-level identity and only enlarge the search space.

`-A directory` controls target acquisition. `-B directory` controls acquisition
of every explicit candidate. When either option is omitted, that side retains
the existing Runtime system-provider policy. The command never adds candidates
by inspecting a catalog, scanning a directory, or consulting additional system
locations. RP05 catalog orchestration remains available through the reusable
Inspection API; a command-level all-candidates mode is deliberately deferred.

## Presentation policy

The existing source controls map directly into
`TerminalDescriptionSourceSynthesisOptions` inside the planning options:

```text
-0
-1
-w width
-s d|i|l|c
-x
```

No layout, capability ordering, extended-capability, delta, or cancellation
logic is reimplemented in the command.

## Planning bounds

RP06 exposes four long-form controls:

```text
--max-parents count
--max-plans count
--require-exhaustive
--allow-bounded
```

`--max-parents` accepts 0 through 64, matching the command's maximum explicit
candidate count. Its default is 2. `--max-plans` accepts 1 through 1,000,000 and
defaults to 4,097. The reusable planner remains authoritative for constructor
validation and execution of both bounds.

Exhaustive planning is the default. `--require-exhaustive` makes that default
explicit for scripts. If the ordered plan space exceeds the evaluation budget,
the command emits a controlled operational diagnostic and no source.
`--allow-bounded` opts into the best plan from the deterministic evaluated
prefix. The two policy switches are mutually exclusive.

Planning-bound controls without `--plan-use` are usage errors. No bound control
is accepted and ignored.

## Selector interactions

Planning is distinct from 1.7 explicit synthesis and semantic comparison:

- `-u` and `--plan-use` are mutually exclusive;
- `-d`, `-c`, and `-n` cannot be combined with planning;
- `-q` remains comparison-only;
- `-D` remains a standalone database-location operation;
- `-A`, `-B`, `-0`, `-1`, `-w`, `-s`, and `-x` retain their established
  acquisition or source-presentation meanings;
- existing rendering, comparison, and `-u` forms retain their behavior.

Missing candidates, duplicate candidate spellings, unsupported numeric bounds,
conflicting exhaustive policy, and selector conflicts return status 2 and write
only a usage diagnostic to stderr.

## Output, diagnostics, and cancellation

On success, stdout contains only `TerminalDescriptionSourcePlan.Source`. The
command writes no report, score, progress message, or acquisition text beside
the source. Successful planning leaves stderr empty.

Target and candidate acquisition retain the existing `INFOCMP0002` and
`INFOCMP0003` diagnostics. Planner argument, representation, or exhaustive-
budget failures use the existing `INFOCMP0004` operational diagnostic and status
1. A cancellation token is observed before command work, during each acquisition,
and at all RP04 planner boundaries. Cancellation returns status 130 without a
partial plan.

## Distribution composition

The router removes only its `infocmp` command operand and invokes the exact same
`Icod.TermInfo.InfoCmp.Command` implementation in process. Direct and routed
tests require identical status, stdout, and stderr for the controlled planning
operation.

The installable `Icod.TermInfo.Tools` package smoke and standalone archive smoke
both publish the same target, useful alias candidate, and decoy candidate. They
run `--plan-use`, require the useful alias reference, reject a decoy reference,
and validate the emitted source with `tic -c` after composing it with the selected
parent source. They then publish that source to a second explicit database and
require its canonical effective rendering to equal the original target rendering.

Archive execution smoke expands to the six native archive RIDs:

```text
win-x64
win-arm64
linux-x64
linux-arm64
osx-x64
osx-arm64
```

PR, main, and release workflows therefore execute the planning path from all
six standalone archives on matching GitHub-hosted runners. Structural archive
validation remains separate and continues to inspect all archive payloads
without executing a foreign architecture.

## Controlled ToolSuite walkthrough

`samples/ToolSuite` adds `icod-demo-decoy` and a selected-parent source fixture.
The walkthrough:

1. publishes the target, useful parent, and decoy to an explicit database;
2. runs direct `infocmp --plan-use` with the decoy first;
3. requires `use=icod-demo-base` and no decoy reference;
4. runs the same operation through `icod-terminfo infocmp`;
5. compares the direct and routed source byte for byte; and
6. combines the planned source with the selected parent and validates it through
   `tic -c -x`.

The walkthrough does not depend on host terminfo state or native ncurses.

## Verification

RP06 tests prove:

- separate `-A` and `-B` roots are honored;
- useful alias spelling is preserved while an inferior decoy is not selected;
- presentation options reach the reusable planner;
- candidate order breaks an otherwise equal score tie;
- exhaustive budget failure and bounded opt-in have distinct outcomes;
- every selector interaction and planning-bound range is controlled;
- duplicate candidates and missing candidates are usage errors;
- cancellation emits no output;
- direct and routed planning are exactly equivalent;
- package and archive smoke execute and validate the planning path; and
- the ToolSuite sample freezes direct, routed, decoy, selected-parent, and
  `tic -c` evidence.

## Compatibility result

RP06 adds no reusable public API and changes no 1.7 synthesis behavior. Runtime,
Source, Compiler, Inspection, and Termcap production dependency directions remain
unchanged. All reusable assemblies retain version `1.0.0.0`.

All coordinated packages and commands advance to `1.8.0-Alpha-6`.
