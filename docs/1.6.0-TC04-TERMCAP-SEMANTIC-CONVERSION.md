# Icod.TermInfo 1.6.0 TC04 — Termcap Semantic Conversion

**Development version:** `1.6.0-Alpha-4`
**Tranche:** TC04
**Status:** Implementation patch

## Objective

TC04 converts a TC03-resolved termcap source entry into the canonical immutable
Runtime `TerminalDescription` model. It is the first 1.6 tranche which crosses
from termcap source semantics into Runtime capability semantics.

Conversion remains explicit and side-effect free. TC04 does not inspect
`TERMCAP`, `TERMPATH`, conventional database paths, or process-global state. It
does not add command/router behavior and does not render termcap text; those
remain TC06, TC07, and TC05 work respectively.

## Public conversion surface

The public surface is centered on:

```text
TermcapConverter
TermcapConversionResult
TermcapConversionDiagnostic
TermcapConversionDiagnosticCodes
TermcapConversionDiagnosticSeverity
TermcapConversionDecision
```

`TermcapConverter.Convert` accepts only a `TermcapSourceResolvedEntry`. Callers
therefore choose parsing and `tc=` acquisition/resolution policy before semantic
conversion begins.

## Header semantics

TC04 adopts a deterministic traditional header interpretation:

1. the first header component is the canonical Runtime terminal name;
2. subsequent components are aliases;
3. when the final component contains whitespace, it is the verbose Runtime
   description rather than an alias;
4. when the final component contains no whitespace, it remains an alias and no
   verbose description is synthesized;
5. duplicate canonical/alias identities are ignored with an explicit
   approximation diagnostic rather than being passed to the Runtime builder.

This preserves common historical descriptions such as
`vt|vt100|DEC VT100` without inventing a verbose description for headers which
contain only machine-readable names.

## Capability mapping

TC04 consumes the TC02 classifier after TC03 has established the effective field
set.

- canonical Runtime mappings are applied directly to the existing Boolean,
  numeric, and string capability enums;
- Runtime-retained `OT...` compatibility capabilities remain ordinary exact
  standard mappings;
- adopted AT&T/XENIX/Tektronix/IRIX aliases map to their TC02 canonical Runtime
  target and produce an informational `HistoricalAlias` decision;
- an unresolved ambiguous historical code is an error; TC04 never guesses;
- a field whose termcap syntax has the wrong value kind for its selected Runtime
  mapping is unrepresentable and is an error;
- when two distinct termcap codes map to the same Runtime capability identity,
  the higher-priority TC03 field wins and the lower-priority field is ignored
  with an explicit approximation diagnostic.

## Unmapped two-character capabilities

An unmapped Boolean, numeric, or string field is preserved as a Runtime extended
capability using its exact two-character name whenever that name does not collide
with a standard terminfo short name. This is a lossless preservation decision,
not a silent standard-capability invention, and is reported as `Extended`.

A colliding unmapped name is reported as unsupported because Runtime deliberately
disallows extended capabilities from shadowing standard terminfo short names.

## String conversion

Termcap and terminfo parameter/padding syntax are not interchangeable. TC04 does
not copy source strings blindly.

Traditional leading termcap padding such as `5`, `20`, or `3.5*` is moved to an
equivalent terminfo `$<.../>` delay suffix so the Runtime output layer sees the
same post-string delay semantics.

TC04 translates the classic BSD parameter operators only for the traditional
capabilities which are defined to take numeric parameters. A percent sign in an
ordinary non-parameterized string remains literal.

The supported operators are:

```text
%%
%d
%2
%3
%.
%+x
%>xy
%r
%i
%n
%B
%D
```

The translation emits the Runtime's ordinary terminfo parameter language using
`%p1`, `%p2`, stack arithmetic, conditionals, and terminfo output formats. The
traditional `%2` and `%3` forms are emitted with modulo 100/1000 followed by
`%02d` / `%03d`, preserving the actual fixed-width byte behavior of BSD-style
`tgoto` implementations even though historical documentation describes the
operators using printf-style notation. TC04 also accepts `%02` and `%03` as
compatibility spellings. The result can therefore be expanded by
`TermInfoParameterExpander` like any other Runtime string capability.

TC04 translates parameters only for an explicit set of standard one- and
two-numeric-parameter capability profiles. If another standard or unmapped
capability contains recognizable classic termcap parameter operators, conversion
fails as `Unsupported` rather than treating those operators as literal text.
This keeps higher-arity and string-parameter capabilities outside the TC04
boundary without silently changing their execution semantics.

A parameter operator outside this frozen TC04 set is returned as an
`Unrepresentable` error. TC04 does not pass unknown termcap `%` programs through
and hope that Runtime expansion happens to interpret them compatibly.

## Structured loss reporting

`TermcapConversionDecision` distinguishes:

```text
Exact
HistoricalAlias
Extended
Approximation
Unsupported
Unrepresentable
```

`HistoricalAlias` and `Extended` are observable but lossless. `Approximation`,
`Unsupported`, and `Unrepresentable` set `TermcapConversionResult.HasLoss`.
Errors suppress the final `TerminalDescription`; TC04 does not expose a partial
semantic description as though conversion had succeeded.

Diagnostics retain the originating unresolved entry, effective source field when
one exists, and best available source span.

## Boundary retained for TC05+

TC04 deliberately does not:

- render Runtime descriptions back to termcap;
- determine reverse representability;
- read `TERMCAP` or `TERMPATH`;
- search conventional termcap files;
- add `captoinfo` / `infotocap` commands;
- change existing Runtime acquisition precedence or fallback behavior.

TC05 is next. It will define reverse representability and deterministic termcap
rendering from Runtime descriptions, using TC04's explicit semantic decisions as
the forward-conversion baseline.

## TC04 gate

TC04 is complete when representative resolved termcap descriptions materialize
as ordinary `TerminalDescription` instances; canonical mappings, historical
aliases, extended fields, inherited cancellation, classic parameter strings, and
padding retain their adopted semantics; and every approximation, unsupported
construct, or unrepresentable value is observable through structured diagnostics
on all three target frameworks.
