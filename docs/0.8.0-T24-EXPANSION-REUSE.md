# Icod.TermInfo 0.8.0 T24 — Expansion Reuse and Extended Capability Symmetry

**Development version:** `0.8.0-alpha.4`

T24 reuses parsed terminfo parameter programs within each immutable
`TerminalDescription` and gives parameterized extended string capabilities the
same explicit expansion path as standard string capabilities.

## Scope

T24 adds:

- lazy parsed-program reuse for standard string capabilities;
- lazy parsed-program reuse for extended string capabilities;
- one cache per immutable `TerminalDescription`;
- thread-safe first-use initialization;
- explicit `ExpandExtendedString` overloads;
- caller-owned `TermInfoExpansionContext` support for extended strings;
- deterministic missing/wrong-kind errors for extended expansion;
- cache-bound and concurrency regression tests.

T24 does not add:

- a process-global parsed-program cache;
- a cache keyed by arbitrary source strings;
- filesystem or compiled-database caching;
- byte/Latin-1 output changes;
- terminal-aware padding changes;
- profile cancellation semantics.

Those remain assigned to later tranches.

## Cache ownership and keys

Every `TerminalDescription` owns two private caches.

The standard cache is keyed by `StringCapability`. A key can enter the cache
only after that capability has been confirmed present in the immutable
description.

The extended cache is keyed by the exact case-sensitive extended capability
name. A key can enter the cache only after the immutable description confirms
that the name exists and carries a string value.

Consequently, cache growth is bounded by the string capabilities already
contained in that one description. Arbitrary caller-supplied source strings
never become cache keys.

Two descriptions containing identical source strings do not share parsed
programs. A standard capability and an extended capability containing the same
source string also remain separate cache entries because their namespaces and
identities are distinct.

## Lazy and concurrent initialization

Cache entries are created on first valid expansion or first internal program
request. Each entry stores a `Lazy<TermInfoParameterProgram>` using
`LazyThreadSafetyMode.ExecutionAndPublication`.

The surrounding dictionaries are `ConcurrentDictionary` instances. Concurrent
first use therefore publishes one cache entry per capability, and only the
published lazy value performs parsing.

A malformed immutable capability program may cache its parse exception. This
is intentional: the capability source cannot change, so reparsing the same
invalid source cannot produce a different successful program.

## Standard expansion

The existing APIs remain unchanged:

```csharp
terminal.Expand(StringCapability.CursorAddress, row, column);

terminal.Expand(
    StringCapability.SetAttributes,
    expansionContext,
    parameters);
```

They now obtain a per-description cached `TermInfoParameterProgram` rather than
calling the arbitrary-source `TermInfoParameterExpander` path on every
expansion.

Output and exception semantics remain those established by T23.

## Extended string expansion

T24 deliberately does not add an ambiguous `Expand(string, ...)` overload.
Standard and extended namespaces remain explicit.

Extended parameterized strings use:

```csharp
terminal.ExpandExtendedString("XM", 1);
```

and, when persistent uppercase variables are required:

```csharp
terminal.ExpandExtendedString(
    "X_CUSTOM",
    expansionContext,
    parameters);
```

The name lookup is exact and case-sensitive.

If the extended capability is missing, expansion throws
`InvalidOperationException`. If the name exists but carries a Boolean or
numeric value, expansion also throws `InvalidOperationException`.

Once the string value has been selected, parsing, analysis, parameter typing,
evaluation, resource limits, and exception behavior are exactly the same T23
runtime used for standard capabilities.

## Direct arbitrary-source parsing

`TermInfoParameterProgram.Parse` remains unchanged and independent.

Likewise, `TermInfoParameterExpander.Expand` remains the convenience path for a
caller who deliberately supplies an arbitrary source string. T24 does not add
a hidden global cache to that path.

This distinction is intentional:

```text
arbitrary caller source
    -> TermInfoParameterProgram.Parse / TermInfoParameterExpander
    -> no global cache

immutable TerminalDescription standard string
    -> cache key: StringCapability
    -> lazy reusable TermInfoParameterProgram

immutable TerminalDescription extended string
    -> cache key: exact extended name
    -> lazy reusable TermInfoParameterProgram
```

## T24 acceptance

T24 is complete when normal build/test confirms:

- repeated standard expansion reuses one parsed program per capability;
- repeated extended expansion reuses one parsed program per exact name;
- concurrent first use is safe;
- cache counts cannot grow from missing or wrong-kind capabilities;
- separate descriptions do not share cache entries;
- standard and extended cache namespaces remain separate;
- extended context-aware expansion preserves T23 persistent-variable semantics;
- standard and extended strings share T23 analyzer/evaluator type behavior;
- direct `TermInfoParameterProgram.Parse` remains independently reusable;
- no process-global arbitrary-source cache has been introduced.
