# Icod.TermInfo 0.8.0 Contract Audit

This document records the final T31 repository-side contract audit for the
`Icod.TermInfo` 0.8.0 release candidate.

T30 froze the intended public API, documentation, samples, package shape, and
CI contract at `0.8.0-rc.1`. T31 sets the project/package version to the final
`0.8.0` value, closes the remaining completion-gate test gaps, and records the
evidence map below.

This document does **not** claim that the final T31 commit has already passed
GitHub Actions. The release is ready to be validated, but `v0.8.0` must be
created only after the exact final candidate passes the complete Windows,
Linux, macOS, and package-validation workflow. No source/package content may
change between that successful validation and tagging.

## Semantic completion verdict

The T31 semantic-completion question is answered **yes**:

> A caller/provider can construct, without changing `Icod.TermInfo` internals,
> a complete immutable `TerminalDescription` representing every semantic value
> shape required by the supported future 0.9 compiled formats, then query,
> enumerate, safely parse/analyze/expand, and output its capabilities through
> the frozen 0.8 runtime.

The basis for that conclusion is structural rather than terminal-specific:

- T22 represents the complete selected standard compiled-table universe through
  canonical metadata and fixed binary indices;
- standard and extended numeric values are signed 32-bit `int` values;
- arbitrary case-sensitive extended Boolean/numeric/string capabilities are
  representable without terminal-name branches;
- primary name, aliases, and verbose description are distinct immutable data;
- conventional compiled capability bytes are preserved one-to-one through the
  Latin-1 bridge;
- standard and extended parameterized strings use the same hardened generic
  parser/analyzer/evaluator;
- effective absent/canceled binary states map to the public absent semantic
  without requiring a public cancellation-state type;
- terminal-aware output consumes explicit description/transport facts rather
  than process-global terminal state;
- provider composition already has deterministic first-hit and clean-miss
  semantics suitable for future acquisition providers.

`T31CompletionGateTests.FutureCompiledSemanticShapeFitsFrozenPublicModel`
exercises that conclusion directly with a provider-created description carrying
aliases, a verbose description, standard/extended capabilities, direct-color
scale numeric values, a near-`int.MaxValue` extended number, absent standard
values, high-byte strings, parameter expansion, per-description enumeration,
and exact Latin-1 output with padding removal.

## Final public contract

The T30 public API freeze remains unchanged in T31.

The final 0.8 surface deliberately keeps these implementation details internal:

- parameter-program instruction nodes;
- parameter-program analysis results;
- per-description parsed-program caches;
- profile-composition cancellation state;
- future compiled-entry parser structures;
- future filesystem/system-database discovery state.

The public contract remains centered on immutable terminal descriptions,
canonical standard metadata, generic extended values, explicit parameter
programs/expansion, semantic color helpers, explicit output policy, provider
composition, environment/size helpers, built-in profiles, and the narrowly
scoped reversible Windows VT lease.

## Completion-gate strengthening in T31

T31 intentionally makes very few code changes.

`CompletionGateTests` is extended so its release-boundary checks include the
three 0.8 Windows identities and so its “every built-in capability string”
padding test actually includes:

- `winconsole`;
- `ms-terminal`;
- `ms-terminal-direct`.

`T31CompletionGateTests` then adds three final assertions:

1. the assembly identifies the final `0.8.0` release rather than a prerelease;
2. every frozen built-in canonical name resolves to the exact singleton
   description exposed by `TerminalProfiles`;
3. the future compiled semantic shape fits the frozen public model end-to-end.

No production terminal behavior or public API is introduced by T31.

## Package and artifact boundary

The final package remains managed and dependency-free.

The package verifier rejects:

- unexpected runtime DLLs;
- native library payloads;
- runtime NuGet dependencies;
- repository-only test/tool content;
- compiled fixture `.bin` files;
- fixture/source `.ti` files;
- missing portable symbols/Source Link repository metadata.

Its fresh consumer exercises the intended 0.8 public features, including
standard metadata/enumeration, descriptions, reusable parameter programs,
extended expansion, exact Latin-1 bytes, terminal-aware padding, and the
Windows Console/Windows Terminal profiles.

## 0.9 boundary remains closed

The final 0.8 package still contains no production implementation for arbitrary
host terminfo acquisition.

Required 0.9 work remains:

- `0432` compiled parsing;
- ncurses extended sections;
- `01036` / 32-bit numeric parsing;
- absent/canceled binary decoding;
- malformed/truncated compiled-entry diagnostics;
- explicit directory providers;
- `TERMINFO` / `TERMINFO_DIRS` and user/default search roots;
- encoded `TERMINFO=hex:...` / `TERMINFO=b64:...`;
- provider-instance loaded-description caching and refresh policy.

The T29 fixtures freeze that future input contract without turning fixture
handling into a production parser.

## Final release sign-off

After the T31 patch is committed, the repository is a **final 0.8.0 release
candidate**. Complete the release without modifying source/package content:

1. push the exact T31 commit to the `0.8.0` branch;
2. require all Windows/Linux/macOS Debug and Release jobs to pass;
3. require the package-validation job and fresh-package consumer to pass;
4. retain the `.nupkg` and `.snupkg` produced from that exact commit (or
   deterministic artifacts reproduced from that same commit);
5. tag that exact commit `v0.8.0`;
6. publish that exact `.nupkg` to NuGet.org and GitHub Packages and the matching
   `.snupkg` to the NuGet.org symbol server;
7. confirm a genuinely fresh consumer can restore and use the published package.

If any source or package content changes after successful validation, the T31
completion gate must be rerun before tagging or publication.
